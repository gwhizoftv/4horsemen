# Plan Review — Issue 109

## Findings

1. **Claude plan — `src/state.ts`, `src/cli.ts`, and `src/runLoop.ts` drop handling:** the plan says `dropAgent` nulls any derived record whose inputs cite the dropped agent, the CLI leaves re-derivation to the next tick without moving the issue cursor, and `R7.finalize` falls back to accepted `R4.implement` pins when derived consensus is absent. Every allowed roster change must recompute or deliberately roll back every affected canonical decision before downstream routing. If a non-reviser voter is dropped after unanimous consensus has advanced the cursor to `R7.finalize`, this plan nulls consensus, never revisits `R6.ballot` where consensus derivation occurs, and prepares finalization against an implementation pin instead of the accepted revision pin. Recompute and journal the superseding consensus during the drop mutation, or reset to `R6.ballot` and block finalization until the replacement is persisted.

2. **Claude plan — `src/derive.ts` decision identity and test 2:** the plan defines identity as `kind + inputSetHash (+ round)` while its tie-break test says reordering `activeRoster` flips the winner and “changes nothing else.” A durable identity must change whenever a semantic election input, including the ordered tie-break roster and eligible candidate set, changes. As written, two plan elections can select different winners but have the same `decisionId`; the machine then treats the old stored identity as current, skips replacement, and routes implementation to the stale winner. Include ordered roster and eligible accepted plan/implementation citations in the canonical hash (or otherwise in the durable identity) and assert that reordering the roster changes both hash and identity.

3. **Cursor and Claude plans — runtime-version file maps and test updates:** both plans bump `RUNTIME_FORMAT_VERSION` from 2 to 3 but omit `test/cursorHookUsage.test.ts` and `test/support/fixtures/analytics-journal.jsonl`, which contain literal version-2 journal records parsed by the strict `journalEventSchema`. A breaking strict-schema bump must update every active fixture that is expected to remain supported while separately testing rejection of old runtime state. Following either file map leaves those active fixtures at version 2, so `pnpm check:fast` fails in cursor-hook usage and analytics before the new workflow can be accepted. Add both files to the change map and update their live fixtures to version 3; keep explicit version-2 rejection cases in `test/state.test.ts`.

## Conclusion

Revisions are required before either peer plan is mechanically safe. The Claude plan can lose or suppress valid replacement decisions after roster changes, and both peer plans omit strict-version fixtures that make the required fast suite fail. The implementation plan selected for execution should hash the full semantic decision input (including roster order), cascade or roll back drop invalidation before downstream actions, and include all runtime-version fixtures in its exact file map.
