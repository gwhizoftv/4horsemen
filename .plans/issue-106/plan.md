# Issue 106 plan — stdin EPIPE must not kill the coordinator

`runTmux` (`src/tmux.ts:13-23`) spawns tmux with `stdio: ["pipe", "pipe", "pipe"]`
and finishes with `child.stdin.end(input ?? "")` (`src/tmux.ts:22`). When tmux has
already exited, that write fails with `EPIPE`. Nothing is subscribed to the
`error` event of `child.stdin` — `child.once("error", reject)` (`src/tmux.ts:20`)
subscribes to the **ChildProcess**, not to its stdin socket — so Node re-throws
the stream error as an unhandled `'error'` event and the whole coordinator
process dies mid-tick. That is exactly the reported stack: `Writable.end` →
`Socket.end` → `dist/tmux.js:15:17`, the compiled form of `src/tmux.ts:22`.

Fix: subscribe to `child.stdin`'s `error` event so the failed stdin write is
recorded and the promise settles from the existing `close` handler with tmux's
real exit code and captured output.

## Exact File List to be changed or deleted

- `src/tmux.ts` — in `runTmux` (lines 13-23), attach `child.stdin.once("error", ...)`
  before `child.stdin.end(input ?? "")`. The handler appends a one-line diagnostic
  (`error.code ?? error.message`) to the already-captured `stderr` accumulator
  declared at line 17 and returns; it does not reject and does not resolve. The
  existing `child.once("close", ...)` handler (line 21) stays the sole settler, so
  the call still reports `exitCode`, `stdout`, and `stderr` for that tmux
  invocation. No signature, no export, and no type changes: `TmuxRunner`
  (`src/tmux.ts:10`) and every `this.runner(...)` call site in `TmuxController`
  are untouched.
- `test/tmux.test.ts` — add one `describe("runTmux", ...)` block with the single
  new case described under Tests, and extend the existing import list from
  `../src/tmux.js` (lines 5-23) with `runTmux`.

Nothing is deleted. `dist/` is gitignored (`.gitignore` line 2) and is not part
of this change; it is regenerated by `pnpm build`.

## Exact file list to be created

None. The production fix belongs in the function that raises the error
(`src/tmux.ts`), and `test/tmux.test.ts` is the existing test file for that
module, so no new file, module, abstraction, or dependency is justified.

## Tests

One new case, added to the existing `test/tmux.test.ts` (no new test file), in a
new `describe("runTmux", ...)` block at the end of the file:

- **"resolves when tmux exits before reading stdin"** — `mkdtempSync` a temp dir,
  write an executable stub `tmux` (`#!/bin/sh\nexit 3\n`, mode `0o700`) into it,
  push the dir onto the existing `roots` array, prepend it to `process.env.PATH`,
  and in a `try`/`finally` that restores the prior `PATH`, `await runTmux(["-V"],
  "x".repeat(4 * 1024 * 1024))`. The stub exits without reading stdin; 4 MiB far
  exceeds the ~64 KiB pipe buffer, so the parent's write outlives the child and
  fails with `EPIPE` deterministically on macOS/Linux. Assert
  `result.exitCode === 3` (the close handler still reports tmux's real exit) and
  `expect(result.stderr).toContain("EPIPE")` (the failure was recorded, not
  swallowed).

  Fails before the change: the stdin `error` event is unhandled, so Node raises
  an uncaught exception and vitest fails the run with an unhandled error rather
  than completing the assertions. Passes after the change: the promise settles
  from `close`, and both assertions hold.

No other test needs to change: `runTmux` has no existing coverage
(`grep -rn "runTmux" src test` matches only its definition and the
`TmuxController` default), and every current `TmuxController` test injects a fake
`TmuxRunner`, so none of them exercise `spawn`.

Commands to run before committing (from `AGENTS.md`): `pnpm check:fast`
(`pnpm lint && pnpm typecheck && pnpm test:fast`). The coordinator's stricter
list is `pnpm check` (`pnpm build && pnpm check:fast && pnpm test:e2e`).

## Alternatives Rejected

- **Reject the promise on stdin `error`.** It stops the crash but converts a
  harmless empty-terminator write into a thrown `Error` at call sites such as
  `src/tmux.ts:685`/`694`/`787`, which turn a rejected runner into a fatal
  "tmux is unavailable" / "cannot launch" throw. The issue asks that one bad
  tmux call log and continue; rejecting keeps the run loop dying, just with a
  nicer message.
- **Resolve from the stdin `error` handler.** Would settle before `close`, losing
  the real exit code and any stdout/stderr tmux had produced, and would make
  `capture-pane`/`display-message` readings silently empty. The `close` handler
  is already the correct single settler.
- **Filter to `code === "EPIPE"` and re-throw everything else.** Any stdin write
  failure has the same meaning here — the input could not be delivered — and the
  child's exit is still the authoritative outcome. Re-throwing another code
  (e.g. `ERR_STREAM_DESTROYED`, `ECONNRESET`) reintroduces the same unhandled
  crash for a case with no better recovery, so the handler records the code
  instead of branching on it.
- **`stdio: ["ignore", ...]` for tmux.** Removes the failing write entirely, but
  drops the `input` parameter of the public `TmuxRunner` type (`src/tmux.ts:10`)
  and the ability to feed tmux via stdin at all. Larger blast radius than the
  bug requires.
- **Add a logger or a spawn-injection parameter to `runTmux` for testability.**
  A new dependency/abstraction the fix does not need: the `PATH`-stub test
  exercises the real `spawn` path, and appending to the existing `stderr`
  accumulator is the log, surfaced by the call sites that already interpolate
  `result.stderr`.
- **`vi.mock("node:child_process")`.** No test in this repo uses `vi.mock` or
  `vi.spyOn`; the convention is dependency injection and real fixtures. A module
  mock would also stub out the very `spawn` wiring the regression is about.

## Risks and Mitigations

- **A genuine stdin delivery failure becomes invisible.** Mitigation: the handler
  appends the error code to the captured `stderr`, which the existing throw sites
  (`src/tmux.ts:685`, `694`, `714`, `787`, `895`) already interpolate, so a
  failing tmux call still names the stdin failure. Confirmed no caller passes
  `input` today, so no payload can be silently lost.
- **The 4 MiB write does not produce `EPIPE` on some platform, making the new
  test flaky.** Mitigation: the write only completes if the child drains it, and
  the stub `sh` exits without reading; a write to a pipe with a closed read end
  fails with `EPIPE` on macOS and Linux (Node ignores `SIGPIPE`). The repo is
  already POSIX-only in this area (`osascript`, `#!/bin/sh` fixtures, tmux
  itself). If the assertion proves unstable in CI, the narrower assertion
  `exitCode === 3` alone still fails pre-fix via the unhandled error.
- **Mutating `process.env.PATH` leaks into sibling tests.** Mitigation: the case
  saves and restores `PATH` in a `finally`, and registers its temp dir with the
  existing `roots`/`afterEach` cleanup.
- **The fix masks a different failure mode where tmux dies mid-command.**
  Mitigation: it does not — `close` still reports tmux's non-zero exit code and
  stderr, so `ensure`/`launch` call sites keep throwing exactly as they do today.
- **The installed tree (`~/.local/share/coordination/dist`) keeps crashing until
  rebuilt.** Mitigation: `dist/` is gitignored and regenerated by `pnpm build`
  (part of `pnpm check`); the fix lands in `src/tmux.ts`, which is the only
  tracked source of `dist/tmux.js`.

## Conclusion

The crash is one missing subscriber: `child.once("error", reject)` covers the
ChildProcess, not `child.stdin`, so the `EPIPE` from `child.stdin.end(input ?? "")`
at `src/tmux.ts:22` escapes as an unhandled `'error'` event and takes the
coordinator down mid-tick. Attaching `child.stdin.once("error", ...)` that records
the code into the existing `stderr` accumulator makes that write non-fatal while
leaving the `close` handler as the single settler, so a bad tmux call reports its
real exit code and the run loop continues. The change is confined to three lines
in `src/tmux.ts` plus one regression case in `test/tmux.test.ts`, with no new
files, exports, parameters, or dependencies, and is verified with `pnpm check:fast`.
