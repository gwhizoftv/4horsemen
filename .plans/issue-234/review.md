## Findings

1. **[P1] Cursor's selected PATH would also select Node for product checks.** The wrapper steps 3–5 and the risk paragraph saying that nvm's PATH mutation is “acceptable and desired” propose retaining the selected environment for the final `exec node`. The issue requires coordinator runtime selection to preserve the workspace's development runtime for product operations, including child processes; preserving only the parent interactive shell is insufficient. When a product uses Node 16 and the wrapper selects Node 26, coordinator-run product checks inherit the new PATH and execute under Node 26. The default process runner inherits process.env (`src/runLoop.ts:141`), as does hook verification (`src/hookPolicy.ts:188`). Thus a successful coordinator startup changes the runtime of the very product work being coordinated. Resolve an absolute coordinator executable, scope any PATH adjustment to coordinator build subprocesses, and test a product child command's Node/PATH after startup.

2. **[P1] Cursor and Antigravity's wrapper-only scope leaves coordinator callbacks on the incompatible runtime.** Both exact file lists change only the root wrapper and its test; Cursor additionally says one wrapper is the only production caller, while Antigravity concludes this fixes all coord commands. Coordinator-owned JavaScript invoked through Git and harness callbacks must use a supported Node even when the product PATH remains old. Antigravity's proposed correct preservation of PATH leaves `gitCredentialHelperCommand` (`src/githubAuth.ts:36–37`) invoking `/usr/bin/env node`; onboarding a private HTTPS product that needs this helper can therefore still fail under Node 16 after the wrapper successfully selects Node 26. In both plans, agent launchers subsequently select the product .nvmrc (`scripts/lib/launcher.sh:19–29`), after which Git verification (`githooks/lib/policy.sh:51,60`), lifecycle/guard receivers and credential helpers again execute the driver under ambient Node. Extend the file map to the actual coordinator dispatch boundaries and add a focused callback/hook regression with an old product PATH. Rewriting product checks or the product's launcher selection is unnecessary.

3. **[P1] Claude's resolver location breaks vendored Git hooks.** Design → Callers derives the install root from the hook library's own BASH_SOURCE location and expects the resolver below that root. Supported shim and vendor installations must both locate the coordinator runtime without weakening verification. In vendor mode, `plannedHookContents` copies policy.sh into the clone's Git hooks directory (`src/hookSync.ts:182–184`), and install deliberately clears coord.installRoot while retaining coord.cliEntry (`src/install.ts:488–489`). Walking upward from the copied policy library therefore reaches the clone's Git directory, not the coordinator install; no scripts/coord-node is installed there. All otherwise valid vendor commits/pushes would fail the new resolver-executable check even with a supported Node present. Derive the install from the recorded CLI entry, or explicitly ship the required resolver and its requirement data with vendored hooks. Extend the existing installed vendor-hook test; the proposed test that sources the repository's canonical policy library cannot expose this failure.

4. **[P2] Cursor, Claude and Antigravity do not mechanically authorize their principal edit.** Their exact file lists name the extensionless root token `coord`. Every intended product change must be represented by the coordinator's extracted approved paths, and that map should stay within the stated scope. The current `isFileMapPath` rejects extensionless single-segment tokens (`src/evidence.ts:84–106`). Running `extractApprovedPaths` on all three bound plans confirms that none authorizes the root coord file, so their central implementation change would fail scope validation. Claude's prose also contributes a literal src/ token outside Reuse and Scope, authorizing the entire source tree despite its narrower explicit list. Use a parser-supported representation for the existing root file (Codex's documented coord/ token matches it under the current tree-root matcher), and keep reference-only paths within Reuse and Scope or outside file-map token syntax. Validate the complete extracted map, not just that it is nonempty. No evidence-parser product change is necessary for this issue.

5. **[P2] Codex's file map omits an existing assertion affected by its credential-helper change.** Its src/githubAuth.ts row replaces ambient Node with process.execPath, but its exact test list omits test/mirror.test.ts. The approved map must include existing tests whose observable contract changes so the required suite can pass without unauthorized scope expansion. `test/mirror.test.ts:94` compares every bound mirror Git call against the exact old `!/usr/bin/env node ...` helper string. BareMirror uses the same gitCredentialArgs builder, so following the plan changes those arguments and deterministically fails this existing fast test. Add test/mirror.test.ts to the changed-file list and update that assertion alongside the other credential expectations; include it in the focused fast-tier command. This is an expectation update in an existing test, not a new abstraction or fixture.

6. **[P2] Cursor and Antigravity's focused commands select a configuration that excludes the target test.** Cursor's Tests section uses the fast vitest.config.ts explicitly; Antigravity's command uses that default configuration implicitly. A named verification command must actually execute the proposed regressions. That configuration explicitly excludes test/wrapper.test.ts; the suite belongs to vitest.system.config.ts. I ran `pnpm exec vitest run --config vitest.config.ts test/wrapper.test.ts` to check this finding: it exited 1 with “No test files found” and executed no tests. Use `pnpm exec vitest run --config vitest.system.config.ts test/wrapper.test.ts`. Cursor should also make the successful old-Node-to-compatible-Node fallback regression required: its current mandatory tests cover refusal and an already-compatible PATH, but do not establish the issue's selection behavior.

## Conclusion

Revise each plan before treating it as implementation-ready. Claude provides a useful shared runtime-resolution design once the vendor-hook lookup and extracted scope are corrected. Codex covers the relevant runtime boundaries and explicitly tests environment isolation, but must add the missing mirror assertion to its approved map. Its captured process.execPath also carries the disclosed operational tradeoff that removing an old Node installation requires regenerating callbacks; Claude's runtime resolver avoids that dependency. Cursor and Antigravity need coordinator callback coverage in addition to their wrapper changes, and Cursor must correct PATH inheritance.

All four reuse the existing wrapper and existing test files rather than creating parallel test frameworks. The shared shell executable in Claude and Codex is justified by multiple callers that must select Node before driver imports; neither introduces a dependency. Codex's broader bootstrap/trust changes correspond to identified coordinator execution sites, rather than unrelated cleanup. Antigravity's extra fnm discovery is not covered by its two proposed regressions and is unnecessary when an explicit executable override is available; it should be omitted or supported with an actual focused case. The required tests should establish runtime selection and product-environment preservation, with existing assertions updated where command rendering changes.
