### Findings

1. **[P1] Claude `src/verificationRunner.ts:108-134`; Cursor `src/verificationRunner.ts:117-148` — dependency state is absent from receipt identity.** A reusable result must bind the dependency state actually consumed by the command, or remain uncached when that state cannot be established. Both implementations construct the key from the source tree, argv, policy, versions/probes and named environment, with no dependency/generated-input identity. An uncached preparation/install command can produce different `node_modules` bytes on the second request while all those fields remain identical; the second lint/test command is then skipped using the first success even if the current dependencies make it fail. A lockfile and `node --version`/`pnpm --version` are not a measurement of the installed bytes. The shipped examples enable this reuse for the test tiers as well as lint/typecheck. Focused regression: keep pin, policy, probes and command argv unchanged, make the preparation command write `good` then `bad` into an ignored dependency, and make the check fail on `bad`. Both peer runners returned success twice with only one check invocation in the in-memory reproduction; Codex ran the check again and rejected the second request. Add an explicit dependency-input declaration and fail closed when its identity is unavailable; do not merely add another source-tree hash.

2. **[P1] Claude `src/verificationRunner.ts:158-164,184,238-248`; Cursor `src/verificationRunner.ts:206-219,302-306` — dirty execution inputs can satisfy the pinned gate.** A result must prove the immutable submitted product, and a dirty checkout must not authorize receipt reuse. Claude checks cleanliness only on the cache-miss execution path and only uses it to suppress receipt creation; a receipt hit bypasses that check entirely, and a successful command that mutates tracked input still returns success. Cursor neither checks tracked cleanliness nor suppresses a receipt after a mutation. Thus an earlier preparation command can change tracked source before a cached check and both runners return the old success without testing that source. Cursor additionally persists and later reuses an exit-0 result from a command that modified tracked source. The reproduction confirmed both dirty-before-hit cases; a mutating exit-0 command was accepted by both, with Cursor caching it, while Codex rejected it and wrote no receipt. Test both mutations separately, including a pre-existing valid receipt, and require rejection rather than just omitting a new receipt.

3. **[P2] Cursor `src/verificationRunner.ts:223-253`; `src/verificationReceipts.ts:168-169,206-214` — live work can lose exclusive ownership.** Same-key consumers must join the existing execution, and expensive-slot ownership must not expire solely because a live suite is slow. After 30 minutes the runner leaves the join loop with `keyLock === null` and proceeds to execute without owning that key. Separately, the receipt module reclaims a lock older than six hours even when its PID is still alive, and the old holder's release unconditionally unlinks the replacement holder's path. A sufficiently slow valid check can therefore execute concurrently twice; successive waiters can also exceed the configured expensive-suite bound. Test with an advanced fake clock while keeping the first owner alive: a second request must not enter the command, and releasing an old token must not remove a new owner's lock. This is a source-level finding, not a claim that a 30-minute/six-hour real-time test was run.

4. **[P2] Claude and Cursor `package.json:13-19`, together with their `vitest.config.ts` system-suite exclusions — existing manual coverage shrinks without an owner policy change.** Owner-driven manual branches must retain their configured checks unless the owner explicitly changes that policy. With the existing installed `verify.precommit = check:fast` and `verify.prepush = test:e2e`, both pins remove the nine system files from `test:fast` while leaving `check:fast` without `test:system`. An upgrade therefore stops running installer/hook/workspace coverage on manual commits and pushes. Adding `test:system` to `config.example.json` and telling an owner to migrate the live config does not preserve unchanged installations. A regression should retain an old workspace config and assert that the combined manual commit/push coverage still includes all pre-existing suites. Codex's compatibility aggregate retains system tests in `check:fast`, while keeping the independently callable `test:fast` tier selective.

5. **[P2] Cursor `src/verificationReceipts.ts:95-105`; `src/verificationRunner.ts:208-218,235-248` — reused results lose their command logs.** Every reviewer must receive the same command result and its usable log, including when the command was reused or joined. The receipt schema stores no log path, and the hit/join branches omit `CheckResult.logPath` and set the record's log to null. After a successful candidate is reused by another candidate or revision, `src/action.ts:150` consequently renders an empty log path. The first execution's log file still exists but is not linked from the result. Extend the existing reuse/join tests to require an existing original log path in both the returned result and generated reviewer action; retain and validate that path in the receipt.

6. **[P2] Codex `src/verificationReceipts.ts:59-78`; `src/verificationRunner.ts:42,109`; `config.example.json:168-169,198-199` — the shipped dependency fingerprint includes the random worktree location.** Equivalent declared inputs must produce a stable receipt key across fresh materializations; irrelevant scratch-directory names must not force reruns. The example fingerprints the entire `node_modules` tree byte-for-byte. pnpm's generated `node_modules/.bin/tsc` shell wrapper embeds absolute worktree paths in `NODE_PATH`, while every verification request uses a new `.verification-<uuid>` directory. Those different wrapper bytes change `dependencyIdentity` even for the same pin, lockfile, installed package contents and toolchain. Consequently the example's cacheable lint/typecheck commands miss instead of sharing a result across fresh installs. A focused in-memory check used the real installed pnpm wrapper, relocated only its worktree prefix, and passed both virtual trees through the exact pinned `dependencyIdentity`: the digests differed. This was not a two-install integration run. Add that realistic fresh-install regression and define a stable, audited dependency identity that retains substantive package/tool changes without treating generated location-only metadata as a new dependency version. Do not solve this by dropping dependency identity altogether. Keeping commit-sensitive tests/build uncached pending an input audit is reasonable and is not itself this finding.

### Scope, reuse, and coverage comparison

- All three keep the issue's opt-in coordinator mode, candidate/final runner, explicit path mappings, receipts, bounded diagnostic retries, analytics, and unit/system split together. The coordinator-provided changed-path lists show the same four justified new files: two verification modules, one runner test file, and one system-test config. None changes hook bodies, adds dependencies, bumps the package version, or changes the live workspace configuration.
- All reuse the existing change classifier, mirror/worktree lifecycle, process-runner injection, accepted-result state, verification measurements, and action rendering. Candidate failures use the existing rejected-submission/reissued-action route; final selection remains classified from the frozen baseline. Existing action, state, hook, run-loop, analytics and configuration tests are extended rather than replaced.
- Claude stays particularly close to the selected plan and carries original log paths on reuse. Its smaller receipt implementation omits dependency binding, and its dirty check protects receipt writes rather than the gate itself. The six focused tests in its new runner file do not cover those failure cases.
- Cursor separates the same responsibilities, but carries an additional returned-record representation and loses logs on cached paths. Its broader runner tests cover happy-path reuse, corruption, failure, retries and ordinary contention, but not dirty input, changed dependencies, live-lock expiry, or replacement-owner release.
- Codex adds stricter origin/policy/clone binding, explicit dependency metadata, exact-commit default keys, post-execution input validation, hashed environment values, preserved original logs, and serialized lock admissions. These are justified by the issue's trust/equivalence requirements, not unrelated scope. It extends one additional existing file, `test/cli.test.ts`, to cover the frozen policy snapshot. Its nine runner tests cover more of the failure boundary, but use simplified dependencies that miss finding 6. The dense implementation would benefit from keeping the regression readable; no broad refactor is requested.
- All pins leave protected `AGENTS.md` unchanged and put coordinator-mode wording into the protocol template/generated actions. Codex's ordinary staging refusal was reported rather than bypassing the skip-worktree protection. This is a disclosed owner-managed documentation limitation, not evidence that the index flag should be cleared.
