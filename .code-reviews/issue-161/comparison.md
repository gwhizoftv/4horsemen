### Findings

Paths and line numbers below refer to the named candidate's bound worktree.

1. **Antigravity — `src/cli.ts:569-582` — P1: implicit controls can target another workspace.** An inferred agent workspace must match both the configured agent identity and canonical clone root, and invalid/ambiguous context must fail closed. This branch accepts any existing `coord.workspaceConfig` without either check; it also swallows resolution errors and falls back to generic context at line 589. A clone carrying another installation's locator can therefore run `pause` or `resume` against that installation's same-numbered issue. Illustrative test: give clone A the config locator for B, with no matching agent root in B; implicit `resume --issue 161` must throw before changing either runtime. Also retain nested/legacy ambiguity errors rather than falling through.

2. **Antigravity — `src/runLoop.ts:982-1020`, `src/interactive.ts:176-178` — P1: `n` performs concurrent delivery instead of queuing one selected task.** The interactive callback must only queue a captured request in the existing loop; completion validation and the loop's serialized effects must remain authoritative. Here bare `n` calls `requestReminder()` with no selection, defaults to the entire active roster, mutates cursor deferrals, and immediately awaits `maybeLifecycleNudge`. Meanwhile `runIssue` is already awaiting the same loop's `run()` (`src/cli.ts:834-879`). A reminder can race a tick's pending effect, invalidate its cursor revision, or resend a task whose completion marker is already present; there is no receipt check in this path. Illustrative test: suspend a tick in an asynchronous resource observation, write a completion, press `n`, and require no cursor mutation or keys until the tick validates that completion.

3. **Cursor — `src/runLoop.ts:2995-3014` — P1: queued reminders outrank completion receipts.** A receipt read before reminder execution must win over delivery. The tick already has `completion` from line 2978, but drains the reminder before testing whether it is missing. An idle agent that has submitted a valid receipt can receive another copy of the task; at four sends this path can instead create a nudge-loop hold and return before accepting the submitted work. Illustrative test: enqueue a reminder, publish a valid completion, run one tick, and assert validation occurs with no nudge and no new budget hold.

4. **Claude — `src/runLoop.ts:1291-1314`; Cursor — `src/runLoop.ts:1204-1230` — P1: owner reminders do not consistently require fresh idle proof or per-key lifecycle checks.** Every explicit reminder must retain current idle-marker/composer proof and veto queued or newly observed activity. Both implementations omit an `execution === "queued"` veto, and install `IdleOverride` only for stale `working` or ready-file cases. For an initially idle/queued record, they use ordinary vendor-prompt delivery with no reminder lifecycle callback. Thus a queued record with zero pending count (for example after an older turn's Stop), or new hook activity during typing, can still be sent/submitted to instead of deferred. Illustrative tests: request a reminder with queued execution and a ready-looking vendor prompt; separately change lifecycle activity after typing but before Enter. Both must prevent submission. A plain vendor prompt without the required current idle marker must not authorize the owner-reminder path.

5. **Claude — `src/interactive.ts:191-195`, `src/runLoop.ts:1001-1022`; Cursor — `src/interactive.ts:182-185`, `src/runLoop.ts:934-948` — P2: menu choices rebind to replacement tasks.** The action/digest/session selected by an open reminder menu must remain its identity, not be discovered when the row is eventually selected. These menus capture only the agent name. If action A completes and B is assigned while the menu remains open, selecting the old row snapshots and reminds B instead. Cursor additionally stores no session identity in its queued request, so a restart between queueing and execution does not invalidate that request. Illustrative test: open the menu for A, replace it with B, then choose the old row; reject it with zero sends. Also queue a request and replace its session without changing its action; discard it.

6. **Cursor — `src/runLoop.ts:1223-1225`, `src/tmux.ts:1085-1098` — P2: the motivating accepted-but-stale-working case cannot be reminded.** An acknowledgment from the earlier delivery must not count as a lifecycle change or acknowledgment of a new reminder attempt. The callback immediately returns `accepted` for the action's existing acceptance. Before the first key, `submitting` is false, so tmux refuses this as `lifecycle-changed`. An agent that acknowledged its plan task, drafted it, and returned to an idle sentinel without a Stop remains stuck when the owner presses `n`. A direct boundary probe with valid current idle proof and the existing-acceptance callback returned `{status:"busy", reason:"lifecycle-changed", stage:"prompt"}` with zero keys. Extend the run-loop fixture to exercise that same already-accepted action through real `TmuxController.nudge`, not a nudge stub.

7. **Antigravity — `src/runLoop.ts:1019`, `src/runLoop.ts:1170-1175` — P2: `n` never enables same-action stale-working recovery.** Explicit owner recovery may challenge a stale working record using fresh terminal idle proof, while automatic delivery must remain restricted. This implementation invokes the unchanged automatic idle path; `deliver` permits a working override only when sends is zero and the action is still ordered and never injected. Consequently an already acknowledged, already sent task with fresh idle proof remains vetoed even though the UI reports that a reminder was requested. Illustrative test: send/acknowledge a task, leave lifecycle working, display its current idle sentinel, request a reminder after backoff, and require one guarded resend of that same action.

8. **Claude — `src/agentLifecycle.ts:645-650`; Antigravity — `src/agentLifecycle.ts:685-690`; Cursor — `src/agentLifecycle.ts:729-738` — P2: an old turn's Stop clears the current missing-Stop warning.** Advisory episodes must count distinct turns and be cleared only by the matching current Stop; delayed older-turn callbacks must not hide missing current confirmation. After prompts t1 and t2, a delayed Stop(t1) resets Claude's entire episode and Antigravity's missing count; Cursor removes t1 and drops below its warning threshold despite t2 still lacking Stop. Direct calls to each pin's `applyLifecycleObservation` reproduced these outcomes; Codex retained `[t1,t2]` for the same input. Test both old-Stop non-recovery and current-Stop recovery, as well as duplicate prompts and replacement sessions. Antigravity also has no completed-action fallback when turn IDs are unavailable; its counter only advances at `src/agentLifecycle.ts:673-674` for an identified prompt.

9. **Codex — `src/workspace.ts:173-176`; Cursor — `src/workspace.ts:184-185` and `src/cli.ts:513-515` — P2: a valid owner locator silently wins over a conflicting agent locator.** Implicit context must reject ambiguous installed locators rather than choose one workspace. If the same worktree has an individually valid owner locator for A and an agent locator for B, these early returns never compare them; owner controls can mutate A although the agent wiring denotes B. A controlled in-memory locator test confirmed both select A; Claude's corresponding helper refuses the conflict. Extend the existing workspace fixture with two distinct, otherwise valid locators and require an explicit root instead of precedence. This is the remaining concrete correction identified in the recommended Codex base.

### Scope, reuse, and coverage

- **All four:** the supplied changed-path lists stay within the approved existing modules and documentation. None adds a product file, dependency, or product-hook change. Existing report, interactive menu, lifecycle, delivery, workspace, and verification seams are reused; there is no unrelated architecture rewrite.
- **Codex:** most complete safety integration. Its menu captures action/digest/session/hook sequence, the loop discards requests on completion/pause/replacement, and every owner reminder uses the per-key override with completion/activity rechecks. It reuses doctor's read-only inspection and actual containment coverage, supplies framed reports and verification progress, and extends all nine corresponding existing test files. Coverage includes real terminal/composer behavior, stale selections, privacy, context, and warning correlation. The dual-locator gap above is not covered by its invalid-owner-locator test.
- **Claude:** similarly broad implementation and focused additions across all nine existing test files. Its explicit progress events, shared doctor inspection, queued request mechanism, completed-action warning fallback, and conflicting-locator rejection are useful. The new `reopenActionForReminder` helper has a specific same-action acknowledgment purpose rather than speculative generality. Its tests exercise a real stale-working resend and completion/pause handling, but do not cover the menu-time binding, non-working reminder guard, or old-turn warning failures above.
- **Cursor:** keeps changes local and reuses `deliver`, but adds tests only in CLI, interactive, report, and run-loop suites. The reminder UI test verifies a callback receiving an agent name, not a bound task or real accepted-action send. New lifecycle, doctor, workspace, and tmux behavior lacks corresponding focused test changes. The extra owner-resolution try/catch duplicates a lookup already performed by its helper. These savings in test surface do not compensate for the completion-order and reminder defects.
- **Antigravity:** smallest coverage, not smallest complete solution. Only the same four suites are changed; no tmux changes implement the new reminder boundary. Its startup helper is a narrow file inspection called during start, rather than the selected plan's startup/resume runtime-binding diagnosis. The existing interactive menu and run-loop queue opportunities are not actually reused for `n`. Its new progress test conditionally skips its assertions if no action exists, so it does not establish the claimed completion/check/push ordering.
