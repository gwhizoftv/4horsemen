# Proposal — make agent setup a coordination deployment, not a per-repo copy

*Draft issue body. Not a registered plan.*

## Problem

Onboarding a repository to the multi-agent workflow currently requires copying
the machinery **into** that repository and committing it before setup will run:

```
scripts/setup_common.sh:355
  [[ -d "$hd" ]] || die "Clone has no tracked githooks/ directory.
     Merge the hook migration into $SHARED_BRANCH first, then re-run setup."
```

So the sequence is copy-first, run-second. `testapp` today carries its own
`scripts/setup_*.sh`, `scripts/lib/launcher.sh`, `scripts/fresh-issue.sh`, and
`githooks/**` — byte-identical duplicates of `coordination`'s, except where they
are not.

### This has already gone wrong

After exactly one downstream project, the copies have diverged:

```diff
$ diff coordination/githooks/pre-push testapp/githooks/pre-push
21c21
< workflow_critical_prefixes=("scripts/" "githooks/" "src/" "test/")
---
> workflow_critical_prefixes=("scripts/" "githooks/" "src/")
```

`testapp`'s pre-push hook does not treat `test/` as workflow-critical. Nobody
decided that; it is drift. With *n* projects the failure mode is *n* subtly
different enforcement policies, each looking authoritative in its own repo, and
a fix applied in one place silently not reaching the others.

### Why the coupling exists

`githooks/post-merge` regenerates `start-<agent>.sh` from
`scripts/lib/launcher.sh`, so the launcher library must be present in the target
repo for hooks to work; and `common_install_hooks` refuses to run unless
`githooks/` is already tracked there. Each dependency justifies the other, and
together they force the copy.

## Goals

1. **One deployment.** Installing coordination against a new codebase is a
   single command against an unmodified target repository.
2. **Single source of truth.** Hook logic, launcher generation, and setup logic
   live in `coordination/` and nowhere else.
3. **Upgrades propagate.** Fixing `pre-push` once fixes every onboarded project.
4. **Hook loss is loud.** A missing or moved coordination install must fail the
   commit or push with a clear message — never silently run no hooks.
5. **Per-project policy stays per-project.** Check commands, harness roster,
   branch conventions, and the `test/`-vs-`src/` question are project facts and
   must remain configurable per repo.

## Non-goals

- Changing the workflow protocol, the driver, or `coord start|run|next|…`.
- Publishing coordination to a registry. Deployment is "clone it and run it".
- Supporting repositories whose contributors have not installed coordination.
  Hook enforcement requires the install; see *Risks*.

## Proposal

### A. Coordination owns the machinery

Move to `coordination/` as the sole copy:

```
coordination/
  install/
    hooks/                  ← the real hook bodies (was githooks/)
      pre-commit  pre-push  commit-msg  post-commit  post-merge
      lib/identity.sh
    shim/hook.sh            ← the ~15-line committed stub, see B
    templates/
      AGENTS.md.tmpl
      agent-shim.md.tmpl    ← CLAUDE.md and equivalents
      launcher.sh.tmpl
    agents/                 ← per-harness knowledge, was setup_<agent>.sh
      claude.sh  codex.sh  cursor.sh  antigravity.sh
  src/install.ts            ← `coord install`, `coord doctor`, `coord upgrade`
```

`scripts/setup_*.sh` and `githooks/**` are deleted from every target repo.

### B. Hook delivery: committed shim, central body

The decisive constraint is that `core.hooksPath` is all-or-nothing — if it points
at a missing directory, git runs **no hooks and reports nothing**. Pointing it
straight at the coordination install would make an uninstalled or relocated
coordination silently disable every guard in the system. For this project that
failure mode is unacceptable on its face.

So each target repo commits one generated shim per hook — small, stable, and
effectively never edited:

```bash
#!/usr/bin/env bash
# Generated by `coord install`. Do not edit; edit coordination/install/hooks.
set -euo pipefail
here="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
install_root="$(git config --get coord.installRoot || true)"
[[ -n "$install_root" && -d "$install_root/install/hooks" ]] || {
  echo "HOOK BLOCKED: coordination is not installed for this clone." >&2
  echo "  Run: coord install --repo $(git rev-parse --show-toplevel)" >&2
  exit 1
}
exec "$install_root/install/hooks/$(basename "$0")" "$@"
```

This gives all four properties at once: a fresh clone has hooks present, the
logic is central so it cannot drift, an absent install **fails closed and says
what to run**, and the shim body is stable enough that regenerating it is a
no-op in practice.

`coord.installRoot` is per-clone git config, so different clones may point at
different coordination checkouts — which is what the agent clones already need.

### C. One command

```bash
coord install --repo /path/to/testapp \
              --agents claude,codex,cursor,antigravity
```

From an unmodified target repo it:

1. reads or scaffolds `coord.project.json` (below);
2. creates sibling clones `<project>-<agent>` for each agent;
3. writes `AGENTS.md` and the per-agent shim from templates, if absent;
4. adds agent paths to `.gitignore`;
5. generates hook shims into `githooks/` and sets `core.hooksPath`;
6. records `coord.installRoot` and the identity config already used today
   (`consensus.agentId`, `agentLabel`, `sharedBranch`, `remoteName`);
7. generates `start-<agent>.sh` into each clone (untracked — the post-merge hook
   regenerates it from the central template);
8. prints exactly what it changed and what still needs committing.

Supporting commands:

| Command | Purpose |
| --- | --- |
| `coord install` | onboard or re-run idempotently |
| `coord doctor` | verify install root, hook wiring, launchers, identity config; non-zero on drift |
| `coord upgrade` | refresh shims and templates after pulling coordination |
| `coord uninstall` | remove shims, unset config, leave the project's own files |

`coord doctor` is the answer to "did someone move the coordination checkout" and
belongs in CI for onboarded projects.

### D. One config, two consumers

`coord.project.json`, committed at the target repo root:

```jsonc
{
  "project": "testapp",
  "origin": "https://github.com/gwhizoftv/testapp.git",
  "baseBranch": "main",
  "branch": "issue-{issue}/{agent}",
  "agents": [
    { "id": "claude", "harness": "claude", "delivery": "nudge" },
    { "id": "codex",  "harness": "codex",  "delivery": "pull" }
  ],
  "workflowCriticalPrefixes": ["src/", "test/", "scripts/"],
  "checks": [
    { "name": "install", "argv": ["pnpm", "install", "--frozen-lockfile"] },
    { "name": "check",   "argv": ["pnpm", "check"] }
  ]
}
```

`coord install` consumes it to build clones and hooks; `coord start` consumes the
same file for the roster, branch template, and final checks. That collapses
today's two sources of truth into one and resolves where the driver config
should live — a question that came up onboarding `testapp`.

`workflowCriticalPrefixes` is the `test/` divergence made into a project fact
rather than an accident. Clone roots are derived (`<parent>/<project>-<agent>`),
not configured, so the file stays portable.

### E. File ownership after the change

| File | Owner | In target repo? |
| --- | --- | --- |
| hook bodies, launcher/AGENTS templates, per-harness setup | coordination | no |
| `githooks/<hook>` shims | generated | **yes, committed** |
| `coord.project.json` | project | **yes, committed** |
| `AGENTS.md`, agent shim (`CLAUDE.md`, …) | project, from template | **yes, committed** |
| `.gitignore` agent entries | project | **yes, committed** |
| `start-<agent>.sh` | generated per clone | no (gitignored) |
| `.plans/`, `.signals/`, `.code-reviews/` | project | yes, on demand |

## Migration

1. Land `coord install` with both repos still on the old layout.
2. `coord install --repo testapp` → replaces `scripts/setup_*`, `scripts/lib/`,
   and `githooks/**` with shims. One commit, reviewable, `coord doctor` green.
3. Self-host: `coord install --repo coordination` for the driver's own clones.
   The canonical checkout is its own install root.
4. Delete the vendored copies from both repos.
5. Reconcile the `pre-push` divergence deliberately: set
   `workflowCriticalPrefixes` per project so the difference is recorded, not
   inherited.

Steps 2 and 3 are separately revertible; nothing forces a flag day.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Coordination checkout moves or is deleted | Shim fails closed with the exact remediation command; `coord doctor` in CI |
| Contributor without coordination installed cannot commit | Documented prerequisite; the shim message names the fix. Genuinely narrows who can contribute to onboarded repos — accepted, see below |
| Hook policy no longer versioned with the code it guards | `coord.project.json` is committed and carries the project-specific policy; central bodies are versioned in coordination and pinned by `coord doctor` reporting the install's commit |
| A bad coordination update breaks every project at once | Blast radius is the point of centralisation, and its cost. `coord doctor --pin` records the expected coordination commit per project so an upgrade is opt-in |
| Shim itself drifts | It contains no policy; `coord upgrade` rewrites it and `doctor` diffs it |

The contributor-prerequisite risk is real and worth stating plainly: today a
fresh clone of `testapp` gets working hooks with no external dependency. After
this change it gets hooks that refuse to run until coordination is installed.
That is a deliberate trade — correct-and-blocked over silently-unguarded — but
it is a trade, and for a repo with outside contributors it may be the wrong one.
`coord install --vendor` (materialise real bodies instead of shims, stamped with
the source commit, `doctor` warns when stale) should exist as the escape hatch.

## Alternatives considered

1. **Absolute `core.hooksPath` into the install, no committed files.** Cleanest
   and zero-drift, rejected because a missing install disables all hooks
   silently — the exact failure class this project exists to prevent.
2. **Git submodule for the machinery.** Versioned and self-contained, but adds
   submodule ceremony to every clone and every agent's workflow, and agents
   forgetting `--recurse-submodules` reproduces the silent-no-hooks failure.
3. **Publish an npm package, install as a devDependency.** Reasonable for
   JS/TS targets, but binds the workflow to a Node toolchain the target may not
   have, and `pnpm install` becomes a prerequisite for `git commit`.
4. **Keep copying, add a drift check.** A `coord doctor` that only diffs copies
   would catch the `pre-push` divergence, but leaves *n* copies to update and
   makes every fix an *n*-repo PR train.
5. **Do nothing.** Viable at two repos. The proposal is worth doing when the
   third arrives, and the drift above suggests that is already late.

## Acceptance criteria

- [ ] `coord install --repo <path> --agents …` onboards a repository with **no
      committed coordination files present beforehand**
- [ ] Onboarding `testapp` from a clean checkout requires no manual copying
- [ ] `scripts/setup_*.sh`, `scripts/lib/launcher.sh`, and `githooks/` bodies
      exist in exactly one place in the workspace
- [ ] A hook run with `coord.installRoot` unset or pointing at a missing
      directory **blocks** the operation and prints the remediation command
- [ ] `coord doctor` exits non-zero for: missing install root, unset
      `core.hooksPath`, stale shim, missing launcher, missing identity config
- [ ] `coord upgrade` after a coordination pull is idempotent — a second run
      changes nothing
- [ ] `coord install` is idempotent and safe to re-run over an existing install
- [ ] `coord start` and `coord install` read the same `coord.project.json`
- [ ] `workflowCriticalPrefixes` from that file drives `pre-push`, and the
      `testapp`/`coordination` difference is expressed there rather than by
      divergent copies
- [ ] Both repos migrated; vendored copies deleted; `coord doctor` green in each
- [ ] `docs/coord-driver.md` gains an installation section
- [ ] Tests: install into a throwaway repo, assert the file ownership table;
      hook-blocked-when-uninstalled; doctor detects each drift class; upgrade
      idempotence; install idempotence

## Open questions for the owner

1. **Shim vs vendor as the default.** Proposal picks the shim. If `testapp` (or
   any future target) expects outside contributors, vendored may be the better
   default with shim as opt-in.
2. **Should coordination self-host?** Step 3 has the driver's own clones depend
   on the driver's install. It is good dogfooding and a real bootstrap
   consideration.
3. **Pinning.** Should `coord.project.json` record the coordination commit it
   was installed from, so `doctor` can flag an unreviewed upgrade?
4. **Scope relative to issue 1.** This is orthogonal to the driver and should
   almost certainly be a separate issue, sequenced after issue 1 merges.
