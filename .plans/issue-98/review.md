## Findings

1. **Cursor plan — Exact File List (`scripts/lib/launcher.sh`) / missing `githooks/post-merge`.** The plan extends `write_launcher` with a required fifth mailbox argument and has `coord start` re-render launchers, but does not change `githooks/post-merge`, which still calls `write_launcher` with four arguments (`githooks/post-merge:44`). Rule: install and post-merge must share one launcher template signature so a regenerated launcher cannot diverge from install. Failure if followed as written: after a merge removes `start-<agent>.sh`, post-merge either fails to regenerate or writes a launcher with an empty/missing grant, and the agent cannot write `complete` while the coordinator waits forever. Smallest correction: list and update `githooks/post-merge` (and a clone identity key) the way Claude and Codex do, or keep the generated file path-independent and resolve the drop at launch time.

2. **Cursor plan — Exact File List (`src/setupWorkspace.ts` / `src/cli.ts`) — refresh launchers at `coord start`.** The plan rewrites each clone's `start-<agent>.sh` from `coord start` after `createIssueRuntime`. Rule: `docs/coord-driver.md` states the coordinator never writes agent clones; launchers are install/post-merge owned. Failure if followed as written: every `coord start` mutates files inside live clones (possibly while a harness is running), races agent processes, and reintroduces two writers for the same generated file. Smallest correction: store an absolute mailbox root in clone identity and derive only the current drop at launch from `COORD_ISSUE` (already set for automated tmux sessions in `src/tmux.ts:696`) plus the fixed agent id — Codex's approach — instead of baking issue paths into the launcher at start.

3. **Cursor plan — Exact File List — missing `test/support/workspaceFixture.ts`.** The plan never changes the product fixture that creates `coordRoot` via a separate `mkdtempSync(join(tmpdir(), "coord-runtime-"))` (`test/support/workspaceFixture.ts:91`). Rule: a derived sibling `dirname(coordRoot)/completes` must be unique per test and cleaned by the fixture. Failure if followed as written: parallel vitest workers share `/tmp/completes`, read each other's SHAs, and flake. Smallest correction: nest `coord-runtime` under `workspaceRoot` (Claude/Codex) or pass an explicit unique `completesRoot` into every fixture.

4. **Cursor plan — Exact File List — no change to `src/action.ts` completion I/O.** The plan moves `complete` under an agent-writable mailbox but leaves `readCompletion` / `clearCompletion` as plain `existsSync` + `readFileSync` / `unlinkSync` with no mailbox containment or no-follow open. Rule: any path an agent can write must be re-validated by the coordinator before trust (same symlink refusal used for `coordRoot`). Failure if followed as written: between poll ticks an agent replaces `complete` with a symlink into `coord-runtime` or a peer drop; the coordinator follows it and treats foreign content as that agent's SHA intent. Smallest correction: confine reads/clears to `completesRoot` with `assertNoSymlink` and no-follow regular-file open (Codex).

5. **Claude plan — Segment order / Alternatives Rejected (issue-first dismissed as a false dichotomy).** Claude requires `completes/<agent>/issue-<n>/complete` because install-time launchers cannot know the issue, and claims the only issue-first options are granting all of `completes/` or rewriting launchers at `coord start`. Rule: automated sessions already export `COORD_ISSUE` (`src/tmux.ts:696`), so a path-independent launcher can grant exactly `completesRoot/issue-N/<agent>` at exec time without baking the issue into the file and without granting peer drops. Failure if followed as written: the implementation departs from the owner's preferred `completes/issue-N/<agent>` layout for a reason that is already false in this tree, and reviewers cannot choose the owner's order without rejecting Claude's stated invariant. Smallest correction: keep per-issue/per-agent segments in the owner's order; persist `completesRoot` in clone identity; resolve the current drop at launch when `COORD_ISSUE` is set (manual mode: no grant).

6. **Codex plan — Exact File List (`scripts/lib/launcher.sh`) — unverified Codex/Cursor flags stated as facts.** The plan asserts Codex uses `workspace-write` plus `add-dir`, and Cursor/Antigravity enable sandboxes plus `add-dir`. Rule: vendor launch flags must match an installed CLI (Claude correctly requires `codex --help` verification and a documented fallback). Failure if followed as written: a guessed `add-dir` (or sandbox flag) that the installed Codex/Cursor binary does not accept makes every generated launcher fail at `exec`, for every issue. Smallest correction: verify each flag during implementation; if absent, keep the current unattended behavior with a comment naming the missing flag and removal condition, and still assert the mailbox path appears wherever the vendor *does* accept a grant.

7. **Codex plan — Exact File List (`src/state.ts`) — `completesRoot` in workspace config only, not in `start.json`.** The plan makes `completesRoot` required on the workspace config and has resume/rebuild use that configured root; it does not require the absolute path on `startStateSchema`. Rule: durable issue paths must reconstruct from `start.json` (immutable for the issue session), not from install config that `coord install` may rewrite. Failure if followed as written: an operator reinstalls or edits config mid-issue with a new mailbox root; the coordinator polls the new tree while agents still hold a grant (or write) to the old one, so completions are missing or stale forever. Smallest correction: persist the resolved absolute `completesRoot` in `start.json` (Claude/Cursor) and reconstruct `IssueRuntimePaths` from that field on resume.

## Conclusion

None of the three plans is safe to implement unchanged. Cursor's plan matches the owner's layout sketch but breaks launcher authorship (clone writes from `coord start`, missing `post-merge`), leaves shared-temp test pollution, and omits mailbox symlink containment on completion I/O. Claude's plan is the strongest on install identity, doctor drift, wipe semantics, and fixture isolation, but its agent-first segment order rests on a false dichotomy given `COORD_ISSUE`. Codex's plan has the right launch-time grant model and the best completion I/O hardening, but states unverified vendor flags as requirements and fails to pin `completesRoot` in `start.json`.

Prefer a merged shape: owner's `completes/issue-N/<agent>/complete` order; absolute `completesRoot` in config **and** `start.json`; clone identity key for the mailbox root; path-independent launcher that grants only the current drop when `COORD_ISSUE` is set; verified-or-fallback vendor flags; coordinator no-follow reads/clears under `completesRoot`; wipe/uninstall scoped cleanup; and fixture-local mailbox roots. Reject Cursor's start-time launcher rewrite and Claude's claim that issue-first cannot be granted narrowly at install time.
