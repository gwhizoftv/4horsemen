## Exact file list to be created

- `src/projectChecks.ts`: a cohesive, read-only discovery and command-input module. It returns labeled alternatives, supporting paths, ordered argument vectors and unresolved choices. This keeps additional native detection and quoted-argument handling out of the already large CLI and workspace installer; it is used by both interactive and unattended onboarding. Test it in the existing verification/onboarding test files.
- `src/checkAmendments.ts`: a small shared policy module for validating/merging additions, deriving effective command digests, checking baseline eligibility, and idempotently persisting accepted additions through the existing workspace writer. The CLI, run loop and diagnostics must share these rules rather than independently reconstruct them. Test it through existing state, CLI and run-loop suites.

No new dependency, test framework, fixture directory, workflow phase, product hook body or package-version change is needed. The plan artifact itself is coordination evidence, not a product-file addition.

**1. Discover runnable alternatives without running project code.** Inspect project scripts, package/build metadata and a bounded scan of `test/` and `tests/` (also native shared-scheme metadata and Swift package test-target evidence). Each suggestion names its supporting file and target/preset/scheme. Test-source files are context, never executable candidates. Keep existing Node, Make, Cargo, Go, Python and Flutter support; include build-only candidates where evidence supports a build but no tests. Do not infer a working test suite solely from a language extension or a manifest. An empty or unfamiliar repository is a valid no-command result. Malformed relevant metadata is a labeled error, not an empty policy. Discovery does not invoke GitHub, package scripts, a build system, or CI YAML; existing CI may be mentioned as context only.

For CMake, read checked-in preset metadata, resolve applicable configure/build/test relationships (including ordinary local includes/inheritance with cycle/path guards), and offer the ordered sequence `cmake --preset <configure>`, `cmake --build --preset <build>`, `ctest --preset <test> --output-on-failure --no-tests=error`. Require a consistent configure preset and necessary configuration; do not borrow an unrelated build directory or untracked user preset. Hidden, disabled, unsupported conditional/macro or otherwise unresolved configurations are not automatic choices: identify what remains unresolved and use owner input or an existing script. Multiple viable preset chains remain alternatives. A resolved configure/build pair without a test target can be chosen explicitly as build-only. This follows the [CMake preset relationships](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html) and [CTest zero-test failure option](https://cmake.org/cmake/help/latest/manual/ctest.1.html#cmdoption-ctest-no-tests).

For Xcode, inspect project/workspace references and checked-in shared schemes. Test suggestions must identify a scheme with test entries or a referenced test plan. Resolve or ask for the container, scheme, test configuration and destination; never guess a simulator, signing setting or unrelated output directory. Offer an argument vector for `xcodebuild ... test`, which includes the necessary build, or a clearly labeled `build` choice when tests are absent. Unsupported scheme arrangements fall back to an owner command/script rather than fabricated defaults. Preserve spaces in project, scheme and destination arguments. See [Apple's command-line testing documentation](https://developer.apple.com/library/archive/technotes/tn2339/_index.html). Swift package commands may be suggested from package/test-target evidence without evaluating the manifest; complex dynamic package declarations require an owner choice.

Map these directly to `verify.precommit` and `checks`; newly selected normal policies use an empty `verify.prepush`. Keep existing advanced prepush/coordinator settings when the owner keeps them. An explicit change previews and normalizes the applicable local/coordinator lists together so obsolete timing cannot remain active invisibly. Build-only is a valid selection with a build label.

Preview exact argument vectors and timing, then write through `writeWorkspaceConfig` and print its absolute path, including `workspaces/<project>/config.json` when applicable. Selection does not run the commands. Continue using doctor to report missing executables; a missing tool or failing real command is never converted into a skip. Cancellation/EOF during interactive editing leaves previous settings intact.

Unattended behavior is explicit > saved > one unambiguous, fully resolved detected plan. Newly detected unattended plans default to the displayed before-PR timing; preserve saved/explicit timing. With no recognized command, persist `verify: { precommit: [], prepush: [] }` and `checks: []` and print `Automated checks skipped: none configured.` Ambiguous alternatives or unresolved parameters fail with an actionable `--declare` example and the real settings path. **5. Persist additions safely for future issues.** Store accepted additions as conditional records in the existing workspace config, not unconditionally in its active command lists. Record source issue/pin, commands, tracked entry-point paths and blob identities. ## Alternatives Rejected

- Only remove `.min(1)` or substitute an always-successful command: this neither guides native users nor adopts new tests, and a fake command misreports skipped verification.
- Require normal users to author JSON, locate an example, or re-onboard after agents add an entry point: contrary to the required onboarding and handoff flow. Retain `--declare` as the advanced explicit escape hatch.
- Guess native destinations/build directories, auto-select the first detected ecosystem, or execute discovered scripts/CI to find out what they do: deterministic evidence plus an owner choice is sufficient and avoids fabricated plans.
- Parse custom commands with whitespace splitting or implicitly pass them to a shell: breaks quoted paths or changes the meaning of user input. Use argument vectors and explicit shell invocation only when the owner requests it.
- Overwrite the issue snapshot, let agents edit runtime config, or immediately activate another branch's proposal globally: breaks review/result identity and can require an unmerged script in unrelated issues.
- Add a separate check-approval phase, framework scaffolder, CI interpreter, new sandbox or verification runner: unnecessary; existing submission, review, state, workspace and execution interfaces cover this issue.

## Risks and Mitigations

- **Scope spans onboarding and completion.** The owner explicitly requires both. Keep native discovery and additive-policy logic in the two cohesive new modules, and keep integration changes to the enumerated files. Do not change merge enforcement, confidence scoring, dependencies or product hook bodies.
- **Native metadata is richer than a small detector.** Support demonstrably resolved plans and label unresolved information. Never treat unsupported/ambiguous data as evidence of no tests; request owner input or an explicit command. CTest's strict no-test option makes an accidentally empty selected suite fail.
- **Settings drift or malformed configuration.** Strict reads and explicit/saved/detected precedence prevent silent policy replacement. Freeze local as well as final settings for newly started issues; serialize config updates and keep prior state compatible.
- **Proposal/result drift.** Bind both the signal commit and product pin into review inputs, keep amendments additive and coordinator-owned, and check effective digests at execution and publication. Exclude losing candidates and reject name conflicts/removals.
- **Crash or competing writes.** Journal/cursor authority plus stable identities and short config locks make adoption replayable. A config write failure remains visible and recoverable before publication, with original snapshot bytes preserved.
- **Future branch mismatch.** Gate activation on exact baseline evidence and retain pending records. Rewritten history that cannot prove the entry point exists needs an explicit owner choice; do not guess or silently claim checks passed.
- **Reporting overclaims.** Empty means skipped, a build is a build result, and local results do not establish review completion or remote CI success. Preserve the existing finalization authorization and cleanliness rules.

## Conclusion

Deliver source-labeled native/project check selection, intentional empty policies, durable saved timing and settings, and reviewed additive check adoption before publication. The existing command model, terminal prompts, workspace config, normal signal/review flow and fresh verification worktrees remain the core interfaces. The listed acceptance tests cover the owner's full requested path without adding a new approval phase or broad framework/CI automation.
