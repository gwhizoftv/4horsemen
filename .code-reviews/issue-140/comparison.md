The selected Codex plan is the common acceptance baseline. Locations below are relative to the named implementation's worktree.

## Comparison

**Prefer Codex as the revision base; none of these pins is ready for unconditional acceptance.** Codex retains the unproved-live-recovery gate, checks lifecycle and cursor revisions around results, preserves binding-wide cooldown state across actions, and uses an awaited bounded telemetry receiver. Its ownership handling still has the two defects below. Claude has substantial focused coverage and a bounded helper, but allows insufficiently proven clearance and leaves telemetry processes unbounded. Cursor has critical helper, installation, and scheduling defects, with no new run-loop or tee tests to expose them.

### Codex findings

1. **[P2] `src/claudeStatusLine.ts:118-120` — do not execute an obsolete captured owner command after effective-command drift.** The tee must preserve the owner's effective command, and detecting drift must affect what runs. Install over inherited user command A, then change the user setting to B: `inspectClaudeStatusLine` reports modified, but every render still launches `manifest.effective` (A) before inspection at line 139. Reinstall returns without repairing this state, and removal refuses it. The owner's new display is therefore indefinitely shadowed by the coordinator's old override. Extend the existing tee test: change only the inherited owner command, render, and require that A is not executed and that supported owner behavior is restored without rewriting B.

2. **[P2] `src/claudeStatusLine.ts:62-66,103-107` — uninstall must preserve edits to the owned statusline object, not only replacements of its command.** Ownership inspection compares the command, then substitutes the saved prior object before checking effective settings. If the owner changes `statusLine.padding` from 2 to 9 while retaining the tee command, inspection still returns installed and removal restores padding 2 (or deletes the entire object when no prior local value existed). This loses an owner edit despite the preservation guarantee. Test a non-command property edit followed by uninstall; it must remain intact or cause a safe refusal.

### Claude findings

3. **[P1] `src/runLoop.ts:1313-1319` — automatic release requires a validated version/auth/resource combination and an identity-stable read.** This production path releases solely from the parsed limits predicate; there is no live-validation gate. The real helper at `src/codexQuota.ts:115-124` issues one account read alongside limits and never re-reads identity; `complete` checks only account type. Consequently an unproved installation, or an account replacement after the limits snapshot, can remove the hold and restore workflow authority. This violates the selected plan's explicit disabled-until-proven boundary. Add a test that an otherwise clear real-adapter result from an unvalidated combination cannot release, and an account change during the helper invalidates the snapshot. Cursor's release at `src/runLoop.ts:2637-2638` also lacks this validation gate; Codex explicitly defaults `recoveryProven` to false.

4. **[P1] `src/resourceEvidence.ts:322-328` — missing restriction fields must not count as affirmative complete clearance.** Parsing converts missing/malformed `spendControlReached` to null and absent reached-type information to null; the clearance predicate then only requires a matching window with usage below 100. A previous exhausted window followed by `ordinaryUsageAllowed: true`, usage 10, and omitted spend-control fields returns true and is eligible for automatic release despite the missing restriction evidence. I reproduced that return value against this exact pin. Extend the existing limits table with missing/null/malformed restriction fields and changed window duration; each must remain owner-only rather than clear.

5. **[P1] `src/claudeStatusLine.ts:142-146` — every telemetry receiver needs bounded lifetime and proved termination before its exclusion can be reused.** The shell wrapper backgrounds the receiver without a timeout or reap, then removes its lock merely because its directory is old. A receiver that never exits survives; later renders remove the lock and start additional receivers over it. Repetition accumulates live processes, and an older receiver can later delete a newer receiver's lock. This is not the planned bounded synchronous/awaited receiver. Test a receiver that never finishes across the stale-lock interval; it must be terminated and reaped without affecting owner bytes or status.

### Cursor findings

6. **[P1] `src/codexQuota.ts:219-224,250-251` — timeout, EOF, and child exit must settle pending RPCs within the total lifetime.** The timer kills the helper but does not reject the pending `initialize` promise. Pending requests are rejected only in `finally`, which cannot run until that same await resolves. A silent or early-exiting helper therefore leaves the coordinator awaiting forever with its reservation and binding lock held. An injected silent helper was killed at the timeout, but the returned promise was still unsettled after 10,302 ms. Add a silent/EOF helper test asserting bounded result settlement, not just receipt of a kill signal. The separate parser buffer also continues growing after the output-cap flag; the cap must stop processing and settle, not merely flag overflow until all RPCs finish.

7. **[P1] `src/claudeStatusLine.ts:96-108,185-190` — repeated installation must recognize its own override and never wrap itself.** The installer writes the bare wrapper path as `statusLine.command`, but recognition looks for `coord-managed-agent-lifecycle-v1` inside that command. The path `.../.claude/coord-statusline.sh` does not contain the marker. On the second install it is therefore captured as the owner's downstream command, and the newly rendered wrapper invokes itself recursively instead of the original owner command. The saved prior setting also becomes the wrapper. Add an install-twice/render/uninstall test asserting one owner execution and restoration of the original setting.

8. **[P1] `src/codexQuota.ts:93-101` — conflicting compatibility and keyed views must fail closed.** An object-valued compatibility `rateLimits` is ignored entirely; even array-valued duplicates are skipped without comparison. With a keyed primary window at 10% but its compatibility view at 100%, this pin's `codexClearsBlockers` returns true for that prior blocker. I reproduced this result. The coordinator can release despite a contradictory exhausted view. Extend the existing parser table with conflicting duplicate views and require rejection/owner-only handling.

9. **[P1] `src/runLoop.ts:2480-2484,2516-2520` — the five-minute cooldown must be durable per binding across issues and actions, not merely per action.** Only the current action's `lastStartAt` is consulted. The binding lock excludes simultaneous execution but carries no last-start record after it is released. Issue A can finish a helper and issue B with the same binding can start one immediately; replacing the action in one issue likewise resets this throttle. Add two issue fixtures sharing a binding and verify that the second cannot start until five minutes after the first, including after coordinator restart/action replacement.

10. **[P1] `src/runLoop.ts:2679-2685,2905-2908` — a held runner must remain alive for authorized future observations, not only observations already due.** After a failed read schedules its five-minute retry, or an exhausted read schedules a future deadline, `hasDueResourceObservation` returns false and `run()` exits. No sleeper remains to execute that authorized work; a restart before the deadline immediately exits again. Test `run()` with a fake clock and a future pending deadline, asserting sleep and one due observation without initialization, delivery, or completion acceptance.

### Scope, reuse, and coverage

- **Codex:** Product changes remain within the approved source/test/README scope, with the planned three focused source modules and one new test file; no dependency, version, launcher, or hook changes. Reuses the existing lifecycle, cursor mutation, locks, report, and safety fixtures. Coverage extends the existing integration boundaries and tests revision/cancellation fences, cross-issue cooldown, restart budgets, byte forwarding, and scoped release. Leaving `src/agentHookSync.ts` unchanged is reasonable because install/CLI wiring uses the dedicated tee module. The code is often compressed into dense statements, making safety review harder, but an unrelated formatting rewrite is not necessary. Live automatic clearance is deliberately disabled, not claimed as validated.
- **Claude:** Uses the same planned source modules and one new test file, reuses existing hook helpers, and adds meaningful fake-clock loop, helper, install, doctor, and event coverage. No unrelated product/version/dependency changes are listed. However, its extra persistent binding record in `src/codexQuota.ts` departs from the plan's existing-cursor-state-plus-lock-only design. More importantly, positive clearance fixtures omit the validation/partial-evidence safeguards identified above; extensive coverage does not establish those invariants.
- **Cursor:** The named product paths remain in issue scope and it creates the same small module set rather than adding a framework or dependency. It reuses state mutation and the binding-lock helper, but duplicates statusline/settings utilities while omitting the planned CLI/doctor integration changes. Added coverage is concentrated in limits/state/paths/report tests: the supplied changed-path list contains no event, lifecycle, tee, install, or run-loop test changes. The helper tests exercise successful responses and identity mismatch, not process timeout or EOF. This narrower patch leaves essential integration behavior unverified, as the findings demonstrate.

### Verification and recommendation

Read the bound source and existing tests directly. Ran in-memory TypeScript-transpiled probes against the exact Claude/Cursor worktree sources, without modifying those worktrees or querying vendor accounts: Claude partial-evidence clearance returned true; Cursor contradictory-view clearance returned true; Cursor silent-helper timeout killed the fake child but did not settle its promise. Other findings are source-level execution traces with focused regression tests specified above. Scratch-file creation under `.codex/tmp/` was denied, so these probes used an inline loader and created no temporary files elsewhere.

Codex's implementation was previously verified with full `pnpm check` (598 fast tests and 2 end-to-end tests); that is evidence for the Codex pin only, not a claim that peer suites pass. Before publishing this comparison, `pnpm check:fast` passed again: lint, typecheck, and all 598 tests across 40 files. Select Codex for focused ownership revisions, retain its unproved-live-recovery prohibition, and rerun the required full checks before accepting the revised implementation.
