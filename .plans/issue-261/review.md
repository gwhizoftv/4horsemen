# Issue 261 plan review — muse

Bound plans: muse `8b78468a623f703332f004a9c98f50ceaee71e16`, claude `daa87d045eafce23b9ee9532f64e6ec8ce253334`, codex `f1d01874ea5d2ccda3d0d07259113c9f9537c8ad`. Governing scope: issue body ("Use the comment to guide the design plan") plus owner design comment items 1–6.

## Findings

### Muse plan `8b78468a623f703332f004a9c98f50ceaee71e16`

1. **Claim (§Reuse and Scope, §Conclusion): explicit-empty `checks` plus re-declare on reinstall is the whole design. Rule: the owner comment requires guided discovery with source labels (item 1), CMake configure→build→test and Xcode scheme handling (item 2), commit/PR timing choice (item 3), and agent-proposed check adoption without re-onboarding (item 5). Failure: following this plan as written, `coord onboard` still offers no discovered command, no timing question, and no `checkProposal` path, so a Mac app whose tests are created by an agent during an issue still cannot gain a finalization check until a human re-onboards — the issue stays open. Correction: treat empty checks as one state inside the discovery/timing/adoption design, not as the design itself.
2. **Claim (§Exact File List, `src/cli.ts`): onboarding succeeds via a new `--allow-no-checks` opt-in. Rule: comment item 4 plus the noninteractive rule — normal onboarding requires no `--declare` or flag authoring, and a first-time noninteractive project with no recognized command gets clearly announced empty settings. Failure: plain `coord onboard <new-repo>` (the exact command that failed for `finalerev`) still throws `Cannot infer finalization checks`, because the flag is never passed in that flow. Correction: default to announced empty settings when nothing is recognized; keep any flag only as an explicit override.
3. **Claim (§Exact File List, `src/setupWorkspace.ts`): marker-only branches for `*.xcodeproj`/`*.xcworkspace` label the toolchain. Rule: detection must work through the code as written — `proposeToolchainPolicy` resolves markers with `existsSync(join(productRoot, relative))`, a literal path join with no glob expansion (`src/setupWorkspace.ts:208`). Failure: `existsSync("….xcodeproj")` is never true (`.xcodeproj` is a directory bundle matched by glob), so the branch is dead code and the Mac app is still "unspecified"; the §Tests case asserting the label fails. The plan also calls scheme commands unknowable while `Package.swift` deterministically supports `swift build`/`swift test`. Correction: enumerate the product root for `.xcodeproj`/`.xcworkspace` directories, and either propose SwiftPM commands or state why they are withheld.

### Claude plan `daa87d045eafce23b9ee9532f64e6ec8ce253334`

4. **Claim (§Design item 4 / `src/runLoop.ts`): a persistence failure when writing adopted checks is logged as `[ACTION]` and does not block publication. Rule: comment item 5 — once accepted, coord records the amendment, runs the new checks before publication, and persists the commands for future issues; publication is the point after which the issue's runner may stop. Failure: the PR publishes, the coordinator exits, and the cursors' unadopted amendment is the only record; no later process is obligated to retry, so future issues silently keep the empty policy the adoption was meant to end. Correction: finish the config write (or surface a retryable, owner-visible incomplete state) before marking publication ready, as the codex plan states.
5. **Claim (§`src/checkSetup.ts`, `resolveCheckSettings`): noninteractive resolution falls back to "an unambiguous detected plan". Rule: every onboarding path must show commands and timing before saving (comment item 3), so the timing for a noninteractive detected plan must be decided by the plan, not invented during implementation. Failure: the implementer must guess whether a detected CMake chain lands in `verify.precommit`, `checks`, or both; two faithful implementations diverge, and §Tests case 10 cannot assert the saved lists. Correction: name the default (e.g. before-PR, i.e. `checks` only) for unattended detection, as the codex plan does.

### Codex plan `f1d01874ea5d2ccda3d0d07259113c9f9537c8ad`

6. **Claim (§Reuse: "An empty configuration is allowed in candidate settings too"): coordinator-mode candidate checks may be `[]`. Rule: candidate checks are the pre-gate that keeps coordinator mode meaningful — `refineVerificationPolicy` already requires `coordinated` + `candidate` together (`src/state.ts:353`), and the comment's empty-list allowance names declarations, workspace configuration, and saved issue state, not the advanced candidate policy. Failure: a workspace in coordinator mode with `candidate.checks: []` passes every implementation/revision pin through `runVerification`'s empty-command pass without executing anything, while presenting as coordinator-verified. Correction: keep `candidate.checks` at `.min(1)` (the claude plan's explicit choice) even as top-level `checks` is relaxed.
7. **Claim (§File map: reporting via `src/issueReport.ts` + `src/runLoop.ts`, with no `src/githubIssue.ts` change): adoption and results are reported at publication. Rule: the PR body is built in exactly one place — `formatFinalizationPullRequest` (`src/githubIssue.ts:62`), called from `publishAcceptedFinalization` (`src/runLoop.ts:2955`) — so a surface the file map never touches cannot gain the adoption lines. Failure: following the map literally, the published PR (the owner's durable record) shows no check summary, contradicting the plan's own reporting claim; only transient logs/status carry it. Correction: add `src/githubIssue.ts` (optional `checkSummary` on the formatter) to the file map, as the claude plan does.
8. **Claim (§File map / §Reuse): move `checkCommandSchema`/`CheckCommand` from `src/state.ts` to `src/protocol.ts` and re-export. Rule: an Exact File List must name every file a cross-module move forces to change. Failure: `src/verificationLog.ts` consumes `CheckCommand` today and appears nowhere in the map, so the stated move either leaves a stale import (typecheck failure) or silently expands scope beyond the approved map — exactly what the amendment-request process exists to catch. Correction: list `src/verificationLog.ts` (and re-audit importers after the move) or keep the schema in `state.ts` and give `checkProposalSchema` a local strict `{ name, argv }` shape, as the claude plan does.

Scope/reuse/test audit: the muse plan reuses existing interfaces well but under-scopes the issue (findings 1–2) and justifies zero new files for a design that needs a discovery surface. The claude and codex plans both stay within the issue, reuse the command model, workspace writer, evidence/review flow, and fresh-worktree runner, justify their new module(s) (`src/checkSetup.ts`; `src/projectChecks.ts` + `src/checkAmendments.ts`), and propose focused tests that fail before and pass after — claude's 21 numbered cases and codex's 7 acceptance groups both cover the comment's acceptance list, including zero-tests-vs-no-checks, quoted arguments, timing, restart recovery, and safe future activation. Neither invents dependencies, a ballot phase, or test-framework scaffolding.

## Conclusion

Do not implement the muse plan `8b78468a623f703332f004a9c98f50ceaee71e16` as written: it solves only the empty-checks slice and leaves the failed `coord onboard` flow and agent-added-check adoption unimplemented. The codex plan `f1d01874ea5d2ccda3d0d07259113c9f9537c8ad` is the most complete basis — it alone specifies the noninteractive timing default, baseline-exact activation, and publication-gated persistence — provided findings 6–8 are corrected (keep candidate checks non-empty, add `src/githubIssue.ts`, complete the schema-move file map). The claude plan `daa87d045eafce23b9ee9532f64e6ec8ce253334` is an acceptable alternative once findings 4–5 are corrected (block or durably surface adoption-persistence failure; name the unattended timing default). Either surviving plan keeps the change inside the listed modules with no new approval phase, and its tests should be kept as maintained project tests in the named existing suites, not as throwaway probes.
