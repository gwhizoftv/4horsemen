The four implementation pins implement the same contract. Cursor `b34cde7dda51655a1fc10ea245218f584bb3002a`, Codex `57cc186f930f0841b22f89a754b3d2bfbf946190`, Antigravity `ff20570dee7d7fa6800c16b423360833ae78f74a`, and Claude `cadc99bd74a32882534cdc43f7fd668e415e49f4` each bind a later `R6.revise` to the preceding accepted revision plus that previous round's published consensus ballots, keep the prior-revision pin when the batch is missing, leave round 1 on the selected implementation only, export `consensus-ballot` as a document, and keep `basedOn` and product ancestry on the single product parent while `inputSetHash` still covers every bound input.

No implementation-code finding meets the required bar: a path and line, a rule, and a concrete failure that follows from the code as written. The differences below are naming, placement, and test shape. They do not change the bound inputs, the scaffold, the evidence decision, or the packet.

Binding. Each pin adds one helper that cites `batch.commitSha` and `batch.paths[index]` with kind `consensus-ballot`, and skips a missing path. Cursor defines it at `src/runLoop.ts:306` and, at line 640, returns the prior-revision list alone when `publishedBallotBatch` is null. Codex defines a null-safe helper at `src/runLoop.ts:341` and spreads it at line 637, so a missing batch adds nothing and the prior pin remains. Antigravity does the same at `src/runLoop.ts:588` and line 645, and also skips an empty-string path; a published batch cannot contain one, because batch paths are non-empty. Claude defines the helper at `src/runLoop.ts:589` and appends it only when the batch is non-null (`src/runLoop.ts:640`). Round 1 in every pin is still the selected implementation (`src/runLoop.ts` immediately after each later-round return). Follow-up in every pin still returns the revision pin and then the same helper (`src/runLoop.ts:658` cursor, `:656` codex, `:663` antigravity, `:659` claude).

Ancestry. Cursor names the filter `revisionProductParentInputs` (`src/evidence.ts:44`) and uses it for `expectedPins` and for the revise scaffold `basedOn`. Codex, Antigravity, and Claude name the same allow-list `revisionProductInputs` (`src/evidence.ts:45` in each) and use it in `src/orderScaffold.ts` for `basedOn`. The filter is `implementation` or `prior-revision` in all four. A later revision whose `basedOn` also names a ballot SHA fails equality against that product-parent list. `computeInputSetHash` is still called on the full input list, so the ballot commits stay in the hash and stay out of ancestry.

Export and docs. All four add `"consensus-ballot"` to `MATERIALIZED_MARKDOWN_KINDS` and leave `MATERIALIZED_PIN_KINDS` and `PINNED_INPUT_KINDS` unchanged, so a ballot is a file in the packet and not a product worktree. The Profiles sentence in `docs/coord-driver.md` now says later rounds bind the preceding revision as the single product parent and also bind the previous round's published consensus ballot batch. Wording and line wrap differ; the claim is the same.
