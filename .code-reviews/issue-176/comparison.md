No bound implementation is ready unchanged. Codex is the preferred revision base because it preserves the never-sent budget check, revalidates lifecycle evidence, and distinguishes its own draft from later input; its terminal-layout defects below still prevent approval.

### Findings

1. `src/tmux.ts:983` in Claude — **P1: preserve draft proof after the prelude.** Before typing the nudge the composer must remain empty; before submitting it the composer must contain only this attempt's text. Setting `began` after the vim `i` key does not establish either condition. After that key, this branch accepts any ready result even when the idle sentinel is no longer proven. An owner draft appearing before the literal paste, or an owner edit after the paste, is consequently combined with the nudge and submitted. An isolated runner against the bound source confirmed both cases return `sent` and emit `i`, the literal nudge, `C-j`, and `C-m`. Add a regression that changes the composer immediately after the prelude and another after the literal paste; neither may reach a submit key.

2. `src/tmux.ts:113` in Cursor — **P1: a composer marker alone is not empty-input evidence.** Recovery must not append to unsent owner input. The allowlist accepts every line beginning with `›`, including `› owner draft`, and readiness reports `idle-sentinel`. The required-sentinel nudge therefore types and submits over an existing draft. The same predicate permits no composer at all. Test a current sentinel followed by a nonempty composer and require zero keys and zero reservations.

3. `src/tmux.ts:960` in Cursor — **P1: revalidate the pane before each key.** A readiness capture must not authorize later keys after the pane becomes busy or its input changes. Codex gets only the initial capture; the per-key gate reads tmux metadata, whose `ownerTyping` field is copy mode, not composer contents or active-turn chrome. The fake-runner probes observed one capture followed by all four keys even after a draft change. A live Working line appearing after initial readiness is similarly never consulted. Test a ready first capture followed by Working chrome before the first key and require no key or reservation.

4. `src/runLoop.ts:1114` in Claude and `src/runLoop.ts:1117` in Cursor — **P1: keep lifecycle vetoes current during asynchronous delivery.** Pending input, background work, a replacement session, or a new unrelated turn must invalidate the old delivery decision. Both callers read lifecycle once and pass only cursor authority into `nudge`; lifecycle observations do not need to mutate that cursor authority. A new prompt or pending-input observation arriving while pane capture is awaited can therefore be followed by a send based on the previous working/idle snapshot. This remains possible even with Claude's pane recapture if the display has not yet updated. Extend the run-loop fixture to write a new lifecycle observation during capture, both before typing and after typing, and assert zero submit keys, with a retained reservation only for the latter case. Codex covers these cases with its delivery-state callback and tests.

5. `src/runLoop.ts:1094` in Cursor — **P2: first-send recovery must require zero prior charged sends.** `delivery: ordered` and `injectedAt: null` are not durable proof that this action has never been sent: an established session replacement resets those lifecycle fields while the action's cursor send count remains charged. With an earlier send, a replacement session reporting working, and a tail sentinel, this predicate can authorize a second send without an idle transition after the repeat delay. The global four-send cap does not make that a first send. Test an injected action followed by a replacement-session working observation, retaining `actionSafety.sends === 1`; the sentinel must not increase the send count. Claude and Codex explicitly require zero sends.

6. `src/tmux.ts:121` in Codex — **P1: accept the observed idle footer layout.** The recovery must work on the live layout it was designed for. Claude's bound `test/tmux.test.ts:745` fixture contains `Context 71% left · weekly 96% left · 258K window · 84.6K used · Vim: Insert` and a shortcuts line with `⚠ 1 warning · f2 to view`. Codex's end-anchored short alternatives reject both. Running that exact fixture through all three bound readers produced `idle-sentinel` for Claude and Cursor but `vendor-prompt` for Codex; required-sentinel delivery therefore stays blocked despite an empty idle composer. Use the full observed fixture for readiness and successful delivery, while retaining rejection of actual extra dialog or transcript lines.

7. `src/tmux.ts:980` in Codex — **P1: determine INSERT mode independently of footer order.** A default vim `i` must not be typed into an already-INSERT composer. This expression requires the context/Vim line to end the entire capture. The otherwise accepted layout `Context 71% left · Vim: Insert` followed by `? for shortcuts` bypasses the skip. A runner modeling actual INSERT behavior confirmed the only emitted key is `i`; the next draft check returns `no-idle-sentinel` at `mid-send`. The run loop retains the reservation and holds delivery before sending the nudge. Parameterize the INSERT-mode regression over both footer orders and require successful delivery with no literal `i`.

8. `src/tmux.ts:128` in Codex — **P2: distinguish displayed placeholder styling from authored text.** Empty-input proof must not treat the owner's text as a placeholder merely because its words match. ANSI has already been stripped when this literal allowlist runs, so an undimmed owner draft exactly equal to `Ask Codex to do anything` passes as empty. Recovery can append its nudge to that draft; the later own-draft check then stops submission and leaves a partial-send hold. The bound-source probe confirms this input reports `idle-sentinel`, whereas Claude's ANSI-aware reader reports `vendor-prompt`. Test dimmed placeholder and undimmed authored text separately; only the former should authorize typing.

### Scope, reuse, and coverage

All three pins change the same five approved product paths: `src/tmux.ts`, `src/runLoop.ts`, `test/tmux.test.ts`, `test/runLoop.test.ts`, and `docs/readiness-policy.md`. None adds product files or dependencies, rewrites lifecycle state to idle, or changes launcher/hook routing outside the approved map. They reuse the existing nudge path, reservation/hold handling, lifecycle helpers, and test fixtures. Coordination artifacts in the supplied changed-path lists are evidence, not additional product scope.

Claude adds an ANSI-aware composer reader and a realistic live fixture, with focused initial-race coverage; its after-first-key shortcut leaves the main remaining safety gap. Cursor's smaller implementation tests baseline recovery and duplicate suppression after a normal send, but omits draft, changing-pane, lifecycle-race, and reset-with-prior-send cases. Codex's extra code and tests cover those delivery boundaries, wrapped owned text, pending/background work, restart persistence, and correlated acceptance after the first submit; its synthetic short footer and fixed ordering are inadequate substitutes for the observed layout.

The selected plan intentionally leaves root callback routing and shared-daemon isolation unresolved. The four-file amendment was rejected, so none of these pins implements that part of owner-included issue 174. This is a remaining issue limitation, not an unapproved-path finding against an implementation.

### Recommendation

Revise Codex's pane parsing and INSERT detection using the observed rich fixture and ANSI-aware placeholder distinction, retaining its send-boundary lifecycle and owned-draft safeguards. Require regressions for both footer orders and authored placeholder-like input before approval. The current passing suites do not cover those failures, so no pin should be approved as-is.
