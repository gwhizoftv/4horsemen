## Exact File List to be changed or deleted

- `src/verificationRunner.ts` — resolve the product execution environment in the materialized candidate worktree and pass it to every verification command, probe and diagnostic retry. Add a diagnostic comparison run for a failed final check. Share the existing command execution, worktree cleanup, log writer, concurrency slots and authority checkpoints. Return the failed command's position in the effective command list, its first attempt's bounded excerpt, comparable diagnostic evidence and log path.
- `src/hookPolicy.ts` — use the same product environment selection for declared hook checks and their executable lookup. Preserve lazy selection when a phase has no commands. Keep the injectable runner for existing callers.

- `src/runLoop.ts` — format the final failure, request the baseline comparison, route the result, and perform the owner retry. Persist the comparison and pause in one revision-checked cursor mutation before the decision machine can accept or reissue the submission. On resume, verify the recorded submission and final pin with the effective final suite and publish through the existing acceptance path.
- `src/state.ts` — extend the cursor schema with an optional pending final-verification retry record. Bind it to the issue session, R7 action, agent, submission SHA, consensus SHA, final SHA, frozen baseline and effective policy digest. Store command identity, bounded diagnostics and both log paths. Older cursor files with the field absent continue to load.
- `src/issueReport.ts` — show the persisted evidence, both pins and log paths, what the owner must repair, and the existing scoped-to-issue resume command. Make the same information available in the live run-loop message and after a coordinator restart.
- `test/verificationRunner.test.ts` — extend the existing worktree and receipt fixtures to exercise actual child runtime selection and receipt compatibility.
- `test/runLoop.test.ts` — extend the final-check fixtures to cover excerpts, baseline comparison, owner pause, retry and publication.

## Reuse and Scope

**Toolchain.** Resolve against the checkout being verified. Honor the product's existing `.nvmrc` convention, including a product pin different from coordination's Node. Use a matching installed Node (including the running executable when it matches) or the installed nvm selector for the product pin. Pass the pin as data, perform installed-version resolution only, and report an unavailable requested version explicitly. For a Node project without an explicit pin, propagate the selected coordinator Node directory as the fallback for its checks. Preserve the inherited tool search path for non-Node projects. Copy the inherited environment and put the selected bin directory first on PATH so pnpm, its shebang and nested scripts resolve the same tools. Preserve the rest of PATH for project tools and the package manager's existing project version selection. Keep this change at the product check boundary. The wrapper and GitHub/vendor callbacks already have distinct runtime contracts.

Use `ProcessRunner`, `ProcessOptions.env`, `runArgv`, the hook's `inheritRunner`, and the existing injectable verification environment. Use the actual selected Node version and effective environment for `receiptKey`, `envDigests` and cache probes. Resolve once for each candidate run and pass the same environment snapshot into its baseline comparison. The two worktrees differ in checkout and working directory only. A subsequent owner retry resolves the environment afresh so a repaired installation is visible.

**Failure evidence.** Keep `runVerification`'s existing private full log for each attempt. Scan the original attempt's complete stdout and stderr before display truncation. Normalize terminal formatting and carriage-return progress for analysis. Select specific diagnostics such as compiler messages and named missing tools ahead of progress, package-manager exit summaries and bare “build failed” messages. Preserve the identifying text after words such as “error”. Bound the displayed excerpt by both line count and characters (for example, eight lines and 2 KiB across both streams), tag the source streams and include a fallback excerpt when there is no recognizable diagnostic. Always include the command and log path outside the excerpt. Preserve diagnostic-retry notes and the first attempt's outcome.

Build comparison evidence independently of the display limit. Compare the complete normalized set of specific diagnostics for the same declared command and failure kind, retaining filenames, error codes and diagnostic payloads. Normalize only known worktree roots and presentation noise. A differing specific error, generic-only output or uncertain extraction cannot establish equivalence. A true spawn ENOENT for the declared command with a valid worktree can identify the exact missing executable for comparison. Preserve the coordinator error path for unrelated spawn, mirror, authority and I/O faults.

**Baseline and retry.** In `verifyFinalizationChecks`, retain `verifyFinalization`, baseline-to-final classification, adopted check additions and the effective policy digest. After a command fails, materialize `start.baselineSha` with `BareMirror` in its own clean directory. Use the same declared argv, expanding `{worktree}` for that checkout. Reproduce any preceding setup by executing the ordered prefix through the failed command, then stop. Bypass receipt reads, joins and writes for this diagnostic execution. Keep its evidence identified as baseline-only, separate from successful candidate/final receipts and final-check totals. If a prerequisite fails first or the baseline is unavailable, report the inconclusive comparison without classifying it as a shared failure. Preserve checkpoints, slot release and cleanup on all exits.

When the baseline passes or evidence differs, return the existing rejected observation for normal correction with the candidate evidence and comparison outcome. A tracked-input integrity failure also keeps its existing rejection. On a positive match, return a typed comparison outcome to the tick, which atomically records the pending retry and uses `setPaused` for owner intervention. Retain the completion intent and authorized pins. Show both diagnostics and full log paths before advising the owner to repair the tool or environment and use `coord resume --issue N`. Reuse `setOwnerPause`, `issueCommand` and the run loop's existing paused-state and revision checks. A running coordinator waits without polling the failed suite. A restarted coordinator reads the same evidence.

After explicit resume, use the saved submission SHA for evidence evaluation and revalidate its action, consensus, final pin and effective policy before executing. A changed marker cannot substitute another SHA. Run the complete effective candidate final suite fresh, bypassing success reuse on this retry. Another matching failure pauses again. A different failure takes the normal correction path. Retire the pending record with the corresponding acceptance, correction or action retirement. Only successful candidate verification may lead to `publishAcceptedFinalization`. Keep R4/R6 candidate failure routing and diagnostic retry policy intact.

## Alternatives Rejected

Exporting PATH from the top-level launcher would also change unrelated CLI children and could override a different product pin. Taking stderr first or taking a tail from either stream discards early errors. Matching excerpts, exit statuses or one shared generic line can misclassify a newly introduced compiler error. Running the baseline's own selected profile could compare different commands. Reissuing the finalization action for a shared failure would discard the owner's ability to retry the already approved submission.

## Risks and Mitigations

Keep full diagnostic evidence in the existing private logs and persist bounded display text only. Use conservative matching when progress or generic wrappers obscure the underlying error. A crash between comparison, pause, resume and acceptance must leave the issue either waiting or requiring successful verification again. Bind transitions to the current state revision and saved pins, and clear stale retry state when its action retires. Replay setup in independent clean worktrees so dependencies prepared for the final SHA cannot accidentally make the baseline pass. Keep the existing no-publication gate for all failed or inconclusive checks.

## Conclusion

Issue 272 is complete when nested checks use the project's selected toolchain, the final summary retains actionable diagnostics with a full log, and the owner can repair a demonstrated shared failure and verify the original approved commit before publication. A passing or differently failing baseline sends the candidate through correction.
