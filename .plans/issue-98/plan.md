# Issue 98 — move the `complete` drop to a sibling `completes/` mailbox

## Summary of the design

`agentRuntimePaths().complete` is today `coordRoot/issue-<n>/agents/<agent>/complete`
(`src/paths.ts:161`). Writing it forces every harness to hold a writable grant on
`coord-runtime`, which also contains `cursors.json`, `journal.jsonl`,
`start.json`, and every peer's `action.md`. Codex is on
`--sandbox danger-full-access` for exactly this reason
(`scripts/lib/launcher.sh:27`), and Claude/Cursor/Antigravity refuse or prompt.

This plan moves **only** the completion SHA file to a third tree that is a
sibling of both the clone and the runtime:

```text
<workspace>/
  coordination-<agent>/            agent clone (trusted)
  coord-runtime/                   coordinator only (start.json, cursors.json, journal.jsonl, agents/<agent>/action.md)
  completes/<agent>/issue-<n>/complete
```

`action.md` stays coordinator-owned under `coord-runtime`. `completePath`
already lives in the action **body** (`src/action.ts:105`), so the rendered
action needs no format change — only a different absolute value.

### Segment order: `<agent>/issue-<n>`, not `issue-<n>/<agent>`

The issue sketches `completes/issue-<n>/<agent>/complete`. Both orderings satisfy
the stated constraint ("per-issue **and** per-agent segments"); the agent-first
order is required by a mechanical fact about this repo:

- Rule: a harness grant is baked into `start-<agent>.sh`, and that launcher is
  generated at **install** time (`writeAgentLauncher`, `src/setupWorkspace.ts:439`)
  and regenerated by `githooks/post-merge:44`. Neither caller knows an issue
  number — `coord install` runs before any issue exists, and `post-merge` has only
  `AGENT_NAME`/`AGENT_LABEL`/`SHARED_BRANCH` from `githooks/lib/identity.sh:101`.
- Failure with issue-first: the only issue-independent prefix an install-time
  launcher could grant is `completes/` itself, which hands every agent write
  access to every peer's drop — the exact thing the issue's integrity section
  forbids ("Do not add ... all of `completes/` (all agents) to every harness
  allowlist"). The alternative, re-rendering launchers on every `coord start`,
  rewrites a file inside a clone while agents may be running and gives
  `post-merge` a second, issue-less template to disagree with.
- With agent-first, `completes/<agent>` is a stable per-agent prefix: granted
  once at install, never covering a peer, and correct for every future issue.

Documented deviation, stated here so the reviewer can reject it explicitly
rather than discover it in the diff.

## Alternatives Rejected

- **Keep `completes/issue-<n>/<agent>` and grant `completesRoot`.** Rejected:
  the only install-time-stable prefix is the whole mailbox, so agent A could
  overwrite agent B's completion SHA and forge a peer submission. That is the
  integrity property the third tree exists to create.
- **Keep `completes/issue-<n>/<agent>` and re-render launchers at `coord start`.**
  Rejected: it rewrites a file inside a clone per issue (possibly while a harness
  is running), and `githooks/post-merge` — which has no issue number — would then
  regenerate a launcher with a *different* grant than `coord install` wrote,
  reintroducing exactly the two-authoritative-copies drift that
  `scripts/lib/launcher.sh` was created to end.
- **Leave `complete` under `coord-runtime` and just widen every harness grant.**
  Rejected: it hands agents `cursors.json`, `journal.jsonl`, and peers'
  `action.md`. An agent that can edit `cursors.json` can select itself as
  implementation winner; the workflow's authority would no longer be
  coordinator-owned.
- **Have agents report completion through `coord next --complete <sha>` instead
  of a file.** Rejected as out of scope: it changes the completion protocol,
  `parseCompletion`, restart reverification, and every agent's AGENTS.md, when
  the issue asks only that the drop move. Worth its own issue.
- **Put the grant in `.claude/settings.local.json` via `agentHookSync`.**
  Rejected as the primary mechanism: that writer manages only `hooks` and exists
  for one vendor, while `launcher_command()` is already the single source of
  truth for vendor launch flags for all four. A Claude-only second channel would
  leave Codex and Antigravity unsolved.
- **Derive `completesRoot` only, with no config field.** Rejected: nested and
  shared runtimes (`workspaces/<project>/`) do not share a parent with the clone,
  so the derived sibling would put the mailbox in the wrong place with no way to
  correct it. Optional field, derived default.

## Risks and Mitigations

- **In-flight issues break.** A required `completesRoot` in `startStateSchema`
  makes issue 98's own live `start.json` fail to parse after the change, so the
  run that implements this cannot be resumed by the new build. *Mitigation:* the
  issue states no backward compatibility is needed; the failure is a loud parse
  error naming the field, not a silent wrong path. Land the change and start
  subsequent issues fresh (`coord wipe-issue <n>` for anything half-run). This is
  the one item the reviewer should overrule if in-place resume matters.
- **A harness flag that does not exist.** Writing a guessed Codex writable-root
  flag would produce a launcher that fails at exec time, for every issue, in a
  file nobody re-reads. *Mitigation:* the flag is verified against
  `codex --help` during implementation; absent support, `danger-full-access`
  stays with a comment naming the missing flag and the removal condition. Same
  rule for Antigravity `trustedWorkspaces` and the Cursor extra folder.
- **A stale launcher silently drops the grant.** `writeAgentLauncher` skips the
  write when the rendered text matches, and `post-merge` never overwrites an
  existing launcher. A clone carrying a pre-change launcher would keep failing to
  write `complete` while `coord doctor` reported nothing. *Mitigation:* the grant
  text is part of the rendered comparison (so `coord install` rewrites it), and
  `doctor` gains the `coord.completesDir` required-key and drift checks.
- **Symlink escape through the new root.** `completesRoot` is owner-configurable
  and, unlike `coordRoot`, has a directory inside it that an agent can write.
  *Mitigation:* the same `assertNoSymlink` / `nearestExistingRealPath` /
  `containedPath` chain `coordRoot` already uses, applied at resolution and again
  after each `mkdir`, plus the overlap check against `coordRoot` and every
  configured clone.
- **Test pollution in a shared `/tmp/completes`.** Covered by the
  `workspaceFixture` change; without it, parallel vitest files would read each
  other's completion SHAs and the suite would fail intermittently — the worst
  kind of failure for a change like this.
- **Wipe leaves a stale SHA.** A `completes/<agent>/issue-N/complete` surviving a
  wipe would be read as a completion by a re-`start` of the same issue number.
  *Mitigation:* `wipeIssue` and `uninstall --wipe-runtime` both remove the
  matching prefixes, each with a test.
- **Two orderings in the tree.** If the segment order is later changed to match
  the issue sketch, the per-agent grant must change with it. *Mitigation:* the
  order is derived in exactly one place (`agentRuntimePaths`) and asserted in
  `test/paths.test.ts`, and the rationale is recorded in `docs/coord-driver.md`.

Carried forward from issue 88, unchanged by this plan: the `test:fast` wrapper
stays in the tree with its hazards and removal condition documented in
`docs/repo-map.md`, and the ship gate comparing against `origin/main` on every
branch remains the root cause behind mid-issue version bumps. Neither is in this
file map.

## Conclusion

Move only the completion SHA, to `completesRoot/<agent>/issue-<n>/complete`, with
`completesRoot` defaulting to the sibling of the coord root and overridable in
config. `action.md` and every other runtime file stay coordinator-owned, and the
action format is untouched because `completePath` is already a body field. The
agent-first segment order is what lets the install-time launcher grant exactly
one agent's mailbox — the property that makes the harness grant safe instead of
merely necessary — and it is the one place this plan knowingly departs from the
issue's sketch. Fourteen files change, one test file is added, and every new
containment rule and every grant has a named test.
