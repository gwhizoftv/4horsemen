## Findings

### F1 — cursor: Python precommit always runs `ruff check .` (blocking)

**Plan claim:** "Python … precommit `{ name: "lint", argv: [...prefix, "ruff",
"check", "."] }`", proposed for every Python tree whether or not it uses Ruff.

**Rule:** The issue requires Python to be "fully supported without requiring
anything special". A detector default must not require a tool the project
never adopted, and must not fail onboarding over one.

**Failure:** Take a plain `requirements.txt` + pytest repository that doesn't
use Ruff.

- Bare `python` toolchain: `ruff` is `argv[0]` and isn't on PATH. Doctor
  reports `toolchain ruff` and exits 16, so `coord onboard` fails and the
  owner workspace isn't registered (`src/install.ts:833`). The owner is back
  to writing `--declare`, which is exactly what the issue reports.
- Ruff installed, or a uv, Poetry or Hatch runner (where doctor checks only
  the runner): `ruff check .` applies Ruff's default `E`/`F` rules to a
  codebase never linted with them. Every agent commit is then blocked on
  unrelated pre-existing lint.

**Smallest correction:** Propose Ruff only when the repository configures it
(`ruff.toml`, `.ruff.toml`, or `[tool.ruff` in `pyproject.toml`). Otherwise
make the test command the precommit, as codex does.

### F2 — cursor: the onboarding notice shows the proposal, not what was recorded (blocking)

**Plan claim:** `renderInferredPolicyNotice(proposal, appliedChecks)` prints
the proposal's precommit, prepush and critical paths whenever
`config.checks` equals `proposal.checks`.

**Rule:** The issue asks onboarding to "announce the effects of those"
defaults. The announcement must describe the policy that was actually
written. `buildWorkspaceConfig` merges each field separately
(`src/setupWorkspace.ts:288-328`).

**Failure:** An owner of a Python repo without Ruff (see F1) passes
`--declare` with only
`{"verify":{"precommit":[{"name":"test","argv":["pytest","-q"]}],"prepush":[]}}`.

- The declaration has no `checks`, so `config.checks` equals
  `proposal.checks` and the notice prints.
- The notice says `precommit: ruff check .` and `prepush: pytest -q`.
- The workspace config actually records `pytest -q` / none.
- The owner is told the hooks will run a command they never will.

**Smallest correction:** Render the notice from the validated `config`
(`toolchain`, `verify`, `checks`, critical paths), and label each group as
declared or inferred from the matching `declared` field. Add a test where the
declaration overrides `verify` only.

### F3 — cursor and codex: `flutter analyze` with its default fatal-infos (blocking for Flutter)

**Plan claim:**

- cursor: precommit `["flutter", "analyze"]`.
- codex: precommit `analyze: ["flutter", "analyze"]`, with finalization
  running `analyze` and then `test`.

**Rule:** A default commit gate must fail on real defects, not on advisory
diagnostics that predate the agent's change. Otherwise every agent commit
depends on unrelated cleanup, which goes against the implementation-discipline
rule to keep work within the issue.

**Failure:**

- `flutter analyze` treats info-level diagnostics as fatal by default
  (`--fatal-infos` defaults to on).
- Apps generated by `flutter create` enable `flutter_lints`, whose rules
  (`prefer_const_constructors`, `use_key_in_widget_constructors`, …) report at
  info level.
- An existing app such as the issue's `Soundsplore_MobileApp` with any one of
  those infos blocks every agent commit, whatever the agent touched.
- Under codex's plan, the same info also blocks the finalization gate before
  the PR.

**Smallest correction:** Propose `["flutter", "analyze", "--no-fatal-infos"]`.
Warnings and errors stay fatal. Name the flag in the onboarding announcement
so the owner can declare the stricter form.

### F4 — cursor and codex: Python unconditionally outranks a Makefile with a `test` target

**Plan claim:**

- cursor: Flutter and Python come before Make, so Make "no longer wins when a
  Flutter or Python marker matched".
- codex: "Python and Flutter precede the Make fallback", and Python wins over
  auxiliary Make targets.

**Rule:** Re-running `coord onboard` / `coord install` is the documented repair
path, and it regenerates `checks` and `verify` from the proposal. So a new
detector must not silently replace a policy that installs successfully today.

**Failure:** Take a Python repository with `pyproject.toml` and a
`Makefile` whose `test` target activates its environment (for example
`uv run pytest`, or a docker invocation).

- Today it onboards with `checks: make test`.
- After either plan, a plain reinstall records bare `pytest -q` (plus `ruff`
  under cursor).
- That fails, or tests the wrong environment, in the fresh finalization
  worktree (`src/mirror.ts:181`).
- The owner learns this only from a later hook or final-check failure.

**Smallest correction:** Keep a Makefile that yields a `test` target ahead of
Python and Flutter. Consult Python and Flutter only where Make produced no
finalization checks. Add a test that pins `pyproject.toml` +
`Makefile(test:)` to `make`.

### F5 — claude: plain Python uses `python3 -m pytest`, which hides a missing pytest from doctor

**Plan claim:** For the plain runner, "anything else means
`["python3","-m",…]`", and the test is `python3 -m pytest -q`.

**Rule:** Doctor's `toolchain` check is meant to catch a missing tool at
install time, not at an agent's first commit (`docs/setup-workspace.md`:
"`coord doctor` fails when a declared `argv[0]` is not on PATH").

**Failure:** Take a `requirements.txt` repository whose virtual environment
isn't active when `coord onboard` runs.

- `python3` resolves, so doctor reports nothing and onboarding succeeds.
- Every agent's precommit then fails with `No module named pytest`.
- With the venv active, bare `pytest` resolves just as well. So `python3 -m`
  buys nothing and only removes the install-time signal.

**Smallest correction:** Use bare `pytest -q` (and bare `ruff check .` when
Ruff is configured) for the plain runner, as codex does. Keep `uv run` and
`poetry run` for lockfile-managed projects.

### F6 — claude: Node with no `check`/`test` script now falls through to Python

**Plan claim:** "It returns the first matching proposal that carries
finalization `checks`", with the order Cargo, Go, Node, Make, Dart/Flutter,
Python.

**Rule:** A marker match with no usable checks currently refuses with the
`--declare` message. A fall-through may change that only when the later
ecosystem plausibly owns the tree.

**Failure:** Take a Node repository with only a `lint` script and a
`pyproject.toml` used solely to configure an auxiliary Python tool.

- Today it is refused with an actionable message.
- Under the plan it records `pytest -q`. pytest collects no tests and exits 5,
  so every agent commit is blocked.
- The onboarding note makes this visible but no longer prevents it.

**Smallest correction:** Restrict the fall-through to Make, which is the
generic, language-agnostic detector. Leave a Node match without checks
refusing, as cursor and codex do. This keeps the issue's cases working:
Python or Flutter with a Makefile that has no `test` target.

### F7 — claude: names the wrong `describe` block for the new tests (minor)

**Plan claim:** New cases go "in the existing `describe("declared
verification")` block next to 'proposes non-Node argument vectors for
non-Node trees'".

**Rule:** The Tests section must name where the cases join existing coverage.

**Failure:** That test is in `describe("installer proposals")`
(`test/verify-config.test.ts:155`), not in `declared verification` (line 40).
An implementation following the plan literally splits proposal tests across
two blocks.

**Smallest correction:** Use `installer proposals`.

### F8 — codex: moves `js-yaml` to runtime dependencies to detect one SDK marker (scope)

**Plan claim:** Move `js-yaml` from devDependencies to dependencies,
regenerate `pnpm-lock.yaml`, and parse `pubspec.yaml` with `load`.

**Rule:** Justify every dependency and keep the change minimal. Detection in
this module already uses line regexes (`makeTargets`).

**Failure (scope, not correctness):**

- The plan widens the change to `package.json` and `pnpm-lock.yaml`.
- The `package.json` edit is classified as a workflow-critical product change.
- All of this is to recognise `sdk: flutter` under `dependencies`.
- The YAML parse does buy correctness on inline (`flutter: {sdk: flutter}`)
  and quoted (`sdk: "flutter"`) forms. That benefit is real but small.
- Bootstrap already installs devDependencies (`scripts/bootstrap.sh:99`), so
  the runtime import works either way. The move is hygiene that the issue
  doesn't need.

This isn't blocking. If the team prefers the parser, the plan's own risk
mitigation (moving the dependency plus updating the lockfile together) is
correct.

  claude's plan does the same.

## Conclusion

No plan is ready unchanged.

- **codex (`6f1f7877`)** is the strongest base:
  - It uses bare `pytest` (doctor-visible) with no speculative linter.
  - Its summary comes from the effective config with provenance.
  - Its detection order keeps a Node match without checks refusing.
  - It needs F3 (`--no-fatal-infos`) and F4 (Make with a `test` target stays
    ahead of Python and Flutter). F8 is optional.
- **cursor (`1ae7ee36`)** has two blocking defects:
  - F1: unconditional Ruff fails onboarding for non-Ruff Python repositories,
    which is the issue's own complaint.
  - F2: the notice can contradict the recorded policy.
  - It also shares F3 and F4.
- **claude (`bfdbea3d`)** needs fixes for:
  - F5: use bare `pytest` / `ruff` for the plain runner.
  - F6: limit the fall-through to Make.
  - F7: correct the `describe` name.

The preferred synthesis is codex's plan with:

- `flutter analyze --no-fatal-infos`;
- Make with a `test` target kept ahead of Python and Flutter;
- Ruff proposed only when the repository configures it;
- uv/Poetry runner prefixes when their lockfile is present, with a
  fresh-worktree install step for Poetry and `pub get`.
