## Reuse and Scope

### Existing facilities to preserve

- `runCli`, `runIssue`, `CliIo`, `CliRunLoop`, `existingContext`, `resolveStart`, and `existingIssueRuntime` already resolve the exact workspace and issue. Bind the interactive session to those resolved paths; do not re-resolve commands from an ambient working directory or spawn nested CLI processes.
- Reuse the existing `answer`, `drop`, `pause`/`resume`, `status`, and `attach` bodies. Extract only enough named helpers within `src/cli.ts` to share them. Keep `rederiveAfterDrop`, `clearAgentLocalWork`, `invalidateUnpublishedBatches`, and the current stale-question, revision-limit, last-agent, authorized-reviser, and active-hold checks. CLI commands retain their current follow-up `runTick`; interactive callbacks mutate/read through the helpers but never create a second runner or overlapping tick.
- All shared owner mutations use `mutateCursorsState` and `appendJournal`. Slow Terminal/tmux effects stay outside cursor locks. The runner's `requireStateMutation`, `authority`, and `StateConflictError` continue to reject an effect result made stale by an external command or interactive mutation.
- Reuse `setPaused` and `releaseHold`, including the explicit nudge-budget-reset requirement; reuse `renderIssueReport`, `readAgentLifecycle`, `reportOwnerAgentClients`, and `TmuxController.openOwnerAgentClients` for presentation and attach.
- Reuse `CoordinatorRunLoop.run`, `advance`, `amendmentTransition`, `prepareAction`, `buildOrder`, `reissue`, `rewriteOrderedAction`, and `writeAction`. Rendering guidance must not independently write action files or alter delivery/nudge policy.
- Extend `test/cli.test.ts`'s `setup`, `fakeLoop`, and existing fake process/start dependencies; `test/runLoop.test.ts`'s `fixture`, fake mirror/tmux, injected clock/sleep/action IDs, and existing response/evidence fixtures; `test/state.test.ts`'s `initialize`; and `test/action.test.ts`'s `order`. Add terminal fakes locally in the CLI test file rather than another fixture package or test suite.

### Foreground interaction

1. Start the adapter only for `coord <issue>`, `coord run`, and `coord resume --run`, and only when stdin is a TTY with raw-mode support and stdout supports terminal output. A non-TTY, redirected-output, or unsupported terminal remains on the existing noninteractive path: no stdin reads/listeners, raw-mode changes, ANSI prompts, or new wait for input. `coord start` and one-shot commands remain noninteractive.
2. Support `s` for a fresh status snapshot; `p`/Space for an atomic toggle of **manual** pause; `a` for the existing owner attach behavior; `d` for a numbered active-agent menu; `q` for stopping only this foreground runner; and `?`/`h` for help. Pause toggling must read `manualPaused` under the lock, not invert effective `paused` and accidentally release a safety hold.
3. Provide `r` as a numbered active-hold recovery menu so this issue's hold-release use case also needs no UUID copying. Bind the choice to the displayed hold ID, use `releaseHold`, and require explicit confirmation when resetting a nudge-loop budget. Never clear all holds or infer resource recovery from a keypress.
4. Observe the initial cursor snapshot and completed runner ticks (including paused ticks). On a new `ownerQuestion.id`, show numbered choices generated from that question's actual `allowedAnswers`, not a hard-coded three-choice list. Submit the displayed ID and selected answer to the shared handler; under the mutation lock revalidate identity, answer, and holds. An externally answered/replaced question closes or refreshes the prompt instead of applying input to its replacement. Escape cancels a menu, and status can reopen a still-pending question.
5. `/` enters a line buffer; `/steer <text>` queues guidance. In line/menu modes letters such as `q`, `p`, and `d` are text, not global hotkeys. Support editing, Enter, and Escape; reject unknown slash commands. Bound input length, ignore unsupported control/escape sequences, and do not expand pasted/multicharacter data into a series of destructive quick controls. Confirm drop and abandonment selections before applying them.
6. Route normal and verbose runner logs and control feedback through a prompt-aware writer: clear the input line, emit the log, then redraw the unchanged buffer/menu prompt. No alternate-screen/full-screen UI and no unbounded log buffering. Serialize asynchronous interactive callbacks and report errors without breaking the runner. Re-read state after a command and revalidate any selected agent/hold/question in its shared handler.
7. `q`, raw Ctrl-C, input EOF/error, and SIGINT/SIGTERM request foreground cancellation and restore the terminal. Pass an `AbortSignal` into the existing run loop; do not kill tmux sessions, close agent windows, abandon the issue, clear guidance, or call `detachCompletedIssue` on a user-stopped run. An effect already executing may finish safely; check cancellation before the next initialization/tick and wake the poll wait promptly. Preserve normal completion cleanup when the workflow finishes without a stop request. Use `finally` to remove only installed listeners, close the input adapter, cancel waits, and restore the previous raw/paused input state on success, error, or cancellation. Quit returns success; interrupt/termination retain conventional nonzero exit codes.

### Durable guidance and its boundary

1. Add one defaulted guidance object to format-4 cursors containing a FIFO pending list, a monotonically increasing workflow-boundary generation, and the active cohort snapshot. Each entry has a UUID, timestamp, and trimmed nonblank text. Use explicit limits (4,000 characters per entry, 32 pending entries), reject terminal control characters, and reject enqueue on completed/abandoned issues. Old format-4 JSON without this object parses with empty defaults; make the in-memory input type compatible with existing literal fixtures rather than forcing unrelated file changes. No runtime-format bump or migration of old issue directories.
2. The shared enqueue helper takes the cursor lock, validates capacity against current state, appends an `owner-guidance-queued` journal event with the entry ID, and persists the addition with all other cursor fields preserved. Acknowledge only after the durable cursor write. Both `/steer` and `coord steer` call it; external CLI steering remains usable without a foreground TTY. Enqueue never rewrites an action, invalidates evidence, nudges an agent, or interrupts a turn.
3. A boundary is a **workflow cohort transition**, not a polling iteration or an individual agent finishing early. In the same locked state transition that advances to a new cohort, move the pending FIFO into the active snapshot, clear only those pending entries, and increment the generation. Freeze that snapshot before preparing the first recipient; all recipients of that cohort see the same guidance even when another steer arrives between their preparations. Guidance queued after that commit waits for the following boundary.
4. Apply that helper at `advance` (including derived plan/implementation/consensus advancement), amendment entry/resume via `amendmentTransition`, and the shared owner-answer retry/revise transition. Integrate explicit whole-cohort resets performed by `rederiveAfterDrop`, including cancellation of a pending amendment; promote once for the final reset target, not each intermediate derivation. An ordinary drop without a cohort reset, pause/resume, per-agent `restart-action`, malformed completion reissue, or approved-path refresh is **not** a new boundary and must keep pending guidance pending. Owner retry is an explicit new cohort even if its step/round labels repeat. Same-step whole-cohort resets therefore cannot be detected solely by comparing step names.
5. Persist the active snapshot with its generation and target step/round. `buildOrder` reads it without consuming it and passes only the matching active snapshot to rendering. Reissue, same-step restart, refreshed orders, and coordinator restart reuse it; they must never read the live pending list. Record the promoted guidance IDs and boundary in journal evidence (deduplicated by stable transition/entry identity using existing `appendJournal` support), and include IDs in `action-prepared` details for audit. Promotion must be durable before action preparation; a crash after the first recipient cannot deprive later recipients. State conflicts during preparation cause normal reobservation, not queue loss.
6. Guidance is one-cohort advisory context, not an implicit persistent policy. A later boundary replaces the active snapshot, including with an empty one. Completing/abandoning the workflow without another action leaves pending entries visible as unapplied rather than silently discarding them. Document this lifetime and show the queued count in status/acknowledgements.
7. Render the section in both Git and response orders using a shared renderer. Explicitly state that guidance does not override bound inputs, approved paths, response scaffolds, checks, or workflow rules. Quote/prefix every user-text line so headings, fences, and front-matter-like text cannot masquerade as coordinator-generated sections. Preserve text content and Unicode; do not change the restricted front matter or create new ballot fields.

## Alternatives Rejected

- A full-screen TUI, third-party prompt dependency, or new owner-control framework: unnecessary for one input line and a few menus; reuse Node input primitives and current handlers.
- Calling `runCli` recursively or shelling out to `coord` from hotkeys: duplicates resolution, can start concurrent ticks, and complicates output/lifecycle ownership. Shared path-bound handlers retain the existing safety checks.
- Per-keystroke or per-agent injection into existing actions: changes work mid-turn, gives peers different guidance, and invalidates action-digest/delivery assumptions. Only explicit cohort boundaries consume the queue.
- Clearing pending guidance after writing the first action, or keeping it only in memory: loses other recipients or loses acknowledged input on restart. Persist the cohort snapshot before any action is written.
- Treating `p` as release-all or selecting a replacement question by its new numeric index: bypasses scoped recovery or applies the owner's choice to an unseen question. Preserve exact selected identities and validate under the lock.
- Sticky guidance on every future phase and automatic scope expansion: not requested; guidance is advisory for the next cohort and cannot authorize files or override evidence.

## Risks and Mitigations

- **Terminal left raw / input interpreted in the wrong mode:** one adapter owns input state; explicit input modes, bounded buffers, safe paste handling, confirmation for destructive menus, and idempotent `finally` cleanup cover every exit path. Non-TTY operation never initializes it.
- **Races with owner commands and slow effects:** shared locked mutations preserve unrelated fields; selections bind stable IDs; existing revision checks force reobservation. Interactive handlers do not invoke a parallel `runTick`.
- **Missing a transition or leaking guidance into a reissue:** wire the named normal, derived, amendment, answer, and drop-reset boundaries explicitly and test them; a durable generation distinguishes a same-step new cohort from a per-agent retry.
- **Crash between state/journal/action writes:** retain the repository's atomic cursor and append-first journal discipline, stable journal identities, and a persisted active snapshot. Acknowledge enqueues only after persistence; action creation reads rather than drains it.
- **Advisory text mistaken for authority:** render escaped/quoted text under a dedicated section in both action modes and keep all existing bound protocol/scope fields unchanged.
- **Over-broad refactoring or fixture churn:** keep control helpers in the existing CLI, use optional/defaulted additions for old callers, create only the terminal adapter, and avoid altering hooks, lifecycle/resource policy, or dependencies.

## Conclusion

Implement a thin, TTY-gated owner interface over the existing control plane and a durable, one-cohort guidance queue over the existing workflow transitions. Acceptance requires shared safety guards, unchanged noninteractive execution, safe terminal teardown without agent shutdown, and identical next-cohort guidance for every recipient across external mutations and restarts. Keep product changes within the exact file map above.
