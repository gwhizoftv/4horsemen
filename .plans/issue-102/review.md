# Issue 102 plan review

## Findings

1. **Antigravity plan `ba6c7daa132cb6937aa1eca0032310e005611c9f`, “Agent Protocol Conventions” / file map — forbidden and ineffective protocol edit.** The plan claims the waiting convention will be implemented by changing `AGENTS.md`. The repository rule is that the clone-local managed block is hidden with `skip-worktree` and must not be edited or have its index bit cleared; durable agent instructions must come from the managed protocol template and, for per-action completion wording, the action renderer. Following the plan either leaves the convention out of the submitted commit because the `AGENTS.md` edit is hidden, or violates branch-preparation invariants to force it into Git; because the plan omits `templates/product/AGENTS.protocol.md` and `src/action.ts`, new overlays and rendered actions still lack the convention. Replace the `AGENTS.md` entry with those two owning files and their existing action/install tests.

2. **Antigravity plan `ba6c7daa132cb6937aa1eca0032310e005611c9f`, “Scope and Problem Analysis” — it does not implement the owner’s degraded-observability acceptance cases.** The plan claims to address all four reliability issues, but the required behavior is that every degraded path records a reason and rationale, correlation lag must not unconditionally prescribe restarting the CLI, and later `intent-seen`/workflow completion must clear or downgrade the sticky warning. Following the plan leaves the current “Restart the CLI so it loads hooks” message and degraded health unchanged after an agent successfully writes `complete`, reproducing B2/D5 even if its busy reasons improve. Add cause classification and completion-based recovery in the lifecycle/run-loop changes, with normal-output and journal assertions for both “hooks never seen” and “correlation lagged.”

3. **Antigravity plan `ba6c7daa132cb6937aa1eca0032310e005611c9f`, “Hook Authority vs. Screen Scraping” — its priority rule can inject into a live turn.** The plan says an idle lifecycle hook should take precedence over screen scraping except for a short list of “physical blockers.” The owner’s three-layer rule requires pane scraping to remain the authority for whether typing is safe, while hooks authorize or suppress duplicate delivery; stale `Stop`/idle evidence across turn boundaries must not override real in-flight chrome. With the proposed rule, a delayed Stop from T1 can mark hooks idle while the pane is actively processing T2, and the coordinator can type the next action into that live composer. Preserve the scrape veto, narrow the known false-positive regex/scrollback matching, and journal both hook and scrape evidence when they disagree instead of letting the hook bypass the typing gate.

4. **Claude plan `4029b017e2a8c5f17c1d588a8267b8cd1e72e8a4`, `AGENTS.md` file-map entry — it explicitly violates the clone protocol.** The plan claims the tracked copy can be updated “without touching” the `skip-worktree` bit. The rule is stronger: on a prepared automated branch the agent must not edit that hidden file at all, and the installed managed block is owned by `templates/product/AGENTS.protocol.md`. Implementing the listed edit cannot produce a normal staged diff and invites clearing the bit or overwriting the coordinator’s overlay, which branch preparation and hooks correctly reject. Remove `AGENTS.md` from the approved map and keep the instruction solely in the template plus the action renderer if every current action must carry it.

5. **Claude plan `4029b017e2a8c5f17c1d588a8267b8cd1e72e8a4`, idle-sentinel design in `src/tmux.ts` — the positive cue bypasses vendor safety blockers and is not correlated in the main send path.** The plan claims `harnessPromptReadiness` will return ready when the sentinel is the last non-empty line before running any vendor branch other than the trust check, while action-order correlation via `idleSentinelAfterAction` is only specified for lost-injection recovery. A readiness hint must not outrank live Cursor/Antigravity turn chrome or the Antigravity verification overlay, and stale scrollback must not authorize a new send. As written, an old sentinel remaining at the bottom can return ready without the current action UUID ordering check and bypass a real verification/in-flight predicate, causing discarded or misrouted keystrokes. Evaluate all hard/vendor blockers first and require sentinel-after-current-action correlation anywhere the sentinel contributes to `nudge`, not only in `actionAbsentAtReadyPrompt`.

6. **Claude plan `4029b017e2a8c5f17c1d588a8267b8cd1e72e8a4`, `src/issueReport.ts` entry — the proposed data flow is not mechanically defined under the strict schemas.** The plan alternately says the run loop stores an optional `degradedCause` “without a schema change” and that an optional third argument may be added after reading the newest journal event. Runtime state schemas are strict, and a mechanically complete plan must choose where the value is persisted/read and how each caller receives it. Storing the undeclared field fails parsing, while the alternative has no specified journal read or caller signature and can leave the report without the promised alert. The smallest correction is to omit this non-required report change, or choose one explicit route (prefer passing a derived journal value) and list the exact caller/test changes.

7. **Codex plan `f1a824657dd73f3b07c25bb367bdfbc735f28f1c`, opening precedence contract — fresh Stop is incorrectly allowed to override screen activity.** The plan claims fresh lifecycle Stop evidence may override “stale or ambiguous activity/prompt chrome.” The owner’s authority split requires scrape to veto unsafe typing and hooks to govern duplicate authorization; a Stop can lag an action boundary and cannot prove that current pane chrome is stale. Following the plan can therefore inject during a genuinely active turn whenever hook and pane timing cross, turning an observability defect into prompt corruption. Retain pane/prompt vetoes, fix the concrete Cursor false-positive, and record split-brain evidence rather than overriding it.

8. **Codex plan `f1a824657dd73f3b07c25bb367bdfbc735f28f1c`, scope and tests — required A1/B2/D5 cases are absent.** The plan claims every decision becomes explainable, but the owner’s concrete acceptance list also requires the bare Cursor `/Thinking/i` false-positive to be narrowed, degraded correlation-lag messaging to stop prescribing a restart, and successful `intent-seen`/completion to clear the sticky warning. Following the plan can add reason codes while still classifying ordinary “thinking” prose as busy and still telling the owner to restart a healthy CLI after work has already advanced. Add the anchored/ellipsis Cursor chrome correction, degraded-cause classification, completion recovery, and their normal-stdout/journal tests; do not substitute a lifecycle override for the false-positive fix.

The Cursor plan `fe93f93e173bf52e0b5e5851994d3b2cb553150a` is the only bound plan that covers the owner’s A1, B2, C1, C2, and optional D5 cases while preserving the scrape/hooks/workflow authority split and avoiding forbidden `AGENTS.md` edits.

## Conclusion

Revise the Antigravity, Claude, and Codex plans before selecting them. Prefer the Cursor plan as the implementation basis: it keeps scraping as the typing-safety veto, hooks as duplicate-send authority, and `complete` as workflow truth; adds concrete reason-coded journal/normal-output diagnostics; fixes the Cursor false positive; classifies degraded correlation lag; and clears the stale warning when workflow evidence proves delivery. If the optional waiting sentence is retained from another plan, add it through the managed template/action renderer and ensure it remains subordinate to current-action correlation and every live safety blocker.
