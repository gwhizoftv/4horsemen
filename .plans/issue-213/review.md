## Findings

1. **Cursor launcher proposal, Codex Reuse and Scope §1, and Antigravity launcher proposal: add Claude `--settings '{"editorMode":"normal"}'` [P1].** The editor change must preserve the existing status-line telemetry integration. `resolveEffective` in `src/claudeStatusLine.ts:106` treats any launcher containing `--settings` as ambiguous, and `syncClaudeStatusLine` refuses installation in that case (`:193`, `:208`). Following these plans on a fresh Claude clone therefore prevents the quota/status-line tee from being installed; an upgrade also cannot repair or refresh it through that path. None of these three file maps includes the resolver or its existing status-line tests. I reproduced the refusal with the built `syncClaudeStatusLine`, a temporary launcher containing exactly the proposed flag, and `dryRun: true`: it returned `changed: false` and `disabled: "the launcher passes --settings, which outranks clone-local settings"`. Choose a setting mechanism compatible with that resolver, or explicitly include and test a narrowly defined resolver change. This finding applies to my own submitted plan as well.

2. **Cursor `ensureCursorAgentVimOff` and Antigravity per-clone wiring: put `editor.vimMode` into `.cursor/cli.json` [P1].** Generated vendor configuration must be accepted by the actual harness and affect the intended setting. Cursor's project schema is permissions-only and strict; its global schema adds `editor`. The installed 2026.10.14-0f9edde schema contains `I = object({permissions: ...})`, a global extension with `editor`, and a strict project form of `I`. The [official Cursor configuration documentation](https://prod.cursor.com/docs/cli/reference/configuration) likewise limits project configuration to permissions. Adding `editor` to the project file is rejected rather than overriding the global Vim setting, so these plans can prevent Cursor from starting. Assertions that merely read the newly written JSON cannot detect this. Use a supported configuration layer and verify its effective behavior; do not retain the invalid overlay.

3. **Cursor Node verification/cache proposal and Antigravity default verification/cache proposal: infer cacheability from recognized script names and a fixed Node dependency list [P1].** A reused success must cover every input the command reads; names such as `check` and `test` establish no such contract. The existing rule explicitly excludes undeclared environment, Git identity/history, external services, and evidence-reading commands (`src/state.ts:95`, `docs/setup-workspace.md:578`). For example, a valid project's `test` script can read `FEATURE_FLAG`; the proposed declarations omit `env`, so it defaults to `[]`. An identical tree first passing with one flag value can later reuse that receipt with a different value without executing the now-failing test. A script that reads `.plans/` is also incorrectly cached across changes excluded by `tree-excluding-evidence`. Probing Node/package-manager versions and hashing `node_modules` does not fix either case. Require reviewed command/input declarations, or leave inferred commands uncached. The existing runner should remain unchanged.

4. **Cursor Node candidate/final/docs checks and Antigravity generated coordinator/docs checks: run package scripts in coordinator worktrees without a preceding setup command [P1].** Each coordinator command sequence must prepare the dependencies needed in its fresh worktree. `MirrorManager.materializeWorktree` only performs `git worktree add` (`src/mirror.ts:179`); `runVerification` then executes the declared commands (`src/verificationRunner.ts:167`, `:176`). The current proposal is just `pnpm run check` or `test` (`src/setupWorkspace.ts:214`), and the proposed docs sequence is just `check:docs`. Consequently a normal Node project whose scripts require local Vitest, TypeScript, or ESLint fails its newly enabled candidate gate because `node_modules` is absent, even when the developer clone has passing checks. Mentioning that an `install` command is uncached does not add it to either sequence. Specify an uncached, lockfile-appropriate dependency setup before the candidate/final/docs scripts and test execution from a fresh worktree, not only the shape of the generated configuration.

5. **Cursor documentation proposal and classifier extension: exempt the entire `docs/` prefix by default [P1].** The issue's document exemption must not turn executable product/build inputs into unchecked documentation. With the proposed default critical prefixes (`src/`, `test/`, `scripts/`, `githooks/`), a change to `docs/build.ts` or `docs/package.json` matches only the new docs prefix. When there is no docs validator, commit, push, candidate, and final selection can all return no commands for that executable change. The plan acknowledges this consequence but leaves it to a later owner override. Enumerating concrete conventional prose/image paths at setup preserves the existing conservative classifier and avoids this default coverage hole; a directory-wide schema extension is unnecessary for that solution.

6. **Antigravity launcher proposal and Vim mitigation: turn Claude Vim off while changing only Codex's prelude [P1].** Delivery keys must agree with the editor mode actually launched. Claude's current `resolveNudgeKeys` calls `vimInsertPrelude` for its default empty prelude, and the latter returns `['a']` whenever INSERT is not visible (`src/tmux.ts:306`, `:367`). A non-Vim Claude pane has no INSERT indicator, so this plan still prefixes the action/reminder text with a literal `a` after applying its launch flag. Updating Codex defaults does not alter Claude's branch. Specify the effective-mode/prelude change for Claude and test both automatic nudges and owner reminders with a plain composer.

7. **Antigravity `pipeToLog` proposal: use Perl `-pe` with `$|=1` as an unbuffered streaming timestamper [P2].** Terminal capture must record prompt and repaint bytes when received, including chunks without a newline; timestamps must describe receipt rather than a later input delimiter. Perl `-p` reads a complete input record before executing the proposed body. `$|=1` disables output buffering but does not change that input behavior. In a direct reproduction of the exact proposed filter, `prompt without newline` produced no output while stdin remained open; writing the newline released the timestamp and prompt together. A TUI can repaint or wait for input for minutes without a newline, leaving the log stale and assigning the later time to earlier bytes. Use a chunk-based reader and add a before-EOF/no-newline assertion. This also exposes why checking only a timestamp regex after process exit is insufficient.

8. **Antigravity `buildWorkspaceConfig` proposal: always inherit `proposal.verification` when `declared.verification` is absent [P2].** A proposed candidate policy must remain consistent with the owner's selected final commands, including the schema's same-name/same-argv rule. Consider a recognized package with a proposed `test` command, while `--declare` replaces final `checks` with `{name: 'test', argv: ['custom-test']}` and omits verification. The proposed candidate still names the package-manager `test`, so `refineVerificationPolicy` rejects the installation (`src/state.ts:357`). With different names, the installer can instead introduce unrelated candidate commands the declaration did not request. Suppress or recompute the proposed policy against the effective final checks; test an explicit check override. Cursor's plan already accounts for this case.

9. **Claude Exact File List versus Tests: five test files are only listed outside the authorized file map [P2].** Every path intended for modification must appear in a file-list section; citing tests in Reuse or Tests does not expand implementation scope. The plan promises changes to `test/tmux.test.ts`, `test/agentHookSync.test.ts`, `test/verify-config.test.ts`, `test/install.test.ts`, and `test/onboard.test.ts`, but none appears in its Exact File List. An implementation following the approved map cannot add its required regressions without an amendment. Add those five existing files to the map before approving it. The test reuse itself is appropriate.

10. **Claude `removeAgentLifecycleHooks` proposal and accepted uninstall risk: delete `editorMode` whenever its value is `normal` [P2].** Uninstall may remove coordinator-owned settings, but it must preserve pre-existing owner settings; equality with a default is not ownership evidence. Start with an owner-provided `.claude/settings.local.json` containing `editorMode: 'normal'`, install the managed hooks, then uninstall. The proposed removal deletes the owner's original setting even though installation preserved it. Current removal copies the existing object and removes only marked hook handlers (`src/agentHookSync.ts:216`), so the proposed deletion is a regression. Record ownership/prior state for the added key, or leave an unowned normal value intact. Extend the existing uninstall fixture with both an originally absent key and an originally present normal key.

## Conclusion

**Revise all four bound plans before implementation.** Codex needs the Claude telemetry-compatible setting path; Cursor and Antigravity additionally need valid Cursor configuration, sound cache declarations, and complete fresh-worktree setup. Antigravity also needs mode-aware Claude delivery, genuinely streaming logging, and declaration-consistent candidate policy. Claude needs its test paths in the approved map and an ownership-safe uninstall rule.

Retain the shared strengths: reuse the existing receipt engine, make verification declarations available through setup, keep documentation selection bounded and reviewable, and test delivered text and received bytes rather than only rendered configuration strings.
