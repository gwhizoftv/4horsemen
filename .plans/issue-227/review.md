## Findings

1. **[P1] Both plans — credential renewal changes the shared active account.** Cursor's Reuse and Scope chooses `gh auth login` as the storage integration. Claude's Scope limits and Risks explicitly run owner-attended `gh auth login`, then restore the previous active account. **Rule:** workspace authentication and renewal must preserve concurrent projects' account selection without changing shared active-account state. **Failure:** while workspace B logs in, GH changes its shared active account to B; a simultaneous unbound GH/Git operation in workspace A uses B. Restoring A afterward does not undo that operation, and overlapping logins can restore stale selections. Owner attendance does not eliminate the race. GH's implementation also writes a host-wide active keyring slot, so merely isolating configuration files would not fix that effect. Choose a renewal/storage path that never mutates the shared active slot, and test an interleaved second workspace during renewal. [GH authentication implementation](https://github.com/cli/cli/blob/trunk/internal/config/config.go)

2. **[P1] Both plans — private coordinator bootstrap remains outside the account binding.** Cursor's file map omits `scripts/bootstrap.sh`; Claude's Scope limits explicitly leave it unchanged because no workspace exists yet. **Rule:** the issue explicitly includes coord installation and clone creation, since authentication can be required before issue startup. **Failure:** first installation from a private coordinator fork still executes ambient `git clone` at `scripts/bootstrap.sh:70`, and later updates execute ambient fetch at line 82. Selecting an account later in onboard cannot authenticate either earlier operation; a machine active as account A still cannot install account B's private source without changing shared credentials. Add an explicit pre-workspace account input and credential path for private bootstrap, plus a first-install regression. Public/local bootstrap can retain its existing behavior.

3. **[P1] Both plans — the owner worktree and owner GH workflow have no selected-account path.** Cursor's setup section configures agent clone helpers and agent launcher environments. Claude's Design points restrict persistent helpers to agent clones and `-c` settings to coordinator subprocesses; its file map has the same omission. **Rule:** issue 227 includes the owner as well as agents, and the saved workspace account must govern owner project Git/GH work without global changes. **Failure:** after selecting B in onboard, the owner remains in the product worktree with A's ambient helper/environment. `git push` or the current owner `gh issue create` workflow still authenticates as A, even though agents use B. Child-process environments cannot change the parent owner's shell. Include owner-local Git wiring and an explicit workspace-scoped GH invocation or shell path, with matching owner documentation and a test using conflicting ambient account A.

4. **[P1] Cursor — SSH is explicitly allowed to authenticate differently.** The Risks section says that the account binding governs GH while Git SSH continues to use the user's SSH agent. **Rule:** a selected workspace account must apply consistently to both Git and GH; unsupported transports must fail clearly instead of continuing as another identity. **Failure:** with `github.account=B`, an SSH origin, and an SSH agent authorized as A, GH operates as B while fetch/push authenticates as A. Documentation does not enforce the account. Refuse that selected-account/origin combination before effects, or deliberately route it through a selected-account transport. Claude's explicit refusal addresses this particular gap.

5. **[P1] Cursor — the proposed runner overlay misses the direct wipe API fallback.** Its file map covers CLI/run-loop/mirror/synchronous Git but omits `src/wipeIssue.ts`. **Rule:** every workspace GitHub API operation must use the selected account and must not fall back to ambient credentials after a Git failure. **Failure:** `deleteRemoteBranch` directly calls `spawnSync("gh", ...)` without an explicit environment at `src/wipeIssue.ts:112`. If selected Git deletion is refused, this fallback can delete the branch as ambient A or fail despite B having access. Wrapping the run loop's `processRunner` does not reach this call. Add the source path and a regression that forces Git deletion failure and inspects the GH fallback environment. Claude explicitly identifies this call site.

6. **[P1] Cursor — replacing a local helper value does not exclude inherited helpers.** The setup section prescribes a local `credential.helper=!coord git-credential` and tests only the helper's presence. **Rule:** selected-account Git must prevent an earlier helper from satisfying the request with another account's credentials. **Failure:** Git treats helpers as an ordered list across config scopes; a global osxkeychain helper can return A's complete credential before the new local helper runs. The planned configuration then publishes under A despite selecting B. Require an empty helper reset before the account helper, scope the settings appropriately, and exercise actual `git credential fill` with a competing global helper. Claude's explicit empty-reset design handles this issue. [Git credential helper ordering](https://git-scm.com/docs/gitcredentials)

7. **[P2] Claude — direct launcher restart checks token presence, not authentication validity.** Design points / Agent terminals runs the named token lookup, exports the returned value, and exits only if that lookup fails; the Conclusion nevertheless promises restart validation. **Rule:** the issue requires agent restart to load and validate the saved selection, failing clearly when authentication is unavailable. **Failure:** GH's credential store can still return a revoked token successfully. Directly restarting `start-<agent>.sh` therefore launches the harness with the revoked token, bypassing the `/user` and repository checks performed by CLI start/resume. Add a shared validation step at the actual launcher boundary and execute a restart test where token retrieval succeeds but the API returns 401. A rendered-script string assertion cannot demonstrate this behavior.

8. **[P2] Both plans — the focused test command excludes several named suites.** Cursor's Tests gives a default `pnpm vitest run` command containing CLI/onboard/install files. Claude likewise calls for default `pnpm vitest run` of its touched files. **Rule:** the plan must name commands that actually execute the proposed tests. **Failure:** `vitest.config.ts:7-17` excludes those files; the default invocation can exercise auth unit cases while silently skipping the installation/startup regressions the plans claim to validate. I confirmed discovery with `pnpm exec vitest list test/cli.test.ts test/install.test.ts test/onboard.test.ts --filesOnly`: it listed no tests. Adding `--config vitest.system.config.ts` listed all three files. Split focused validation by the actual fast/system configurations. The eventual hook's broader checks do not make the proposed focused command accurate.

Both peer plans otherwise stay on the credential issue, reuse the existing config, installer, runner, mirror, and launcher seams, and justify their new `githubAuth` module/test pair. Neither proposes unrelated product cleanup or hook changes. Claude supplies more concrete runner threading, frozen account state, helper precedence, and cleanup coverage. Cursor's conditional `config.product.example.json` and either/or mirror-test paths should be resolved into a definite file map before implementation. Their focused test ideas are relevant, but helper-value/launcher-text assertions should be supplemented by the boundary tests named above; neither plan currently proposes a concurrent-renewal test that would expose finding 1.

The bound Codex reference proposes a wider map and one native dependency to address secure renewal, bootstrap, owner execution, and credential refresh. Those additions have explicit issue-related justifications, but the dependency's persistent-store behavior and Node/platform compatibility still require implementation evidence; this review does not claim they have passed validation.

## Conclusion

**Request revisions to both peer plans.** Claude is more concrete about core runner propagation, but its active-account restore still violates isolation and its explicit bootstrap exclusion leaves a required entry point uncovered. Cursor additionally permits Git/GH identity divergence and misses an existing direct API call and helper-precedence requirement. Resolve the concrete failures above before either peer plan is approved for implementation.
