# Issue 124 plan review

## Findings

1. **Claude plan `3ac5aad5d214caea6298696a855d71a1b03d05bb`, “Wrapper body,” claims that `-C`, `--git-dir`, `--work-tree`, and repository environment redirects should bypass the wrapper.** The automated-issue rule must refuse `git status` and `git diff` regardless of ordinary Git global repository selectors; only the explicit `COORD_GIT_DELEGATE=1` coordinator/hook path may bypass policy. As written, an agent can run `git -C . status` or `git --git-dir .git diff` and obtain exactly the redundant reads Part A is meant to stop. The smallest correction is to parse past selectors, identify the subcommand, and enforce status/diff while using the delegate guard—not repository redirection—as the trusted bypass.

2. **Claude plan `3ac5aad5d214caea6298696a855d71a1b03d05bb`, “Scope boundary” and “Alternatives Rejected,” and Antigravity plan `ae1b42852d773191ea721e56a684ff9a63262b07`, wrapper tests, claim that `git show <sha>:<path>` remains allowed without defining a transition when the current action is materialized.** The narrow pinned-show form may be a fallback only before the bound input packet exists; once `action.md` exposes materialized inputs, all agent-side show reconnaissance must be refused. Following either plan literally lets every R3/R5 agent continue issuing repeated pinned shows even though the coordinator produced the files, so the measured token waste remains. Detect the current action's materialized-input marker/manifest and block show then; permit the exact forty-hex fallback only when that marker is absent because preparation could not supply a packet.

3. **Cursor plan `b173b8e4ed9946dcccf92dbc1cf50d053dba899a`, `src/paths.ts`/`src/runLoop.ts` and “Stale read grants” risk, claims that action preparation can rewrite `read-grants.json` and the launcher can read it at process start.** A grant must exist when the sandboxed harness process starts or the already-running process must be reliably respawned with resume semantics; rewriting a file cannot change an existing process's `--add-dir` argv. The coordinator starts one persistent harness before later plan/review/implementation pins exist, so R3/R5 paths written after startup remain outside the sandbox and direct reads fail. Pre-create and grant only dedicated per-issue `inputs/` and `worktrees/` parents before launch, with exact immutable children named in each action, or specify and test a cross-vendor respawn/resume mechanism.

4. **Cursor plan `b173b8e4ed9946dcccf92dbc1cf50d053dba899a` and Claude plan `3ac5aad5d214caea6298696a855d71a1b03d05bb`, `githooks/post-merge`, claim that an existing/customized wrapper should be left untouched and only a missing wrapper regenerated.** `.coord/bin/git` is coordinator-owned generated state and must adopt template changes; unlike a human launcher customization, preserving arbitrary wrapper bytes preserves obsolete enforcement. After an upgrade that tightens show blocking or fixes delegation, every existing clone would keep the old wrapper indefinitely because an untracked file is not removed by merge. Render the canonical wrapper after merge, compare it, and replace only the file carrying the coordinator-managed marker when bytes differ; diagnose foreign bytes rather than silently accepting them.

5. **Claude plan `3ac5aad5d214caea6298696a855d71a1b03d05bb`, `src/wipeIssue.ts`, claims that `git worktree prune` should run before `rmSync(paths.issueRoot, ...)`.** Every materialized worktree must be unregistered while its target is known, or pruning must run only after the directory is gone. Pruning first sees each target as a valid existing worktree and removes nothing; the subsequent recursive delete leaves stale registrations in `mirror.git`, and a later materialization can fail with “already registered” even though the path is absent. Call `BareMirror.removeWorktree(target)` for each issue worktree before deleting the runtime, then prune as a final cleanup.

6. **Antigravity plan `ae1b42852d773191ea721e56a684ff9a63262b07`, “Disk space” risk, claims stale worktrees are removed by `coord wipe`/issue teardown, but `src/wipeIssue.ts` is absent from both file-list sections.** The exact file map must include every path needed to satisfy a lifecycle promise, including abandoned or force-wiped issues that never reach a normal step advance. If implemented within the listed scope, current `wipeIssue` recursively deletes `issueRoot` without unregistering mirror worktrees, leaving the same stale registrations and disk/mirror state the mitigation says cannot occur. Add `src/wipeIssue.ts` and its existing test to the exact file map and remove registered targets before runtime deletion.

7. **Cursor plan `b173b8e4ed9946dcccf92dbc1cf50d053dba899a`, file map, claims `package.json`, `config.product.example.json`, and `test/cli.test.ts` should change solely to advance `0.0.27` to `0.0.28`.** This repository's workflow requires ordinary issue-branch commits not to plan a pre-1.0 version bump; that check is deferred to the PR into `main`, and implementation scope must remain limited to issue behavior. Following the plan authorizes three unrelated version-only paths, expands approved change scope, and creates avoidable conflicts without making the wrapper or materialization work. Remove the version-bump paths and leave release advancement to PR finalization policy.

## Conclusion

All four plans select the correct core reuse points—`BareMirror.readBlob`, `materializeWorktree`/`removeWorktree`, `deriveBoundInputs`, contained runtime paths, the existing launcher grant array, and current action rendering. The Codex plan at `e2de333f19160e93fa0ce9d9972eaf0cfdde64bb` is the closest mechanically complete baseline because it pre-creates dedicated persistent-harness grant roots, makes show blocking conditional on current materialization, covers normal completion and wipe cleanup, reuses the launcher library rather than adding a second shell template, and avoids a version bump. Any selected implementation should still preserve exact Git-pin authority and verify read-only packet bytes, but the Cursor, Antigravity, and Claude plans should not be followed verbatim until the findings above are corrected.
