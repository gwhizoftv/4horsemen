# Plan review — issue 110

Bound plans reviewed: Claude `493590055e2a1d670328f7bfdf8e0b7a587b42ac`, Cursor `d7b899ec300f0337cb0aa51b9cb769b7f2a1c6b7`, and Codex `da91466d268ecc83745f04ef303b6d8c27bceb35`.

## Findings

1. **Claude plan, “Response path” design decision and `src/paths.ts`:** the plan deliberately places responses under `<completesRoot>/issue-<n>/<agent>/responses/`. The public contract requires the action-scoped response path to be `<issue-root>/agents/<agent>/responses/<action-id>.json`, with the accepted archive separately coordinator-owned; the shared-account limitation is handled by protocol non-disclosure and narrow write grants, not by changing the authoritative namespace. Following the plan produces a different public `responsePath`, path derivation, archive topology, and test contract from the issue, so conforming agents and coordinator code do not agree on the required runtime handoff. The smallest correction is to keep responses at the specified issue-runtime path and grant only that agent's `responses/` child plus its completion directory, never the agent root or issue root.

2. **Cursor plan, file map around `src/paths.ts` and response-mode actions:** it chooses the required issue-runtime response path but does not change `scripts/lib/launcher.sh` or its install tests. Every sandboxed harness must be able to write its own response directory without gaining write access to coordinator authority or peers; today the launcher grants only the per-agent completion mailbox. Following the plan leaves Codex and other sandboxed agents unable to create the response file under the coordinator runtime, so every ballot stalls before a valid marker can be satisfied. The smallest correction is to add a second narrow `--add-dir` for `<issue-root>/agents/<agent>/responses/` and verify that neither the issue root, peer paths, nor accepted archives are granted.

3. **Cursor plan, “Runtime format” and `src/protocol.ts`:** it explicitly keeps coordinator-published canonical ballots at `protocolVersion: 1`. Canonical ballots created from private responses must use protocol version 2 and carry `actionId` plus `responseSha256`, while the remaining agent-authored Git artifacts stay at version 1. Following the plan emits new coordinator-authored ballots with the old version discriminator, so a strict consumer cannot distinguish the new provenance-bearing format and the issue's byte/schema tests reject all three batch variants. The smallest correction is to make only plan, comparison, and consensus canonical ballot schemas version 2.

4. **Claude and Cursor plans, response staleness/acceptance claims versus `src/state.ts`:** both require action-digest agreement in tests or prose, but neither mechanically adds the current rendered action digest to the cursor/authorized-response state and checks it during acceptance. The response path, response action ID, completion action ID, cursor action ID, and current action digest must all agree before bytes are accepted. Following either plan allows a same-UUID correction reissue to change `action.md` while an older response at the unchanged action-specific path can still match the marker and cursor IDs; the coordinator has no durable expected digest with which to reject that stale handoff. The smallest correction is to persist `actionDigest` when writing/reissuing the action, hash the current action bytes at response acceptance, and require equality before parsing or archiving.

5. **Claude and Cursor plans, derived-decision provenance versus the existing `derivedInputCitationSchema` in `src/state.ts`:** both say derived decisions will cite response digests and the published evidence commit/path, but their state file maps add accepted responses/batches without replacing the Git-only citation shape. Response provenance must remain distinct from `AcceptedSubmission` and must persist `actionId`, 64-character `responseSha256`, and the coordinator evidence commit/path used by the decision. Following either plan makes strict state parsing reject those new fields, or pressures the implementation to mislabel a response digest as the existing 40-character `submissionSha`, losing the required provenance distinction. The smallest correction is a strict discriminated derived-citation union with separate Git-submission and response-publication variants, and hash inputs over the full variant.

6. **Claude plan, `package.json` entry:** it plans a `0.0.23` to `0.0.24` issue-branch bump. This repository's workflow rule requires no version bump in ordinary issue work because post-merge CI advances `0.0.N`. Following the plan adds an unrelated approved product change, reserves a version before merge, and can conflict with the actual post-merge bump or concurrent work. Remove `package.json` from the file map and leave the version unchanged.

7. **Claude plan, runtime-format risk/test remediation:** it says the exact failure should instruct `coord wipe <issue>`. Failure remediation must name a real CLI command that lets the owner recover without guessing; this repository exposes `coord wipe-issue <issue>`, not `coord wipe`. Following the plan strands an operator at an unknown command immediately after the intended fail-closed format rejection. Use `coord wipe-issue <issue>` plus restart wording in code, docs, and the asserted test message.

## Conclusion

Neither peer plan is mechanically safe to implement unchanged. Claude's plan violates the specified response namespace and repository version policy; Cursor's plan leaves sandboxed agents without a writable response path and assigns the wrong canonical ballot protocol version. Both also need a persisted action-digest binding and a response-specific derived-citation schema. Revise those items before selecting either implementation plan; the remaining batch, fast-forward, retention, privacy, and #109-routing structure is broadly aligned with the issue.
