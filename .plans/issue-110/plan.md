## Implementation and state transitions

1. **Reserve and derive the evidence branch.** Replace `{issue}` normally and `{agent}` with the reserved literal `coordinator-evidence`; reject configurations where that value is an agent ID or where the result collides with an agent branch, final branch, or base branch. The first evidence commit has the issue baseline as its parent; every later commit has the last published evidence tip as parent.
2. **Prepare a response action.** Create a UUID, derive `<issue-root>/agents/<agent>/responses/<uuid>.json`, render the strict response action and exact trusted Git inputs, write `action.md`, hash its bytes, and persist that digest with the cursor. The action says to write the response first and then the one-line `response <uuid>` completion marker; it contains no ballot Git destination or commit/push instruction.
3. **Accept intent safely.** Ignore response bytes until a marker exists. Reassert state authority; require marker ID, parsed action ID, cursor ID, response path, and current action digest to agree; then `lstat` every existing component, reject symlinks/non-regular files, reject more than 8 KiB before parsing, and apply the strict step-specific schema and current eligibility. Hash the exact accepted bytes. Invalid input clears only the marker, removes the current invalid working response, and reissues the same action with concrete corrections; it creates no accepted record, journal acceptance, archive, or Git object.
4. **Archive and persist once.** Exclusively create the coordinator-owned archive (or accept an existing byte-identical archive after a crash), persist one action-ID-unique `AcceptedResponse` with full bounded semantics/digest, append `response-accepted`, clear the response and marker, remove the action, and mark the agent waiting for peers. Replayed or duplicate markers cannot create another record. A transient later publication error never touches the accepted record/archive and never re-nudges that agent.
5. **Freeze a batch.** When every active participant has a valid response, compute one SHA-256 from length-prefixed batch kind, round, ordered active roster, trusted bound Git citations, and each ordered `(agent, actionId, responseSha256)` tuple. Build every active canonical ballot with a shared batch hash, stable field/citation ordering, and a final newline. Plan batches write `.plans/issue-<n>/ballot-<agent>.json`; comparison batches write `.code-reviews/issue-<n>/ballot-<agent>.json`; consensus batches write `.code-reviews/issue-<n>/consensus-ballot-<agent>-round-<r>.json`.
6. **Create and publish the outbox.** Resolve the expected evidence parent, create exactly one coordinator-authored commit for the whole batch, and persist its exact SHA/parent/paths before attempting the network push. Normal push is fast-forward-only. A retry pushes that persisted SHA; if origin already equals it, mark success without rebuilding. A transient failure records an error/attempt and retries on normal cadence; an unexpected origin tip remains a failed conflict requiring owner intervention. Only `ballot-batch-published` unlocks result computation.
7. **Apply unchanged voting policy.** Plan and comparison plurality counts accepted response choices and breaks ties by persisted active-roster order. Consensus checks `escalate`, then `revise`, then unanimous approval, with the existing three-round limit and owner-answer routes. Derived records cite each private response digest/action and the published evidence commit/path set. Removed selection, reviser-authorization, and declaration actions are not recreated.
8. **Handle roster changes explicitly.** Preserve accepted responses from remaining agents when still eligible. Mark a not-yet-published stale outbox invalidated and build a new roster-bound batch. If a published batch is superseded, retain it and its commit in history, create a new cumulative fast-forward commit (removing stale current-tree ballot paths where necessary), and journal the supersession. Reissue only an active ballot whose choice became ineligible; publication retries never cause agent work.
9. **Retain and report evidence.** Finalization continues to create the clean product `finalSha` and does not merge or delete evidence. Status, the issue report, and final PR body show evidence branch/latest tip but no pending semantic response. The evidence branch remains after ordinary completion; only the owner's explicit destructive `coord wipe-issue` operation removes it.

## Alternatives Rejected

- **Keep agent-authored ballot commits and merely batch-fetch them.** This preserves the twelve or more commit/push operations the issue is specifically removing and continues to trust copied coordinator-known envelope fields.
- **Use `requiredPath` for an absolute runtime file.** Repository paths and private runtime paths have different confinement, authority, rendering, and completion contracts. Overloading one field makes forbidden cross-mode combinations parse and invites Git validation on a runtime path.
- **Put responses beside `action.md` and grant the whole agent runtime directory.** That lets the agent rewrite its current authority document. A dedicated `responses/` child plus a separate completion-directory grant is the narrow writable surface.
- **Store responses as `AcceptedSubmission` with a fake SHA/path.** A private-byte digest is not a Git commit, and doing so would conflate agent intent with coordinator publication provenance in decisions, reports, and retries.
- **Publish one coordinator commit per response.** It leaks partial ballots before the denominator closes and fails the one-commit-per-gate/round acceptance criterion.
- **Derive the decision before pushing, then publish eventually.** A crash or network failure could advance workflow state without durable origin evidence. The published-batch record must be the barrier for every result, including escalate/revise outcomes.
- **Rebuild a commit on every retry.** Author/committer metadata changes the SHA; retries would produce multiple candidate commits and break durable outbox semantics. Persist and retry one exact commit.
- **Force-push or merge an unexpected evidence tip.** Either rewrites audit history or accepts an untrusted parent. Normal fast-forward push plus explicit conflict is the fail-closed behavior.
- **Merge the evidence branch into the final product branch.** That would make ballots part of the product PR and require agents/finalization to delete evidence, defeating independent retention.
- **Add compatibility or migration for format 3 ballots.** The issue is explicitly new-workflow-only; dual modes create ambiguous completion parsing and state. Format 4 rejects old runtime with wipe/restart remediation.
- **Claim same-user filesystem secrecy.** The protocol prevents pending-response disclosure through actions/status/publication, but the launcher grant is not cryptographic or OS-user isolation. Stronger secrecy requires separate process identities/access controls and is outside this issue.
- **Add `coord respond` in this change.** The helper is optional and not needed for the durable protocol. Keeping the required surface to two small atomic writes avoids coupling correctness to vendor-specific tooling; a helper can be added later against the same schemas.

## Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| An agent can see another response because all harnesses share one OS account | Never render pending peer semantics or paths, grant only the named response directory, and publish only after close. Document that this is protocol privacy, not cryptographic isolation. |
| Marker arrives before a partial response write | Read only after the marker, enforce a regular bounded file and strict JSON schema, and instruct response-first/marker-second writes. Invalid input clears the marker and reissues without accepting bytes. |
| A stale marker or response satisfies a new action | Use action-specific filenames and require marker, response body, parsed action, cursor, path, and persisted action digest to agree. |
| Archive/state crash creates a duplicate or loses accepted judgment | Use exclusive immutable archives keyed by agent/action, byte equality on recovery, unique accepted action IDs, and idempotent state/journal reconciliation before clearing working bytes. |
| Publication fails after all agents finish | Keep accepted responses and the exact pending commit, retry without regeneration, and suppress all agent re-nudges. |
| Remote evidence branch was advanced or rewritten externally | Fetch/compare the exact expected parent and use only normal pushes. Mark an unexpected tip as a publication conflict; never force. |
| Roster changes make a frozen batch stale | Bind the ordered roster into the input hash, invalidate unpublished stale batches, retain published history, and create an explicitly superseding fast-forward batch/decision. |
| Canonical JSON differs across retry/process versions | Construct explicit key order, canonical citation/agent ordering, one serializer, and a final newline; test complete byte strings. Retries use the persisted commit regardless. |
| Ballot evidence leaks into the product PR or is deleted at finalization | Build commits only in the bare mirror's coordinator worktree, never an agent clone; final PR uses only `finalSha`; final cleanup does not touch the remote evidence branch. |
| Reserved evidence branch collides with configured agents/templates | Reject `coordinator-evidence` as an agent ID and validate the fully derived branch against every agent, final, and base branch before starting/publishing. |
| Format-3 in-flight state is interpreted under new semantics | Format 4 has no migration path and reports the exact `coord wipe-issue`/restart remedy before effects. |
| Root `AGENTS.md` wording remains Git-oriented | Do not violate its managed `skip-worktree` protection. Response actions are authoritative and explicit; update both installed templates now and leave any repository-specific preamble edit to the owner. |

## Conclusion

Implement a strict response-mode action for the three ballot steps, accept only a small action-bound semantic response into durable private runtime state, and publish the closed active set as one canonical coordinator-authored fast-forward commit on a retained evidence branch. Format 4 keeps private response provenance separate from Git publication provenance, blocks every #109 result on successful origin publication, retries exact commits without repeated agent work, preserves drop/revision/tie-break policy, and keeps both pending ballots and all ballot files out of the final product PR.
