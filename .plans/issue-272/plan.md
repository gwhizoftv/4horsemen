## Alternatives Rejected

- **Modifying `scripts/lib/node-runtime.sh` or `coord` to export the coordinator's Node onto `PATH` globally:** Rejected because `coord`'s Node (`>=26`) is intentionally isolated from products that pin an older Node in `.nvmrc`; resolving the project's declared toolchain per worktree/clone in `resolveProjectToolchain` respects each project's intended version while still overriding an older inherited `PATH` entry.
- **Unconditionally copying `stderr` or tailing the last N lines of combined output:** Rejected because diagnostics written to `stdout` before trailing progress lines (e.g., `compiler error A` followed by progress output and generic `build failed` on `stderr`) would be lost; classifying and prioritizing actionable diagnostic lines across both streams preserves the root cause within a bounded budget.
- **Matching baseline vs candidate failures by exit code or raw `stderr` string equality (or running only the single failed command without prior setup steps):** Rejected because shared exit codes, generic messages (`build failed`), and random `.verification-<uuid>` paths cause false positives and false negatives, and omitting prerequisite setup/build commands before the failed step would cause spurious setup failures on a fresh baseline worktree.
- **Using `publication.status = "failed"` or rejecting `R7.finalize` for matching baseline failures:** Rejected because `publication.status = "failed"` auto-retries on every tick (and only applies after acceptance), while rejecting `R7.finalize` forces the agent to create a new commit instead of allowing the owner to fix the host/environment issue and retry the same approved commit.

## Risks and Mitigations

- **Host `nvm.sh` interaction in tests and CI:** Sourcing a user's real `$NVM_DIR/nvm.sh` when `NVM_DIR` isn't isolated could fail or add noise when tests use stub binaries on `PATH` or `COORD_NODE`. Mitigation: capture `PATH` via an explicit sentinel in bash when `$NVM_DIR/nvm.sh` exists and exits 0 with a valid matching `node`, and cleanly fall back to scanning `COORD_NODE`, `PATH` entries, `${NVM_DIR}/versions/node/v*/bin/node`, and `process.execPath` so tests work identically with or without `nvm.sh`.
- **Running prerequisite commands on baseline:** If `commands` contains setup steps before the failed check (e.g., `[install, lint, build, test:e2e]` and `test:e2e` fails), running `commands.slice(0, failedIndex + 1)` on baseline could fail on an earlier command if the baseline itself was broken earlier. Mitigation: if baseline passes or fails on a *different* earlier command, it cannot produce the same actionable failure and safely routes the candidate for correction; receipt reuse still skips already-verified cached baseline commands.
- **Blocking other work or spinning on `ownerQuestion` during `runTick`:** If `runTick` continues processing `runtime.complete` while `ownerQuestion` is active, it would re-run verification every poll interval. Mitigation: skip submission verification in `runTick` while a non-terminal `ownerQuestion` is pending, and log each `ownerQuestion.id` prompt once per runner instance.
- **Backward compatibility of `cursors.json` and existing `verifyFinalizationChecks` tests:** Existing tests construct `ownerQuestion` without `details`, assert `verifyFinalizationChecks` call counts on generic `"failed"` stubs, and expect `"rejected"` when an issue-added `checkProposal` fails. Mitigation: keep `ownerQuestion.details` optional, only run baseline comparison when the failed command is part of the baseline's declared checks (not solely an issue `checkAmendment`) and produces an actionable diagnostic, and keep `baseline` verification events on `"baseline"`/`"baseline-check"` rather than `"final-check"`.

## Conclusion

By extracting shared project toolchain resolution (`src/toolchain.ts`) and failure diagnostic/comparison logic (`src/verificationDiagnostics.ts`), integrating them into `src/verificationRunner.ts`, `src/hookPolicy.ts`, and `src/runLoop.ts`, and extending `ownerQuestion` (`"finalization-baseline-failure"`) across `src/state.ts`, `src/steps.ts`, `src/machine.ts`, `src/ownerControls.ts`, `src/issueReport.ts`, and `src/interactive.ts`, Issue 272's three requirements are solved with minimal, cohesive changes that preserve all existing invariants and test contracts.
