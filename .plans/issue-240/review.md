Plans reviewed, as bound in this action: muse `289ccb9f71ea759c72a8011fb9730e12c7b9df44`, cursor `b6795003b1eb3501e214dfb40041a278983b69c2`, codex `3926ba07d27b27512435ca07e4b0e87f6de18ff4`, claude `998ee7f73d1fbc36b3f5c5b956052ed0ef804249`. Claims below were checked against the baseline tree (`src/cli.ts`, `scripts/lib/launcher.sh`, `scripts/lib/node-runtime.sh`, `test/cli.test.ts`, `test/install.test.ts`, `test/wrapper.test.ts`, `vitest.config.ts`, `vitest.system.config.ts`, `githooks/post-merge`, `docs/coord-driver.md`).

## Findings

1. **Cursor plan, "Extend `launcher_environment` … prepends the `bin` directory of coord's selected Node to `PATH`" (shared by maintenance and generated launchers).** The rule that must hold is the one stated in the header of `scripts/lib/node-runtime.sh` and asserted by `test/wrapper.test.ts:107` ("selects %s Node for the CLI and build while product children keep their Node"): coord's Node selection must never change `PATH` for product subprocesses. `launcher_environment` runs inside the generated launcher immediately before `exec <vendor>`, so the agent process — and every product command it later runs — inherits whatever `PATH` that function leaves. If followed as written, a pane launched on a Node-16-pinned product resolves bare `node` (and Node-based product tooling) to coord's Node >= 26 instead of the product pin, so product checks run under a different runtime than the product declares. The plan's mitigation ("only vendor CLI resolution must prefer coord's Node") cannot be achieved by a `PATH` prepend alone, because `PATH` is not scoped to the vendor lookup. Smallest correction: resolve the vendor executable to an absolute path (or run it through coord's Node) without leaving coord's bin directory ahead of the product's in the launched process's `PATH`.

2. **Cursor plan, Risks: "change the template … next `coord install` / post-merge rewrite picks it up".** The rule that must hold is that a fix relying on regenerated launchers must name a regeneration path that actually rewrites existing launchers. `githooks/post-merge` states "Never overwrite an existing launcher" and only calls `write_launcher` when the launcher file is missing; only `coord install` (via `writeAgentLauncher` in `src/setupWorkspace.ts`) re-renders and replaces an existing launcher whose content differs. If followed as written, existing clones keep their previously embedded `launcher_environment` after a pull, so the launch half of the fix silently does not reach them. Smallest correction: state that a `coord install` re-run is required for existing clones, and drop the post-merge claim. The same correction applies to the claude plan's Risks item ("regenerated by `githooks/post-merge` on pull").

3. **Cursor plan, `src/cli.ts` and Tests sections (maintenance passes `COORD_NODE=process.execPath` when unset; launch rediscovers via `coord.installRoot`).** The rule that must hold is the plan's own premise that update and launch select the same vendor installation. Maintenance is guaranteed coord's Node through `process.execPath`, but the generated launcher's rediscovery depends on `git config --local --get coord.installRoot` naming a usable selector, and the plan's own Risks concede vendored clones may lack it, leaving launch on the product pin with only a warning. If followed as written, on exactly those clones the update succeeds against coord's Node installation while the pane still execs the broken product-pinned CLI from the issue. Smallest correction: give the launcher the same guaranteed input as maintenance (for example the `coord.cliEntry`-derived selector, which every non-vendored clone records), or scope the plan's same-installation claim to clones where rediscovery succeeds.

4. **Claude plan, Tests: `pnpm exec vitest run --config vitest.config.ts test/cli.test.ts -t "after nvm setup"`.** The rule that must hold is that a named focused command must actually execute the tests it cites. `vitest.config.ts` (the fast tier) explicitly excludes `test/cli.test.ts`; that file runs only under `vitest.system.config.ts`. If followed as written, the command collects no test files and the new regression case is never exercised during development, so the "fails before the fix" property is unverified. Smallest correction: use `--config vitest.system.config.ts`. The same defect appears in the muse plan's Tests section (`pnpm vitest run --config vitest.config.ts test/cli.test.ts`) and in the cursor plan's Tests section (`pnpm vitest run test/cli.test.ts` with no `--config`, which loads the same excluding default config); the codex plan's use of `vitest.system.config.ts` is correct.

5. **Claude plan, Design item 1 (`launcher_environment` returns 1 with an `ERROR:` when the executable is not found beside coord's Node or on the pre-`nvm` `PATH`).** The rule that must hold is the existing maintenance contract in `updateAgentVersions` (`src/cli.ts:181–186`): a missing or failing vendor command warns and continues, recording a null version, so one absent agent cannot block a fresh start — and, for launch, a missing CLI previously failed at `exec` with the vendor's own not-found error. The search path in the plan is `$HOME/.local/bin` (antigravity/muse only), then coord's Node bin, then the pre-`nvm` owner `PATH`; it deliberately excludes any installation reachable only through the clone's `nvm use` that is not already on the owner's `PATH` (for example a CLI installed while the pin was active in a different shell whose `PATH` coord does not inherit). If followed as written, such an installation changes from "found after `nvm use`" to a hard `launcher_environment` failure in both maintenance and the generated launcher (`set -euo pipefail`), a regression for currently working setups. Smallest correction: keep the not-found case on the existing warn-and-continue path for maintenance, and include the post-`nvm` `PATH` as the final fallback segment of the search path instead of discarding it.

6. **Codex plan, Implementation step 3 ("Pass `process.execPath` as a distinct positional shell argument … consume it explicitly before `exec "$@"`") and step 1 (maintenance "must not source nvm").** Two rules must hold. First, existing maintenance tests key off exact argv positions (`argv[3] === "coord-agent-maintenance"`, `argv[5]`, `argv.at(-2)`, `argv.at(-1)` across `test/cli.test.ts:222–381`), so the plan must state exactly where the new positional argument goes and which assertions change; it only says to update the shared-installation test. If followed as written, an implementer can place the argument where it silently breaks the ordering, timeout, and warn-and-continue assertions the plan says need "no new duplicates", or breaks them without the plan noticing. Second, by skipping the clone's `nvm use` entirely, a vendor CLI installed only under the product pin's bin directory (and nowhere on the inherited `PATH`) becomes undiscoverable during maintenance, whereas today `launcher_environment` finds it — the plan's Risks acknowledge broken installations are not repaired, but do not acknowledge losing currently discoverable ones. Smallest correction: name the exact argv slot and every affected assertion, and either keep the pinned bin directory as a trailing fallback segment in the maintenance `PATH` or explicitly accept and document the discoverability loss.

7. **Codex plan, file list (adds `docs/coord-driver.md` and `docs/setup-workspace.md` edits) — scope assessment.** The rule that must hold is that every changed file be justified by the behavior change. The two doc edits are justified: `docs/coord-driver.md:310` currently claims maintenance "shares the generated launcher's nvm setup for the clone's Node pin … so it selects the installation the launcher will use", which this plan deliberately makes false, so leaving the docs would publish a wrong contract. No correction needed; this is recorded because the same justification is missing from the muse plan, which changes the documented maintenance behavior in `src/cli.ts` while listing no doc update even though its own design keeps the `docs/coord-driver.md:310` sentence half-true (maintenance still starts from the launcher's environment) — an implementer following the muse plan must at minimum re-check that paragraph rather than assume it stays accurate.

8. **Muse plan, Tests (new test asserts maintenance ran with coord's Node) and Conclusion ("fixing the failed update and `unknown` version").** The rule that must hold is that the plan's claimed outcome must cover the failure the issue reports. The issue's sample shows three symptoms: `claude update` fails, the version is `unknown`, and the Claude pane exits with status 1. The muse plan explicitly scopes generated launchers out, so on a workspace where `claude` exists only as the broken install under the old pin, the pane still `exec`s that same broken binary after a successful coord-Node update of a different installation — the most visible symptom persists, and `agentVersions` can record the version of an installation the pane does not run (the plan's own Risks concede this divergence). If followed as written, issue 240 can be closed on the strength of the update fix while the reported pane exit remains. Smallest correction: either extend the maintenance-prepend idea to the launch resolution (as the cursor and claude plans attempt, subject to findings 1 and 5), or state plainly in the plan's Conclusion that the pane-exit symptom is not fixed and name the follow-up that owns it.

9. **Muse plan, derivation `io.env.COORD_NODE !== undefined && io.env.COORD_NODE.startsWith("/") ? dirname(io.env.COORD_NODE) : dirname(process.execPath)`.** The rule that must hold is that the Node placed first for maintenance is one coord has validated against its >= 26 floor (`scripts/lib/node-runtime.sh` validates `COORD_NODE` before use and rejects non-absolute or incompatible values). The plan's expression accepts any absolute `COORD_NODE` — including a stale absolute path to a Node 16 executable in an embedded or test context where the wrapper never validated it — and puts its bin directory first, reintroducing the exact failure under a new name. If followed as written, an unvalidated ambient `COORD_NODE` silently overrides the known-good `process.execPath`. Smallest correction: prefer `process.execPath`, and use `COORD_NODE` only as the test seam the new test needs, or validate the candidate's major version before honoring it.

10. **All four plans — new files and test focus.** The rule that must hold is that every new file be justified and tests be few and focused. All four plans create no new product, test, or config files (each new test joins `test/cli.test.ts`; the claude plan additionally updates two expectation lines in `test/install.test.ts`, which its file list names and justifies), and all reuse the existing fixtures (`setup`, `successfulStartGit`, `runArgv`, `writeAgentLauncher`, the labelled-stub nvm fixture). The cursor plan is the only one whose stated test would not run as written for a second reason beyond finding 4: it asserts both update and launch hit the coord-side binary, but its file list changes `launcher_environment` for launchers while its Risks concede existing launchers are only repaired on regeneration, so the launch assertion can pass in the fixture (freshly generated launcher) while the shipped behavior for existing clones differs — the test does not cover the stale-launcher case the plan itself identifies. Smallest correction: add one assertion or fixture using a pre-change generated launcher, or drop the launch claim for existing clones per finding 2.

## Conclusion

No plan is implementable exactly as written. The claude plan (`998ee7f73d1fbc36b3f5c5b956052ed0ef804249`) is the closest to the issue as reported: it is the only one that fixes update, version probe, and the pane launch together while keeping the product's Node on `PATH` for the agent's own commands, and it reuses `coord.cliEntry`, `node-runtime.sh --resolve`, and the existing fixtures without new files — it needs the corrections in findings 2, 4, and 5 before implementation. The cursor plan (`b6795003b1eb3501e214dfb40041a278983b69c2`) aims at the same full coverage but its `PATH`-prepend mechanism violates the product-Node isolation rule (finding 1) and its same-installation guarantee fails on vendored clones (finding 3). The codex plan (`3926ba07d27b27512435ca07e4b0e87f6de18ff4`) is the most disciplined maintenance-only plan — correct test config, justified doc updates, explicit environment isolation — but it leaves the reported pane exit unfixed by design and underspecifies its argv change (finding 6). The muse plan (`289ccb9f71ea759c72a8011fb9730e12c7b9df44`) is the smallest maintenance-only change and preserves the existing same-installation test, but it likewise leaves the pane symptom behind (finding 8), adds an unvalidated `COORD_NODE` path (finding 9), and names a test command that runs nothing (finding 4). Recommended direction: implement the claude plan's shared, absolute-path resolution with findings 2, 4, and 5 applied; if the coordinator instead chooses maintenance-only scope, the codex plan with finding 6 applied is the safer base, provided the chosen plan states explicitly that the pane-exit symptom remains open.
