## Findings

1. **[P1] Cursor's launcher/grant section does not establish a publishable pull participant.** The file map, `scripts/lib/launcher.sh` bullets (plan lines 22–29), selects `--approval-mode never --trust-workspace` and repeats `--workspace` for the four external roots; the scope section explicitly excludes live compatibility proof beyond argv tests. The required invariant is that an installed participant can stage/commit/push and write its completion/response files under a demonstrated permission policy. Issue 210's launcher R row is expressly contingent on a working narrow-grant/Git design, and its acceptance step 2 states that pull delivery does not solve blocked Git/mailbox writes. Following these instructions retains the default `.git` protection, so a Git action cannot create its index lock and publish the required commit; asserting repeated workspace arguments also does not establish access to all four external roots. The risk paragraph proposes stopping if live publishing fails, but the test/scope sections exclude the check that would discover that failure. Require the filesystem/Git compatibility gate before shipping the config and specify the resulting verified launcher contract. Do not encode an unproved additive interpretation of `--workspace` as the expected test result. Meta's [permissions reference](https://dev.meta.ai/docs/muse-code/permissions) confirms the protected directories; no live success is claimed here.

2. **[P1] Claude's launcher section removes the write boundary instead of satisfying the required grants.** Product-code item 1 (plan lines 52–58) selects `--approval-mode never --disable-sandbox --trust-workspace` and intentionally discards `coord_grant`; the risks section substitutes the Git shim, product checks and pin verification for filesystem containment. The required invariant from issue 210's R-row contract and acceptance step 1 is narrow external-root access while coordinator-owned state and peer directories remain outside agent write grants. With this command, Muse can write the owner's `cursors.json`, peer response/mailbox files and other owner-writable files directly. A normal file write or shell redirection does not pass through the Git shim, and later product-pin verification cannot undo an altered workflow state or receipt. Describing the flags separately from `--yolo`, or noting Antigravity's existing posture, does not preserve that boundary. Keep compatibility blocked until a working bounded policy is demonstrated; an alternative isolation design needs explicit scope and evidence. The [vendor reference](https://dev.meta.ai/docs/muse-code/permissions) also states that disabling the sandbox removes file-tool confinement, not just shell restrictions.

Thus, after Cursor's proposed UI-default change, a normal Muse reminder still types `a` ahead of the owner's text. Add the small Muse prelude exclusion and its existing-file key-resolution regression; Claude's plan already includes this correction. This does not require enabling automatic nudge delivery.
