# Issue 240 — Implementation comparison

## Comparison

Bound implementation pins, all implementing the selected plan for issue 240 (resolve agent CLIs beside coord's Node, not the product's):

- codex: `613dfd04d651c73b180a1033753e6c974dc45301`
- muse: `2f48a6b3cdc68d2a8c7ac32e84d37b13a24f725d`
- cursor: `76db847bd32cde6a0adb55d5a68792caf23270bb`
- claude: `16dd9d5a4e1242ff63dd36250caf9c24ff564626`

All four stay within the issue and the approved path set (the same five product/test/doc paths each: `scripts/lib/launcher.sh`, `src/cli.ts`, `test/cli.test.ts`, `test/install.test.ts`, `docs/coord-driver.md`), create no new files, reuse `launcher_environment`/`launcher_executable`/`node-runtime.sh`, and keep the product's Node on `PATH` for the launched pane. They differ in four load-bearing details, in descending order of importance.

**Finding 1 — muse (`scripts/lib/launcher.sh:42`) and cursor (`scripts/lib/launcher.sh:63`): a vendor CLI discoverable only through the product pin is no longer found.** The rule that must hold is that maintenance and launch must keep finding an installed vendor when only its interpreter needs changing; before this change, `launcher_environment` ran `nvm use` first, so an installation under the pinned Node's bin directory was always reachable. Both implementations resolve the executable before `nvm use` against only the pre-`nvm` `PATH` (plus coord's bin and, for antigravity/muse, `~/.local/bin`), and return 1 when it is absent there. Concrete failure, verified with a shell probe against each bound worktree (clone pinning Node 16 via a fake `nvm.sh`, `claude` present only in the pinned bin, coord's Node 26 bin holding no `claude`): muse and cursor both fail with `ERROR: claude was not found beside coord's Node … or on PATH`, so maintenance warns and records `unknown` and a generated launcher exits, whereas claude (`scripts/lib/launcher.sh:77`, resolving against `coord_search` plus the post-`nvm` `PATH`) and codex (`scripts/lib/launcher.sh:64`, an explicit post-`nvm` `type -P` fallback) both resolve the pinned installation. Owner shells whose current nvm version differs from the clone's pin hit exactly this case. Smallest illustrative test: add the pinned-only case to the existing nvm-setup fixture — codex already carries it (`{ id: "claude", label: "pinned", … }` in `test/cli.test.ts`), muse and cursor do not.

**Finding 2 — muse (`src/cli.ts`, maintenance script) and cursor (`src/cli.ts`, maintenance script): the updater's own child processes still run on the product's Node.** The rule that must hold is the issue's requirement that updating agents use the Node coord requires, including ordinary Node subprocesses a vendor update spawns by name. Both implementations exec the resolved vendor command directly after `launcher_environment`, whose `nvm use` has put the pinned Node first on `PATH`, and neither prepends coord's Node for the maintenance child. Concrete failure: a vendor update distributed as a shell wrapper (`#!/bin/sh` + `exec node updater.js`) resolved beside coord's Node runs, but its `node` child is the product's pinned Node 16, so the update can fail or misbehave on exactly the workspaces the issue reports; a Node-shebang CLI that itself spawns `node`/`npm` by name has the same exposure. Codex (`src/cli.ts:179`) and claude (`src/cli.ts:183`) both add `export PATH="$(dirname "$coord_agent_node"):$PATH"` for the maintenance invocation only, and their tests assert the maintenance vendor sees `v26.1.0` as its child `node` while the launched pane sees the product Node. Smallest fix: copy that one-line maintenance-only prepend; no test in muse or cursor currently records which `node` the vendor's children see during update.

**Finding 3 — codex (`scripts/lib/launcher.sh:30`): a configured Node selector that fails hard-fails every launch and maintenance run.** The rule that must hold is the existing maintenance contract that failures warn and continue with a recorded null version, and its launch analogue that a degraded coord Node resolution should not be more fatal than the vendor lookup it feeds. Codex runs `coord_agent_node="$("$selector" --resolve)" || return 1` with no fallback, deliberately (its docs state a configured selector failure stops the invocation). Concrete failure: an owner who runs a generated launcher by hand with a stale `COORD_NODE` in their shell environment — a value the `coord` wrapper would reject, but a bare launcher never re-validates — gets no pane at all, even when a working vendor CLI is on `PATH`; claude (`scripts/lib/launcher.sh:51–56`), muse (`scripts/lib/launcher.sh:29`), and cursor (`scripts/lib/launcher.sh:41`) warn and fall back to `PATH` resolution in the same situation. This is a documented, defensible fail-closed choice rather than an oversight, but it is the only implementation that can turn a previously working launch into a hard stop. Smallest illustrative test: extend the nvm-setup fixture with `COORD_NODE` pointing at a Node below the floor and assert the previously expected behavior (launch proceeds with a warning) is the intended one.

**Finding 4 — cursor (`scripts/lib/launcher.sh:73`): the Node-shebang test matches any first line containing `node`, and cursor (`scripts/lib/launcher.sh`, entry check) silently skips coord Node resolution when the recorded CLI entry file is absent.** The rule that must hold is that shebang detection must identify a Node interpreter, not a substring, and that a skipped coord Node selection must be visible. Cursor's case pattern `"#!"*node*` wraps the resolved binary in coord's Node whenever `node` appears anywhere in the first line, so a shell wrapper whose first line merely mentions node (for example `#!/bin/sh` with a trailing comment, or an interpreter under a `node`-named directory that is not Node) is executed by Node and fails; muse (`scripts/lib/launcher.sh:51`, anchored `env node` / `env -S node` / path-final `node` patterns), claude (`scripts/lib/launcher.sh:47`, anchored Node-shebang regex), and codex (plain no-argument Node shebangs only) all anchor the match. Separately, cursor only attempts the selector when `[[ -n "$entry" && -f "$entry" ]]`, so an unbuilt or moved install (recorded `coord.cliEntry` whose file is missing) degrades to pre-`nvm` `PATH` resolution with no warning, while the other three at least warn. Both are narrow, but they are unforced errors in the only implementation that also carries Findings 1 and 2. Smallest fix: anchor the shebang patterns as muse does and warn when a recorded entry names a missing file.

**Finding 5 — claude (`scripts/lib/launcher.sh:51`) and, by omission, cursor and muse: no coord Node is available to maintenance or launch when the clone records no `coord.cliEntry`, and claude's warn-and-fallback re-opens the original failure silently.** The rule that must hold is that the two callers should have the same chance of selecting coord's Node; a vendored clone (no `coord.cliEntry`, by design in this repository) is still launched and maintained by coord, which knows its own Node. Codex's maintenance passes the running coordinator's own selector as `launcher_environment`'s third argument (`src/cli.ts`), so maintenance resolves coord's Node even without a recorded entry, while its generated launchers warn and fall back. Claude, cursor, and muse all derive the selector solely from the clone's `coord.cliEntry`; without one, maintenance performs the same post-`nvm`-style lookup that caused the issue, with only a warning (claude, muse) or silence (cursor, per Finding 4). Concrete failure: on a vendored clone in a Node-16-pinned product, `claude update` again runs the broken install and the version is recorded `unknown`, with no signal stronger than a warning line. Smallest fix: adopt codex's third-argument fallback selector for the maintenance call.

**Scope, reuse, and coverage compared.** Codex adds the most: the fallback selector argument, maintenance child-`PATH` prepend, post-`nvm` fallback, the strictest shebang handling, and the broadest tests (seven fixture cases including muse's no-update agent, the pinned-only fallback, and a no-pin case; child-Node assertions for both maintenance `v26.1.0` and launch `v16.18.0`; input-environment immutability; plus a host-vendor isolation fix in `test/install.test.ts`). Claude is next: maintenance child-`PATH` prepend, post-`nvm` fallback resolution, the broadest shebang regex, and tests asserting the maintenance child's Node and the pane's product Node, though its fixture reaches `coord.cliEntry` through a bare-repo `GIT_DIR` rather than a real clone config, and it adds two launcher-text assertions in `test/install.test.ts`. Muse is the smallest faithful implementation of the selected plan (hermetic fixture install copy, no `ensureBuilt` dependency), and cursor is the same shape as muse with the weaker shebang and silent-skip details of Finding 4 and an `ensureBuilt()` call in its regression test; neither muse nor cursor covers the pinned-only fallback or the updater's child Node. No implementation adds files, dependencies, or unrelated refactors, and none changes product `PATH` behavior in the pane.

**Verdict.** Codex `613dfd04d651c73b180a1033753e6c974dc45301` is the most complete implementation: it is the only one that simultaneously keeps the pinned-only fallback (Finding 1), gives the updater coord's Node for its children (Finding 2), and supplies coord's Node to maintenance on clones without a recorded entry (Finding 5), with the tests to prove each. Claude `16dd9d5a4e1242ff63dd36250caf9c24ff564626` is a close second, missing only the no-entry selector route. Muse `2f48a6b3cdc68d2a8c7ac32e84d37b13a24f725d` and cursor `76db847bd32cde6a0adb55d5a68792caf23270bb` both implement the selected plan's core correctly for the reported workspace, but both regress pinned-only discovery (Finding 1, probe-verified) and leave updater subprocesses on the product Node (Finding 2); between them muse is preferable for its anchored shebang patterns, warning on selector failure, and hermetic test fixture. Whichever pin is selected, Findings 1 and 2 should be treated as required follow-ups if they are not already in it, and Finding 3's fail-closed selector behavior should be confirmed as intended if codex is chosen.
