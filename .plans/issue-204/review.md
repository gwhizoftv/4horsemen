## Findings

1. **[P2] Claude — the file-map sections for `src/runLoop.ts` and `src/issueReport.ts`, plan lines 70–88, clear the notice only after a `tmux.nudge` result and display it without lifecycle correlation.** A current delivery-wait notice must stop when current observations show that copy mode ended or that the agent accepted the action; an `ordered` workflow cursor alone does not prove delivery is pending. If a pane initially blocks delivery in copy mode, then the owner returns to the bottom and submits the action directly, lifecycle state becomes accepted/working while the workflow cursor remains ordered. `maybeLifecycleNudge()` takes its lifecycle-wait return (`src/runLoop.ts:2053` and `2092`), or `deliver()` returns before nudge (`src/runLoop.ts:1353`). The planned clearing block is never reached. Status continues telling the owner to scroll to the bottom even while `observeUnfinished()` can see mode exited and the agent is working. The timestamp qualifies the old observation but does not make the current `[WAIT]` instruction accurate. Clear from the existing successful pane observation and correlate the status line with current delivery/lifecycle state. Add the accepted-without-another-nudge transition to the existing focused test.

2. **[P2] Cursor — Reuse and Scope, behavior 6 (plan line 45), displays the delivery-wait sentence for every live pane with `ownerTyping`.** The requested sentence describes coord deferring a send, so status must distinguish a blocked pending delivery from an operator merely reading an agent's output. After an action has been acknowledged and is running, or after the issue is complete while retained panes remain available, scrolling a live pane meets the plan's only two conditions. Every status caller then prints “scroll to the bottom to let coord send” although no send is waiting. A dropped agent with a retained pane can produce the same false instruction unless explicitly filtered. Correlate pane observations with active roster, current action identity, delivery state, and issue state before rendering a wait. Keep the live inspection if desired, but test a scrolled, already-accepted action and a completed issue as negative cases.

3. **[P2] Cursor — Reuse and Scope, behaviors 1–2 (plan lines 40–41), issues unconditional `pane-scrollbars on` commands.** Adding optional scrolling UI must not break launch/restore on the tmux versions accepted by the current preflight, which checks availability but imposes no 3.6 minimum (`src/tmux.ts:843`). tmux 3.5a does not recognize this option: it is absent from the [3.5a option table](https://github.com/tmux/tmux/blob/3.5a/options-table.c), and scrollbar support is introduced in the [3.6 changes](https://github.com/tmux/tmux/blob/3.6/CHANGES). On such an installation the new command fails, causing the existing nonzero-result handling to reject setup or interrupt a chained launch/attach sequence. Apply a narrow unknown-option fallback, such as `set-option -w -q`, and cover that path while retaining failures for required session options. Both other plans already address this compatibility boundary.

Selecting either plan therefore freezes a broader map than reviewed, including permission to change the generated launcher that both plans say should remain untouched. Move incidental references into Reuse and Scope or remove their path-like backtick formatting, then validate that extraction exactly equals the intended file list. Codex's extracted map is exactly its ten declared paths.
