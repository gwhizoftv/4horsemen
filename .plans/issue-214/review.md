# Issue 214 plan review

Reviewed the bound plans at codex `9ec5d2d04efc1d890625fb8b1227c84d3c13e861`, claude `db10819fb42817204292af7add329f7ce46890df`, and cursor `b3171cc5d6e2f7166cc501f1a09cbce689989cde`.

## Findings

**Cursor plan (`b3171cc5d6e2f7166cc501f1a09cbce689989cde`), Stop branch and Risks.** The plan preserves an older Stop only when `acceptance` is `"execution"`, and the Risks section says a null `acceptance` keeps today's Stop behavior. The rule is that an older Stop must leave the newer turn's execution and turn id in place, including when the live turn was recorded without that new field. Followed as written, the plan's own extension of `uses a current Stop despite background work and revokes it on a new turn` fails: that test's prompt submit carries turn `new` and no action id, so `acceptance` stays null, and the Stop for `old` still assigns `execution: "queued"` as the current `stoppingOlderTurn` branch does. The same gap remains for any in-flight lifecycle file loaded after the upgrade. Smallest correction: preserve execution, `stoppedAt`, and the previous turn id whenever the Stop's turn id differs from the live turn, and restore that previous id after the assignment at `src/agentLifecycle.ts:593`.

**Cursor plan (`b3171cc5d6e2f7166cc501f1a09cbce689989cde`), `orderAgentAction` reread acceptance.** The plan stores a reread continuation as `delivery: "accepted"` while `execution` stays `"working"`. The rule is that a ready receipt for the previous action, and the missing-Stop `COORD-IDLE` recovery, must still be able to send a replacement that the agent did not pick up. `readyForNextAction` returns null unless `delivery === "ordered"` (`src/runLoop.ts:1331`), and `staleWorking` is true only for that same ordered state (`src/runLoop.ts:1365`). Followed as written, a ready file written after the order is ignored, and a pane whose last line is `COORD-IDLE` with no Stop hook does not send. The later `maybeLifecycleNudge` return for accepted `working` or `queued` also skips `deliver`, so the receipt is never reconsidered. The replacement stays accepted and working with no prompt and no completion. Smallest correction: keep reread pickup at `delivery: "ordered"` until a prompt submit or a current-turn tool event proves the new action started, and let the ready receipt and `staleWorking` run for that ordered action.

**Claude plan (`db10819fb42817204292af7add329f7ce46890df`), queued-behind Stop.** The plan says a Stop of `queuedBehindTurnId` sets `execution: "working"`, clears that marker and `action.turnId`, and that any following Stop yields `idle` with an advanced epoch. The rule is that the Stop of the turn a prompt was queued into must not make the new action idle or eligible for another automatic send. `handleAgentEvent` applies a second identical Stop as a new observation (`test/agentEvent.test.ts` records a second lifecycle row for the same Stop payload). Followed as written, that second Stop finds no marker, sets `idle`, increments `idleEpoch`, and `decideLifecycleNudge` returns `send` while the agent is still on the queued prompt. Clearing `action.turnId` also makes `recordFailure` correlate the failure: its rule treats `action.turnId === null` as the current episode (`src/agentLifecycle.ts:515`), so a late failure from the preceding turn opens a resource hold on the new action. Smallest correction: keep `queuedBehindTurnId` until a different execution turn is observed or the action reaches `workflowCompleteAt`, and leave a non-null turn id so a mismatched failure stays advisory.

**Claude plan (`db10819fb42817204292af7add329f7ce46890df`), older Stop with pending input.** Fix 1 keeps today's `pendingInputCount > 0` result of `queued` even when `stoppingOlderTurn` is true, and test 1 requires that result. The rule is that an older Stop must preserve the newer turn's execution. Followed as written, a live turn `gen-new` with `execution: "working"` and `pendingInputCount: 1` becomes `queued` when Stop `gen-old` arrives, and the status text is again "accepted work that has not started". Smallest correction: an older Stop never changes execution or `stoppedAt`; apply the pending-input result only when the Stop's turn id is the live turn.

**Codex plan (`9ec5d2d04efc1d890625fb8b1227c84d3c13e861`), section 2 tool observations.** The plan normalizes Cursor `postToolUse` and `postToolUseFailure` to `working` observations and says repeated activity updates the hook receipt. The rule is that a tool callback must not invalidate a ready receipt the agent just wrote. `readyForNextAction` accepts the file only when its mtime is greater than `max(hookReceipt.at, lastEventAt)` (`src/runLoop.ts:1335`). `observeAgentLifecycleWithResult` advances `hookReceipt` for every non-telemetry observation, including one that leaves execution unchanged (`src/agentLifecycle.ts:752`). Followed as written, the `postToolUse` after the write that created `ready` moves the receipt clock past the file mtime, the ready file is rejected, and the missing-Stop recovery never sends. Smallest correction: a tool observation may set `execution` to `working` only from `queued` or `unknown` for the current turn, and it must not advance `hookReceipt` or `lastEventAt` when execution is unchanged, the same exemption telemetry already has.

## Conclusion

All three plans stay inside issue 214, extend existing modules, and add no product source file. Codex's `started` receipt is a sibling in the existing completion mailbox, which is the justification that plan gives for a new runtime path. The focused tests are extensions of existing files.

None of the three is safe to implement as written. Cursor's older-Stop rule contradicts its own test and its Risks section, and marking a reread `accepted` disables the ready-file and missing-Stop sends. Claude's queued-behind Stop clears the guard that the duplicate Stop path needs, and it still lets pending input overwrite a newer turn. Codex's tool observations advance the hook receipt and reject the ready file that recovery depends on. The corrections above are local: preserve every older Stop, keep unproven reread actions `ordered`, hold the queued-behind guard until a new execution turn or workflow completion, and keep tool callbacks from moving the ready-file clock.
