### Findings

**1. cursor `src/setupWorkspace.ts:308`: Python is consulted before the Make
detector.**
- **Rule:** reinstalling, which is the documented repair path, must not
  silently replace a finalization gate the installer already produced for an
  unchanged tree. All three plan reviews required that a Makefile with a
  `test` target keep precedence.
- **Failure:** a repository has `pyproject.toml` and a Makefile whose `test`
  target prepares its environment (for example `uv run pytest`) or runs
  unittest.
  - At baseline, it onboards with `checks: make test`.
  - At this pin, re-onboarding records `pytest -q` / `pytest -q` instead. That
    fails in the fresh finalization worktree, or misses unittest-style tests.
- **Test:** in the `installer proposals` block,
  `writeFileSync(Makefile, "test:\n\ttrue\n")` plus `pyproject.toml`, then
  `expect(proposeProjectPolicy(root).checks).toEqual([{ name: "test", argv: ["make", "test"] }])`.
  This fails at cursor's pin and passes at the claude and codex pins.

**2. claude `src/setupWorkspace.ts:245` and cursor `src/setupWorkspace.ts:198`:
`flutter analyze` keeps its default fatal-infos behaviour.**
- **Rule:** an inferred commit gate must fail on defects, not on advisory
  diagnostics that predate the agent's change. Otherwise every agent commit
  depends on unrelated cleanup.
- **Failure:**
  - `flutter analyze` treats info-level diagnostics as fatal by default.
  - Apps generated by `flutter create` enable `flutter_lints`, whose rules
    report infos such as `prefer_const_constructors`.
  - An existing app with one such info blocks every precommit at these pins,
    and blocks finalization too, since `analyze` is the first finalization
    check.
  - codex (`src/setupWorkspace.ts:261`) records
    `["flutter", "analyze", "--no-fatal-infos"]`, which keeps warnings and
    errors fatal, and announces it.
- **Test:** for the block-form pubspec, expect
  `checks[0].argv` toEqual `["flutter", "analyze", "--no-fatal-infos"]`.
  This is codex's existing case in `test/verify-config.test.ts`.

**3. claude `src/setupWorkspace.ts:244` and cursor `src/setupWorkspace.ts:286`:
the Flutter detector runs before Node, even when Node already supplies checks.**
- **Rule:** the same no-silent-regression rule as finding 1. A root
  `package.json` whose `check` or `test` script onboards today must keep
  producing that gate.
- **Failure:** a Flutter app that keeps a root `package.json` with a `test`
  script (for tooling or web glue) onboarded at baseline with `npm run test`.
  At these pins a re-onboard records `flutter analyze` / `flutter test`
  instead.
- **Severity:** low. The plan's stated order (Flutter before Node) is what
  these two pins follow, and such repositories are uncommon.
- codex's `src/setupWorkspace.ts:242` keeps the Node proposal whenever it has
  checks. It falls through to Flutter only for a Node manifest with no
  finalization script, and `test/verify-config.test.ts` pins both directions.

**4. cursor `test/onboard.test.ts:523` and `:533`: the missing-tool regression
depends on the host and asserts the wrong thing.**
- **Rule:** a regression test for "a missing inferred tool is a doctor
  finding" must not depend on what the host installs in `/usr/bin`. It must
  also assert the specific executable.
- **Failure:**
  - The test sets `PATH=/usr/bin:/bin` and expects some `toolchain` finding.
  - On a Linux host with distribution pytest (`/usr/bin/pytest`, e.g. Debian's
    `python3-pytest`), `pytest` resolves, so no toolchain finding is raised
    and the test fails.
  - The assertion checks only the finding class, so a finding for some other
    executable would also satisfy it.
- **Comparison:**
  - claude's pin uses `flutter` for this case (`test/onboard.test.ts:469`),
    which no system directory provides, and asserts `subject: "flutter"`.
  - codex's pin builds a PATH that contains only symlinked system tools, and
    asserts the subject.
- **Fix sketch:** use `flutter` (or a hermetic PATH) and
  `toContainEqual(expect.objectContaining({ class: "toolchain", subject: "pytest" }))`.

### Scope, reuse and coverage

- **Detection.**
  - claude adds a private `declaresFlutterSdk` and a `PYTHON_MARKERS`
    constant.
  - cursor adds separate `proposeFlutterPolicy` and `proposePythonPolicy`
    helpers.
  - codex adds a compact `hasFlutterSdk` and keeps everything else inline in
    `proposeToolchainPolicy`.
  - None introduces a new module or abstraction beyond these.
- **Tests.**
  - codex's tests are the most compact: a table-driven `it.each` for markers
    and manifests, one mixed-precedence walk-through, and one parameterized
    onboarding test. Together they cover dry run, missing tool, success, a
    partial-declaration override, and coordinator labels.
  - claude's coverage is similar, spread over three onboarding tests.
  - cursor's tests are the largest and include finding 4.
- **Docs.** All three update `README.md` and `docs/setup-workspace.md`.
  cursor's README states the order "Cargo, Go, Flutter, Node, Python, then
  Make", which matches its code and therefore finding 1.
