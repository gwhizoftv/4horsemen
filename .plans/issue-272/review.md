## Findings

Reviewed the bound Antigravity plan at `8cbda15a6b23bb8dada9927ccd2ff935e860c924`, Claude plan at `4cb22ad81efae1a6f6bee01c8682288ab6eeb728`, and Codex plan at `f3c1cdcb1b4c7fe3349255dea5ceeac8aa8897b2` against the frozen issue and the verification, evidence and owner-control paths.

1. **Antigravity and Claude, receipt keys.** A success reused after the PATH fix must establish that the check ran under the selected product runtime. Before the fix, `runVerification` records `process.version` even when pnpm invokes a different Node. Suppose the coordinator and product both select Node 26, the old child used Node 23, and the cache declaration lists neither PATH nor a runtime probe. Recording the effective version still yields the identical v1 key. The gate can accept the Node 23 result without executing the check under Node 26. Change the receipt identity for corrected executions and seed this specific legacy receipt in the regression test.

2. **Antigravity and Claude, owner retry.** Retry must re-evaluate the same signal commit and the same approved product commit identified in the question. The plans clear the question and rely on the completion marker staying in place. In `src/runLoop.ts`, the next tick reads that writable marker and assigns its value to the cursor's submission SHA before evaluating it. A replacement valid signal can therefore select a different cleanup commit. Antigravity's CLI fixture also puts `finalSha` in the marker, which `src/evidence.ts` explicitly rejects because the cleanup pin and its later signal commit must differ. Persist both SHAs with the action identity through the retry and test replacement of the marker during the owner wait.

3. **Antigravity and Claude, baseline eligibility and missing executables.** A failed final command must receive a baseline execution under the same environment. The resulting evidence determines whether owner retry is appropriate. Both plans skip the baseline when the candidate output fails the keyword filter. Antigravity also skips checks added by amendment, including one that could invoke a tool already required by the baseline. Further, when the declared executable itself is unavailable, `runArgv` rejects with ENOENT and `runVerification` rethrows before either plan's comparison of nonzero process results. A real `["protoc", "--version"]` check can consequently bypass the owner recovery flow altogether. Run the effective command on both pins and distinguish a named executable lookup failure from unrelated runner errors. Generic-only output still cannot establish equivalence.

4. **Antigravity, baseline receipt reuse.** A baseline comparison must observe the current failure environment. The plan explicitly permits cached baseline commands. A baseline success recorded before a tool disappeared can stand in for running the failed check today. The candidate is then sent for correction even though both revisions currently lack the tool. Run the diagnostic prefix through the failed command without reading or producing success receipts, including for setup that must create files in the fresh worktree.

5. **Claude, comparison capped at 50 diagnostic lines.** The display budget may truncate evidence shown to the owner, but the match decision must account for conflicting actionable diagnostics. If two compiles have 50 common errors and the candidate has a distinct 51st error, the proposed lists compare equal. The owner gets a shared-failure question for a candidate-specific regression. Compare all specific evidence independently of the excerpt limit, or mark an incomplete comparison inconclusive.

6. **Antigravity and Claude, baseline measurement phase.** The hook mailbox must accept only hook verification phases. Both plans widen the shared schema to include `baseline`. Claude says hook ingestion already excludes every phase except precommit and prepush. In fact, `createVerificationIngestor` in `src/verificationLog.ts` explicitly excludes only `candidate` and `finalization`. A hook envelope with the new phase would enter the journal as a baseline-phase measurement and distort reporting. An allowlist of the two hook phases preserves provenance.

7. **Codex, Node fallback in “Reuse and Scope.”** A project using its configured Node from PATH should retain that selection when coordination has no project pin to resolve. For a Node 22 project without `.nvmrc`, launched with Node 22 on PATH and Node 26 selected solely for coordination, the proposed fallback puts Node 26 first for checks. That can fail a valid product or certify it under an unsupported version. Preserve the product environment in the absence of a product selection, and key the receipt to the runtime actually used.

## Conclusion

Use the Codex plan with the unpinned-runtime correction in finding 7. Its explicit receipt invalidation, separate submission and product pins, uncached baseline execution and fresh owner retry address the failures above. The public recovery command already exists. The proposed environment module has two production callers, and the existing verification and run-loop fixtures can exercise all three issue requirements.

Claude keeps the file map small and reuses nvm, the verification runner and owner questions. Its focused tests cover both correction cases. Extend them to cover a legacy receipt and a replaced completion marker. Antigravity gives the owner evidence in both status and the interactive menu. Its shared resolver has a clear caller in each execution path, and extracting diagnostic comparison keeps display and matching independently testable. Implementing an additional Node range parser and repeating the full retry-to-publication scenario in the CLI suite adds scope. A CLI assertion for answering the question and one run-loop publication test cover those distinct responsibilities.
