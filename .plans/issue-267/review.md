## Findings

1. **All three plans limit acceptance to Codex and Cursor.** The owner's requirement covers Codex, Cursor, Claude, Antigravity, Muse, Gemini and OpenCode, regardless of the active issue roster. A Muse-only workspace could pass every proposed check while releasing a selection leaves the previous text on the Mac pasteboard. Use one parameterized attach/resume test covering all seven launcher IDs. For each supported window, acceptance is an ordinary drag, release and paste into another app yielding the exact selected text, with existing wheel and trackpad scrolling still usable.

2. **The Codex plan's Reuse and Scope steps 1–3 mark only Codex and Cursor and retain the existing linked-client mouse policy** (`9e8d67c7bc6eb1665efd60550ae25683b8b8bd37`). Each managed agent pane must receive the copy behavior through both a freshly attached client and one that stays open through resume. Marking all panes alone would still leave a default Muse linked client with tmux mouse handling off. Its drag would never reach the proposed tmux release binding. Apply the pane policy by coordinator ownership and establish the required mouse setting on new and existing managed macOS agent clients. Keep the wheel bindings and existing per-window scrollbar settings. Verify external paste for both an application that requests mouse events and one that leaves them to tmux.

3. **The Claude plan's proposed helper sets the server's empty copy command to `/usr/bin/pbcopy`** (`97409c3f955c3c7173776ef08f17803f81e1eecb`). A clipboard write introduced by coord must originate in a managed agent pane. On a shared server with an initially empty option, starting an issue would make a subsequent copy in an unrelated tmux session replace the Mac pasteboard. The empty-value guard protects a configured command but cannot isolate that later copy. Its real-tmux test asserts the server option value and would pass with this regression.

4. **The Antigravity plan tags sessions according to the three-agent scrolling allowlist and relies on the default copy-mode release command** (`efac99cd51e776e118ea6d7930a82804872af86a`). Copy eligibility must follow the managed agent pane where the user drags. The primary session's control window would qualify for a clipboard write, while a linked Muse, Gemini, Antigravity or OpenCode client gets no marker of its own. A TUI that consumes the initial drag can also bypass copy mode entirely. Calling `copy-pipe-and-cancel` directly in the proposed test skips that event routing. Exercise an actual drag from the linked client and keep a distinct sentinel in the clipboard sink when dragging in an unrelated pane.

5. **Claude's and Antigravity's two-file maps include additional backticked examples outside Reuse and Scope.** The coordinator must extract only the paths an implementation needs. Running the repository's file-map extractor on the pinned plans admitted the entire `githooks/` tree for Claude and `package.json` for Antigravity, along with dotted identifiers in both. Either map would allow changes beyond its declared two files. Put incidental examples in plain text or the reuse section when preparing a corrected map. The Codex plan extracts exactly its three declared paths.

## Conclusion

All three plans need the seven-agent acceptance criterion. The Codex plan offers the closest starting point because its pane marker can distinguish agent windows from a control window and unrelated sessions sharing the same tmux server. Its two-agent restriction and linked-client mouse setup both need correction. The existing controller, mocked runner and private-socket tmux fixtures are sufficient. The proposed owner-guide edit explains the gestures, and the work needs no new files or dependencies. One roster table and one end-to-end drag test per mouse-reporting behavior keep the regression coverage focused.
