## Findings

1. **cursor — Tests / `runLoop.ts` candidate failure path.** The plan’s Tests section says a candidate failure yields `retry-verification`. Rule: `machine.ts` maps `status: "retry"` → `retry-verification` (cursor → `intent`, same completion re-evaluated with no new action) and `status: "rejected"` → `reissue-action` (agent gets a corrected R4/R6 naming the outstanding text). Failure if followed: the implementer learns nothing about the failing command or log; the same pin is re-checked forever. Smallest correction: return `rejected` with outstanding naming command + log path (as claude does); reserve `retry` for coordinator launch errors that already throw.

2. **cursor — Exact File List / `githooks/lib/policy.sh` + `githooks/pre-push` `--ref`.** The plan edits hook bodies to pass `--ref`. Rule: `pre-push` already pipes `local_ref local_sha remote_ref remote_sha` into `coord_verify` / `hook-verify` stdin, and `inspectOutgoingChanges` already consumes that stdin; product `githooks/` edits force resync/drift and are not required for binding. Failure if followed: every installed clone needs a hook resync for no new information, and binding logic still has to parse stdin for multi-ref detection. Smallest correction: resolve the branch from prepush stdin (single ref → bind; multi-ref → unbound) and leave hook bodies unchanged (claude/codex).

3. **cursor — Exact File List / `src/orderScaffold.ts`.** The plan changes order scaffolds so comparison/ballot surfaces candidate results. Rule: scaffolds are agent-authored JSON that can be copied back; coordinator check outcomes must not round-trip through untrusted agent artifacts (issue: do not trust agent-authored “tests passed”). Failure if followed: a peer can forge or omit results inside scaffold JSON while the real receipt/logs say otherwise. Smallest correction: put pin results only on `InternalOrder` / `buildOrder` → `action.md` rendering (claude/codex); do not edit `orderScaffold.ts`.

4. **cursor — Created files / receipt key “command argv”.** `verificationReceipts.ts` keys on “command argv” without distinguishing declared vs executed vectors. Rule: `verifyFinalizationChecks` substitutes `{worktree}` with a random `.verification-<uuid>` path before spawn, so an executed-argv key never matches a later equivalent run. Failure if followed: receipts never hit; every candidate/final always re-runs. Smallest correction: key on the declared argv (and policy digest / probes / env), as claude states explicitly.

5. **cursor — File map omits `src/changeClassification.ts` while requiring path-to-check `selection`.** The plan stores `candidate.selection` in `state.ts` and says `runLoop` will “apply the selection rules”, but reuses only today’s `selectVerification` (precommit/prepush/finalization × coordination/docs/product). Failure if followed: selection is under-specified or duplicated; hook/template changes may not pull E2E/system forward; unclassified paths may stay on the narrow candidate list. Smallest correction: extend `changeClassification.ts` with a candidate selector (claude’s `selectCandidateVerification` / codex’s candidate-phase extension) and list that file in the map.
