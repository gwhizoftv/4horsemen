## Findings

### cursor `c7466372`

**C1 — blocking. Pane probe types into the AI prompt, not a shell.**
- *Plan claim:* `src/tmux.ts` is to "send a one-line `command -v git` into each
  agent pane and parse `capturePane` output for a path ending in
  `/.coord/bin/git`".
- *Rule:* the probe must run in the agent's shell-tool process. It must also not
  cost model calls or inject text into a harness prompt.
- *Failure:* the tmux pane runs the harness TUI, not a shell. The generated
  launcher ends in `exec claude --permission-mode auto …` and
  `exec codex --ask-for-approval never …` (`scripts/lib/launcher.sh:31,39`).
  The keystrokes `command -v git` + Enter therefore become a chat message to the
  model. The model then spends a turn answering it, and the capture contains
  prose, not a resolved path. The parse then fails in one of two ways:
  - It reads the agent's answer. Claude may well run the command and echo
    `<clone>/.coord/bin/git`, so the probe would "pass" based on what the model
    said, not what was measured.
  - It finds no match and refuses the agent.

  The injection also races the action nudge that `src/tmux.ts:826-933` guards
  with `harnessPromptReady`.
- *Smallest correction:* have the agent run the probe through its own shell tool
  as part of an action it already has (claude and codex plans), or enforce at
  the shell-tool hook (claude plan).

**C2 — blocking. Refusing inert agents with no remedy strands Cursor permanently.**
- *Plan claim:* `src/cli.ts` / `src/runLoop.ts`, "on inert PATH, refuse further
  automated work for that agent".
- *Rule:* containment must be either enforced or visibly reported. The fix must
  not require changing a harness, which the issue lists as not in scope.
- *Failure:* the measured Cursor harness rebuilds PATH after `exec` in every
  session. The plan adds no enforcement point other than PATH. Cursor would
  therefore be refused on every issue from now on, so a working agent is removed
  from the roster. That is a worse outcome than the advisory text it replaces.
- *Smallest correction:* add the native shell-tool hook (`beforeShellExecution`
  for Cursor) as the issue review recommends. Alternatively, warn instead of
  refusing until such a layer exists.

**C3. Removing only `COORD_GIT_DELEGATE` can turn refusals back on during verify.**
- *Plan claim:* `src/hookPolicy.ts`, "strip `COORD_GIT_DELEGATE` from the child
  env", with no other change.
- *Rule:* the verification boundary must isolate coordinator containment state
  as a whole: `COORD_GIT_DELEGATE`, `COORD_ISSUE`, and the `.coord/bin` PATH
  entry together. The issue review requires testing both states together.
- *Failure:* `hook-verify` runs inside an issue-session clone where `COORD_ISSUE`
  is set and `.coord/bin` is first on PATH. Removing only the delegate flag means
  any declared check that runs `git diff` or `git status` against the clone
  (a lint-staged-style step, or `git diff --exit-code`) now hits the shim and
  exits 2. A commit that passes today would fail its pre-commit hook. The
  proposed `test/verify-config.test.ts` case only asserts that the key is
  absent, so it cannot catch this.
- *Smallest correction:* also drop `COORD_ISSUE` and the `.coord/bin` PATH
  entries. The codex plan's §3 does this.

**C4. `inspectGitShim` readiness gate duplicates checks and mostly cannot fire.**
- *Plan claim:* the `src/prepareAgentBranch.ts` readiness gate refuses on a
  missing or unmarked shim.
- *Rule:* new readiness gates must detect the failure the issue reports.
- *Failure:* the measured failure (shim present, PATH reordered) passes this
  file check. The case it does catch, a missing shim, is already regenerated by
  `coord install` (`src/install.ts:400`) and `githooks/post-merge`. This is
  extra scope with little benefit. The doctor finding alone covers it.

### codex `59c72ee1`

**X1 — blocking for issue fit. Detection only; the Cursor bypass stays unenforced.**
- *Plan claim:* "Implement the issue's warning-first option … not a promise that
  PATH is a security sandbox." There is no enforcement layer beyond the existing
  PATH shim.
- *Rule:* the issue's owner-account review ("Recommendation updated
  2026-10-05") scopes this implementation as "one narrow policy across all four
  agents". That means vendor shell-tool hooks reusing `src/agentHookSync.ts`,
  with the shim kept as a fallback.
- *Failure:* after this plan ships, the measured Cursor session still runs
  `git status` and `git diff` with exit 0 on every action. The only change is a
  warning that will always be present, because the harness keeps rebuilding
  PATH. The issue's first impact item, that agents "have been running
  unconstrained", is unchanged.
- *Smallest correction:* add hook-based enforcement that reuses the shim's
  policy. The probe and warnings in this plan then become the verification half
  of it.

**X2. A probe in every action adds the redundant tool use the issue wants to remove.**
- *Plan claim:* "Reuse `buildOrder` to append the probe instruction for both
  submission modes". "One bounded probe per action".
- *Rule:* verify after initialization, and repeat only after a restart or a
  configuration change, "not before every action". The purpose of the issue is
  fewer redundant tool calls.
- *Failure:* each issue has roughly 10–20 actions per agent across plan, review,
  implement, ballot, and revise. Every one of them gains a `coord probe-git` tool
  call plus a spawned `git status`. Response-mode ballots, which today need only
  a JSON write, gain a shell call and a clone-local file write.
- *Smallest correction:* probe once per lifecycle session, for example in the
  R1.join action. Re-issue the instruction only when the lifecycle `sessionId`
  changes.

**X3. Binding the probe to the action id makes every new action unverified until re-probed.**
- *Plan claim:* "Match clone, agent, issue session, action id/digest … Old
  actions … are unverified, never success."
- *Rule:* verification evidence should last as long as the property it measures.
  Here that is the harness session's PATH, not the action.
- *Failure:* combined with X2, every action change resets the agent to
  `unverified`. Doctor then emits code 23 until the agent probes again. If the
  agent skips the probe once, warnings fire on a correctly contained agent,
  which trains the operator to ignore them.
- *Smallest correction:* bind the probe to the session id, and use the action id
  only as provenance.

**X4. Partial scope note on `hermeticGitEnv`.**
- *Plan claim:* §3 reuses `hermeticGitEnv` (`src/mirror.ts:36`) inside
  `inheritRunner`.
- *Rule:* the follow-up the issue names should be kept separate so that the
  containment change can be reviewed on its own.
- *Failure:* not a correctness failure. Bundling makes a regression in either
  part block the other.
- *Assessment:* the content of §3 is correct, and it is the right fix for C3. It
  is acceptable here if the owner wants it, but it should be called out as a
  separable commit.

### claude `b284c842` (self-review)

**L1. A restart mid-issue leaves coverage `unverified` with no way to re-probe.**
- *Plan claim:* the probe instruction is added only to the `R1.join` task text,
  and `containmentCoverage` returns `unverified` when the probe's `sessionId`
  differs from the entry's current session.
- *Rule:* verification has to be repeatable after a restart or configuration
  change.
- *Failure:* a harness restarted after R1.join has a new `sessionId`. Status
  shows `hook=unverified shim=unverified` for the rest of the issue, even when
  the guard is in fact denying. There is no action that asks the agent to
  probe again.
- *Smallest correction:* treat any `hookDenial` recorded with the current
  session id as `hook=active` without needing a probe. Also add the same probe
  sentence to the first action delivered after a lifecycle session change, in
  `buildOrder` and only when the entry's probe session is stale.

**L2. The resolution probe ignores `COORD_GIT_DELEGATE`.**
- *Plan claim:* `containment-probe` records `shim=active` when the first `git`
  on PATH is the clone shim and `COORD_ISSUE` is set.
- *Rule:* the codex plan states the rule correctly: a matching path is not
  enough if inherited controls disable the shim.
- *Failure:* suppose the agent shell inherited `COORD_GIT_DELEGATE=1`, which is
  the leak described in the issue. The shim then `exec`s real git without any
  check (`launcher.sh` delegate short-circuit), yet the probe reports
  `shim=active`.
- *Smallest correction:* record `bypassed` when `COORD_GIT_DELEGATE=1` is
  present.

**L3. Hermetic `hook-verify` is deferred.**
- *Plan claim:* "Hermetic `hook-verify` env — follow-up."
- *Rule:* the issue body lists it as direction item 3. The owner-account review
  moves it to "a separate, small follow-up".
- *Assessment:* this is within the review's scope. It should be filed as its own
  issue that cites codex §3 as the design, so it is not lost.

## Conclusion

The cursor plan is **not acceptable as written**, because of C1 and C2. Its pane
probe measures a chat reply rather than a shell, and its refusal would
permanently exclude the agent the issue measured as bypassed.

The codex plan is **sound but incomplete**, because of X1. It makes the gap
visible but leaves the measured bypass unenforced. It also contradicts the
issue review's four-agent hook scope. Its per-action probe (X2/X3) works against
the efficiency goal.

The claude plan is **the best basis**. It meets the issue review's scope: one
shim policy, all four vendor hooks through `agentHookSync.ts`, verification
inside the shell tool, and warning-first surfaces. It needs these amendments:
- L1: count same-session denials as hook coverage, and re-probe only after a
  session change.
- L2: treat inherited `COORD_GIT_DELEGATE=1` as `bypassed`.

Codex §3 should be adopted as the design for the separate hermetic
`hook-verify` follow-up (L3, and the correction for C3).
