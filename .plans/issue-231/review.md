## Findings

1. **[P2] Claude — Problem/precedence steps 3–4 and the `discoverBaseBranch` catch-all fallback.** When onboarding is asked to select GitHub's default without an explicit override, it must not treat a failed discovery as evidence that `main` or an old saved branch is the current default. Consider a repository with both `main` and `release/alpha`, whose GitHub default is `release/alpha`: on first onboarding, an unavailable gh/API produces a warning, then the plan allows installation to succeed and writes `main` to both required stores. Re-onboarding a workspace originally misconfigured to `main` has the same failure through the saved-value fallback. The existing local-branch check will pass, so the warning does not prevent subsequent work from targeting the wrong branch. Require a successful lookup or an explicit branch before writing a new GitHub-derived configuration; a failed refresh may leave existing configuration untouched and report that it could not refresh. The new regression should cover a failed first lookup with a locally valid but incorrect `main`, rather than only a saved value already known to be correct.

2. **[P2] Cursor and Claude — Risks and Mitigations, “default branch missing locally,” and the decision to retain the local `refs/heads/<branch>` preflight.** A discovered branch that is already available as a valid origin tracking commit must be usable without requiring the owner to create or check out a local branch. With the owner on `feature/work`, `refs/remotes/origin/release/alpha` present, and no `refs/heads/release/alpha`, both plans discover the correct default but then reject onboarding at `src/install.ts:372`; neither required configuration target is updated. Fetching normally updates the tracking ref and still does not satisfy this local-head requirement, so the stated fetch remedy does not resolve this case. `ensureAgentClone` already supports seeding from that exact origin tracking commit (`src/setupWorkspace.ts:490–503`). Accept that existing source in preflight and add the remote-tracking-only case to an existing fixture; no owner checkout change is necessary.

3. **[P2] Cursor — Exact File List and Risks and Mitigations, fake GitHub fixtures.** Every newly introduced GitHub request in existing tests must be intercepted, and every file requiring that adjustment must be in the approved file map. The plan makes discovery mandatory inside `install()` but omits `test/cli.test.ts`. Its existing `installedWorkspace` uses `https://github.com/example/myserver.git`; multiple `runCli(installArgs(...))` calls currently provide neither a discovery stub nor an explicit branch (`test/cli.test.ts:1909–1944`, `1966–1968`). Under the proposed synchronous installer discovery those calls execute real gh and fail on unavailable/nonexistent repository access. The account test's existing CLI runner also does not intercept a separate installer `spawnSync` lookup. Implementing only the listed test changes therefore leaves the required system suite dependent on live GitHub; repairing those callers later would expand the approved map. Include that test file and specify how its CLI invocations supply or bypass the installer discovery seam. Likewise, if direct installer fixtures need adjustment, list `test/install.test.ts` unconditionally rather than leaving the target as an alternative.

4. **[P2] Cursor — Tests, `pnpm vitest run test/githubIssue.test.ts test/onboard.test.ts`.** A named focused verification command must actually execute the integration test it claims to cover. The default `vitest.config.ts` explicitly excludes both `test/onboard.test.ts` and `test/install.test.ts`; passing their filenames as filters does not undo that exclusion. The proposed command can pass after running only the metadata helper tests, without exercising either persisted configuration value. Keep the fast helper command and run onboarding/installer tests with `--config vitest.system.config.ts`. The later precommit suite remains required, but it does not make this focused command accurate.

Scope and reuse assessment: all three plans address the issue's existing `baseBranch` and `consensus.sharedBranch` flow and avoid new product files, dependencies, hook changes, or version bumps. Reusing the existing repository parser, account binding, configuration writers, and workspace fixtures is appropriate. Claude's six-file scope is concrete and accounts for existing CLI test stubs, but its fallback and local-ref behavior leave the failures above. Cursor's discovery-in-install proposal seeks consistent library behavior, but its affected test map and actual test invocation need to be corrected before implementation. Its new tests are otherwise focused on the requested persistence behavior.

Codex's eight-file scope explicitly includes the existing CLI/installer fixture updates and a documentation update for changed error/override behavior. Its additional tests cover the new branch-resolution boundary, account selection, dry-run, and the remote-tracking-only case; they reuse existing files and fixtures. The plan deliberately limits automatic discovery to the two public CLI commands and preserves the synchronous embedded APIs' explicit-branch contract. The issue requests `coord` onboarding behavior, so that boundary is acceptable without a broad installer API conversion. No blocking finding was identified in the Codex plan.
