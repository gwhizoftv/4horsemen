## Comparison

Compared the complete exported worktrees for Claude `217bc09ccd656ab932b5c5fdba76b48c292b2411` and Codex `4b1986e6a2a81ab956fb42371af2ce1af2ec8df4`, against the selected issue-261 plan. Neither implementation is ready unchanged. Prefer Codex as the revision base: it handles competing ecosystems, native configuration compatibility, ordinary timing selection, and distinct cumulative proposals more completely. Its publication lookup, saved-policy preservation, proposal validation, command parsing, and the shared diagnostic gap below still require correction.

### Codex findings

1. **`src/runLoop.ts:3002` (P1): publication must use the same authorized product pin and effective policy as final verification for every workflow profile.** Solo and reviewed workflows do not create an implementation-selection or consensus decision. `deriveBoundInputs` nevertheless binds their accepted implementation as the R7 consensus input, and amendment preparation/verification use it. Publication instead looks only in the two absent decisions, loses the amendment, computes the original digest, and rejects the already verified finalization as an old policy. New-check adoption therefore stalls before publication in both profiles. A focused helper reproduction returned a valid R7 input and an undefined publication pin; the amended and publication digests differed. Extend the existing adoption/publication test to real solo and reviewed cursors without an artificial implementation selection, and require persistence plus successful publication after verification and restart.

2. **`src/projectChecks.ts:402` (P1): reinstall must preserve an existing undeclared local policy; only a deliberate selection or first-install resolution may create an explicit empty policy.** For saved `{ checks: [] }` with no `verify`, `resolveProjectChecks` returns `verify: { precommit: [], prepush: [] }`. `install.ts:404` merges that into the declaration and writes it back. Rerunning install consequently converts the missing-policy commit refusal into an explicit opt-out, without an owner choice. The direct resolver reproduction produced exactly that conversion. Add a reinstall regression asserting that absent saved `verify` remains absent and the existing undeclared-policy hook still refuses product commits.

3. **`src/evidence.ts:215` (P2): proposal acceptance and adoption must agree on the supported entry-point object types.** Acceptance only requires non-null `mirror.readBlob`, whose Git show implementation also returns tree listings and symlink contents. A proposal naming `scripts` or a tracked symlink can thus reach approval, but `checkAmendments.ts:35` accepts only regular-file modes 100644/100755 and rejects it during R7 amendment preparation. The issue cannot finish with its approved proposal. Add evidence tests with a directory and symlink and require rejection before review, matching the adoption rule.

4. **`src/projectChecks.ts:320` (P2): quoted custom commands must preserve literal argument content, including backslashes that do not escape a double quote or another special character.** The parser strips every backslash inside double quotes. Entering `python3 -c "import re; assert re.fullmatch(r'\d+', '123')"` saves a program containing `r'd+'`. In the focused reproduction the entered argv exited 0 and the parsed argv exited 1. Extend the command-input tests with this argument and verify byte-for-byte preservation; keep execution as argv without shell expansion. Claude's double-quote parser distinguishes these escape cases.

### Claude findings

5. **`src/checkAmendments.ts:80` (P1): a later distinct proposal must add to the authorized lineage's earlier additions, while omission carries them forward.** Selecting only the latest proposal discards an R4 proposal for `scripts/a.sh` when R6 adds a different proposal for `scripts/b.sh`. `effectiveFinalChecks` then runs and persists only B, so the earlier approved check A is never required before publication or in later issues. A direct two-submission reproduction returned only the second command. Extend the existing lineage/adoption test with two different entry-point sets and assert that both ordered sequences survive verification, persistence, and restart; distinguish a correction of one proposal from a separate addition.

6. **`src/projectChecks.ts:34` (P1): malformed relevant metadata must be reported, not converted into permission to skip automated checks.** `nodeScripts` catches malformed `package.json` and returns no scripts; discovery reports neither a plan nor a problem, and unattended resolution saves empty local and final checks. A fixture containing only `{"scripts":` reproduced `problems: []` and explicit empty settings. Add a malformed-package unattended-onboarding test that requires an actionable error and no saved replacement policy. The equivalent swallowed YAML read also deserves coverage.

7. **`src/projectChecks.ts:367` (P2): competing build systems must be offered as alternatives and must not be chosen arbitrarily without a terminal.** Discovery calls the legacy first-match detector only once. With both `Cargo.toml` and `go.mod`, it exposes only Cargo and unattended onboarding silently selects Cargo checks, leaving the Go part unchecked. The focused fixture reproduced one Cargo plan and automatic selection. Extend discovery/onboarding coverage to two legacy ecosystems, not just a native plan beside one ecosystem; require both alternatives and unattended refusal pending a choice.

8. **`src/projectChecks.ts:681` (P2): choosing a discovered nonempty command must offer the requested commit / before-PR / both timing choice.** Every legacy ecosystem plan has `settings`, so this early return bypasses the timing prompt. A fresh package with a test script offered only “Choose how to check changes” and immediately saved final-only npm tests. An owner cannot choose commit or both through the advertised normal flow. Exercise an ecosystem plan through the interactive chooser and assert the timing prompt and selected placement, while retaining the saved-settings keep behavior.

9. **`src/projectChecks.ts:477` (P2): a CMake test chain must build the configuration that its test preset executes.** Matching only `configurePreset` pairs a Release build preset with a Debug test preset sharing a Ninja Multi-Config configure preset. Discovery labels this resolved and unattended onboarding accepts it. The fixture reproduced configure `multi`, build `release`, test `debug`, with no unresolved choices. On a fresh worktree the requested Debug test executable has not been built. Extend the preset fixture with mismatched and missing multi-config configuration values; require a compatible chain or explicit unresolved choice.

10. **`src/projectChecks.ts:536` (P2): an Xcode scheme may be paired only with a project/workspace that contains it.** Schemes are collected globally, then multiplied across every selected workspace; workspace project references are never checked. With workspace A referencing project A and an unrelated project B, discovery offers `xcodebuild test -workspace A.xcworkspace -scheme B`. The fixture reproduced that invalid pairing, which cannot run B's tests through A. Extend the existing Xcode fixture with an unrelated project/shared scheme and assert container membership for every offered command.

### Shared finding

11. **`src/doctor.ts:534` (Codex) / `src/doctor.ts:531` (Claude), P2: diagnostics for a running issue must inspect its effective frozen checks, so later owner settings cannot hide a required missing executable or invent an active-issue requirement.** Both public `doctor` paths load the current workspace config and pass it straight to `checkDeclarations`, without resolving the active issue's frozen policy. If an issue freezes a now-missing executable and the owner later saves empty settings, doctor no longer reports that required executable. Codex's change in `inspectStartupAgent` constructs a frozen config but passes it only to `checkClone`, not the command-declaration check, so it does not close this gap. Add a doctor regression around re-onboarding while an issue is active; inspect the frozen commands for the active issue and distinguish settings intended for future issues.

### Scope, reuse, and verification

Both implementations keep the work in onboarding, existing signal/review flow, verification, persistence, reporting, and documentation. Both reuse the existing schemas, argv execution, workspace configuration, locks, evidence machinery, and fresh verification worktrees. Neither adds a dependency, test framework, separate approval phase, product-hook rewrite, or package-version change. Their two new modules have the responsibilities justified by the plan. Codex's additional doctor and hook fixture edits were explicitly approved scope amendments, not an unapproved expansion. Claude leaves the planned active-policy doctor behavior incomplete; Codex's attempted change is insufficient as described above.

Both extend existing test files rather than creating a parallel fixture framework. Codex covers amendment recording, fresh-worktree execution, failure, config-save retry, and future activation, but its adoption test seeds an implementation selection and therefore misses actual solo/reviewed publication. Claude covers ordinary lineage carry-forward and native discovery, but the focused reproductions expose gaps in cumulative additions, ecosystem timing, malformed metadata, competing ecosystems, and native relationships. These need focused regression extensions rather than another framework or broad refactor.

For Codex's unchanged product pin, I previously observed the mandatory commit checks pass: lint, typecheck, 892 fast tests and 282 system tests; its pre-push e2e suite passed both tests. Claude's terminal record reports a passing product `check:fast` hook, but I did not obtain clean per-pin suite results for its other checks and do not count their absence as a pass. The accepted-submission records contain no coordinator `checkResults` for either pin in this local-verification issue.

During this comparison I ran only focused diagnostic reproductions: six Claude helper/discovery scenarios against its exported source, Codex's real R7 bound-input helper plus publication-digest calculation, and Codex's existing built resolver/parser with the small Python argv example. Temporary discovery fixtures were removed. No CMake or Xcode build was run, no full suite was repeated, and no coordinator final check is claimed. The remaining findings are identified above by their concrete code paths and proposed regression cases. Product code was not changed for this review.
