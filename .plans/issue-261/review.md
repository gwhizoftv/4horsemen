The acceptance authority is [issue 261 and its owner design comment](https://github.com/gwhizoftv/4horsemen/issues/261#issuecomment-6483409830), including guided native commands, saved timing, intentional empty policies, and reviewed additive check adoption. This is a plan review, not a claim that any implementation or product suite passed.

## Findings

1. **[P1] Muse — “Reuse and Scope,” scope limits, and Conclusion replace required onboarding/adoption behavior with opt-in and re-declaration.** The rule is that ordinary onboarding discovers runnable alternatives, asks timing, saves settings without JSON authoring, and that an agent-added entry point can become a check for the running issue through normal implementation review. The plan expressly excludes native command discovery, requires `--allow-no-checks` or an explicit declaration, and only upgrades checks by reinstalling for a later issue. Following it, an unattended first-time native repository still fails without the new flag; an interactive owner gets no command/timing selection; and an accepted new test script in a no-checks issue is never run before that issue publishes. These are required behavior, not optional follow-up scope. Retain the existing interfaces, but include the design comment's selection, persistence and additive handoff paths.

2. **[P1] Muse — the install/onboard file-map change and the marker-only onboarding test omit the local verification opt-out.** The rule is that choosing no automated checks must produce a usable workspace with empty command lists, while an absent `verify` remains an actionable error. The plan changes only final `checks`, explicitly leaves `verify` semantics unchanged, and its new native proposals invent no commands. For a marker-only Xcode repository, `--allow-no-checks` therefore yields `checks: []` but no `verify`; `checkDeclarations` in `src/doctor.ts:453` still emits `verifyUndeclared`, and `verifyCommands` still blocks product commits. The promised onboarding test cannot succeed as described. The intentional no-check selection must also record both empty local phase lists.

3. **[P1] Claude — Summary item 4 and the `src/action.ts`/`src/orderScaffold.ts` changes assume reviewers already receive the proposal-bearing signal.** The rule is that new commands must be visible and bound to the implementation review before their execution is authorized. Existing `deriveBoundInputs` binds the product pin for comparison and consensus (`src/runLoop.ts:628` and `src/runLoop.ts:650`), and `materializeBoundInputs` exports its product worktree, not the later readiness-signal commit. A normal agent commits code at P and then publishes a signal with `checkProposal` at S; the worktree at P contains no signal from S. Storing the proposal in private accepted state and adding a generic reviewer sentence does not expose those commands or bind their bytes into review inputs. The plan can therefore execute commands the peers were never given to review. Bind and expose the signal/proposal evidence alongside P, with an identity that changes when the proposal changes; include any necessary materialization file in the map.

4. **[P1] Claude — `src/cli.ts` start-time activation checks only that each adopted entry-point path exists.** The rule is that an unmerged addition must not activate on a baseline that lacks the new runnable entry point. An implementation can add `test:native` to an already-existing `package.json` and propose `npm run test:native` with that manifest as its supporting path. Another issue starting from the old main already has `package.json`, so the proposed `cat-file -e` gate activates the command even though the script does not exist there; final verification now fails because of an unrelated unmerged change. The same failure applies to a new Make target or CMake preset in an existing file. Require evidence for the introduced entry point, such as introducing-pin ancestry or matching approved content, rather than pathname existence alone.

5. **[P1] Claude — `verifyFinalizationChecks` takes only the proposal on the latest submission whose product pin exactly equals the consensus pin.** The rule is that an entry point proposed with an implementation must survive normal authorized revisions unless review explicitly rejects/corrects that pending proposal; optional omission must not silently discard the handoff. Implementation P can contain a test script and proposal, then revision Q can retain that script while changing unrelated code and omit the optional proposal. Q is approved. The proposed exact-pin lookup finds Q without a proposal and runs only the frozen empty policy, so the new tests are never adopted or executed. Bind/carry the selected lineage's pending proposal into revision context and define explicit preservation/correction semantics before final authorization.

6. **[P1] Claude — `publishAcceptedFinalization` treats adoption persistence failure as nonblocking, with retry promised only on restart.** The rule is that accepted commands must be durably available to future issues, and recovery must have a reachable retry path. If the workspace write fails and publication continues, the existing loop marks publication completed and can finish the issue. `publishAcceptedFinalization` immediately ignores completed records (`src/runLoop.ts:2936`), and the normal tick only invokes it for pending/failed publication (`src/runLoop.ts:3445`). Restarting that completed issue does not reach the promised retry. The check passes once but never reaches future settings. Either keep adoption persistence as an outstanding completion obligation or explicitly implement a durable recovery path that still runs after publication/issue completion.

7. **[P2] Claude — “Risks and Mitigations / Config write races” says atomic read-modify-write prevents loss and a lost write remains unadopted.** The rule is that concurrent onboarding and adoption cannot lose an accepted addition or owner setting. The named existing helper, `atomicWriteJson` (`src/state.ts:1070`), atomically replaces bytes; it does not serialize the read/merge/write transaction. Onboarding and adoption can both read C, adoption writes C+A and marks A adopted, and onboarding then writes its older C plus another setting. Both writes succeed, so A is lost while its amendment is already marked adopted; the proposed retry condition never fires. Specify a shared transaction lock or conflict detection across both writers, including rereading under that protection, and cover the interleaving in the existing tests.

8. **[P2] Claude — `readSavedCheckSettings` intentionally parses only `verify`, `checks` and `adoptedChecks`, allowing unrelated invalid configuration to regenerate.** The rule is that a malformed existing configuration must produce an actionable error rather than silently becoming a different or empty policy. A saved config with valid base lists but malformed coordinator `verification` or documentation policy is accepted by the proposed partial reader, while the existing `readPreviousConfig` catches the full-schema failure and returns null (`src/install.ts:231`). Regeneration can discard those required settings without an error. Distinguish a deliberate, documented compatibility migration from invalid policy; validate all saved policy fields before overwriting the workspace.

9. **[P2] Claude — the exact file map and Tests omit `test/install.test.ts` although install now succeeds without inferred final checks.** The rule is that the plan must authorize every file needed to satisfy the required product checks. Existing cases at `test/install.test.ts:545` and `test/install.test.ts:735` demand `Cannot infer finalization checks` for a plain repo with a verify-only declaration, and the latter also demands that no clone was created. The planned announced-empty behavior changes those exact cases, so the mandatory system suite fails while the implementation is forbidden to update the missing test file. Add that file and replace the obsolete refusal cases with the intended no-check behavior while retaining preflight-error coverage for genuinely invalid inputs.

**Scope, reuse and test assessment.** Muse reuses existing helpers and creates no files, but its narrower scope excludes mandatory behavior; it is not a complete alternative for this issue. Its focused test command also points install/onboard cases at `vitest.config.ts`, which explicitly excludes those files; use `vitest.system.config.ts` for them. Claude largely stays within the owner's requested behavior, reuses the runner/workspace/prompts and justifies its new setup module and corresponding test file. Its test list is targeted, but misses the proposal-visibility, revision carry-forward, existing-manifest activation and persistence interleavings above, as well as the obsolete install expectations.

Codex's bound plan covers these integration boundaries explicitly: proposal signal materialization and review hashes, authorized lineage, effective-policy publication binding, serialized persistent adoption, baseline code evidence, frozen local policy, and the existing install tests. Its two new modules have distinct shared responsibilities and their tests extend existing support. The 30-path map is broad because the owner requires onboarding and current/future issue adoption together; it does not add framework scaffolding, CI interpretation, a new approval phase or new dependencies. I found no additional blocking plan defect in this bound version. This is a self-review observation, not implementation verification.

## Conclusion

Request revisions to Muse and Claude at the cited pins. Muse does not implement the authoritative design comment, and its opt-in native path still leaves local verification undeclared. Claude addresses the intended feature set but needs the concrete review-binding, activation, carry-forward, persistence and file-map corrections above before implementation. Codex `f1d01874ea5d2ccda3d0d07259113c9f9537c8ad` is the complete starting plan among these inputs, subject to the normal peer review and ballot.
